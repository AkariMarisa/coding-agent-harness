## 1. 结论

- M0/M1/M2 的代码闭环已跑通；M3 控制面路由已落地。
- 真正的缺口不在代码，而在**环境与真实流量**：容器内没有 goose/OpenCode/LiteLLM，也没有 provider API key 与账单，所以外部 adapter canary、native vs adapter A/B、CPVT 校准都还无法完成。
- 因此当前可以说“路由协议可用了”，不能说“M3 退出标准已满足”。

## 2. 环境卡点

| 卡点 | 影响 | 现状/绕过 |
|---|---|---|
| 容器内没有 `goose` | 无法跑真实 goose adapter canary；M1/M2 的“真实外部 adapter”退出标准悬空 | 只跑过 mock/native；需把二进制加入镜像或挂载 |
| 容器内没有 `opencode` | 无法跑第二个外部 adapter canary | 宿主机有 `/usr/bin/opencode`，但容器不可见 |
| 容器内没有 LiteLLM 服务 | M3 的 LiteLLM 路由、usage 日志、账单对账无法现场验证 | 只保留设计；可先用 native 直连 OpenAI-compatible 做路由验证 |
| 没有 provider API key | 无法跑真实模型、真实 usage、真实失败分布 | 离线测试统一用 `LOOM_NATIVE_SCRIPT` 脚本化 provider |
| 没有 provider 账单/usage 导出 | `cost_source=provider` 无法实测；成本只能用价格表估算 | 本地估算统一标 `pricing_table`，未知价格标 `unknown` |
| 订阅 lane 需要账号持有人登录 | 订阅 vs API 的额度/限流对比无法自动化 | 按设计后置，不阻塞 M0–M3 |

> 容器构建只保证 Rust + git；`curl` 也不在镜像里。涉及网络或外部二进制的验证，先补镜像或显式挂载，再谈“canary 通过”。

## 3. M2 未闭环项

1. **真实 goose / OpenCode canary**：mock/native 通过不等于外部 adapter 契约通过。需要二进制后重跑 `loom adapter canary <kind> --live --task ...`。
2. **native vs adapter A/B**：需要同一任务集、真实模型、相同预算，按 CPVT/TPVT/墙钟比较；当前没有基线数据。
3. **成本预算校准**：`ModelCapability::estimate_cost` 只是本地价格表估算；真实账单可能含缓存写、reasoning、阶梯价、时段折扣，尚未对账。
4. **失败包长期效果**：同一 run 内 acceptance 回灌与上一 run `FailurePack` 已实现，但还没有“带失败包 vs 不带失败包”的 CPVT/首过率对比。

## 4. M3 已落地与未闭环

### 4.1 已落地

- `[routing]` 配置：`roles`、`escalate_after_failures`、`max_escalations_per_task`、`fallbacks`、`cost_limits`。
- 确定性路由：显式 `--model` > 配置的 role→tier > 任务自带 tier；不调用 LLM 判断难度。
- 升级：只按 `task.failed` 事件次数触发；默认 worker 失败 2 次转 frontier，每任务最多 1 次；写 `task.escalated`。
- 成本护栏：任务预算超过 tier 上限，或价格表估算的最坏成本超过上限时拒绝派发。
- 可解释：`loom route TASK` 展示 tier、模型、原因、fallback、预算、估算与问题列表；`loom route stats` 从事件日志统计 worker 占比、升级次数、fallback 次数与路由原因。
- `dispatch` 允许重试 `failed`/`escalated` 任务，并在 `TaskDispatched.data.route` 记录决策。
- 同层 fallback：只对可用性失败（退出码 4 / 超时）按 `[routing.fallbacks]` 顺序切换；跨层在配置加载时被拒绝；显式 `--model` 不切换；每次切换写 `task.fallback` 并为新 attempt 开独立 run；`attempt` 不变，升级阈值不受污染。

### 4.2 未闭环

| 项 | 缺口 | 下一步 |
|---|---|---|
| worker 占比 ≥50% | 统计口径已可测（`loom route stats`），缺真实任务集 | 用固定任务集跑 role→tier，检查 `tasks.worker_share` |
| CPVT −20% | 需要真实账单与同任务集对照 | 跑 worker-only vs role→tier 两组，按 `loom ledger` 比较 |
| 质量不退化 | 需要首过率/verify 通过率/defect escape | 固定任务集，记录 first-pass verify 与人工返工 |
| fallback 真实效果 | 只在 mock 上验证过；真实 provider 的 5xx/限流分布未知 | 拿到 key 后用故障注入或真实抖动跑 A/B，看 `route stats.fallbacks` 与误升级率 |
| LiteLLM canary | 无服务、无账单日志 | 补 LiteLLM 服务后验证 model alias、usage 透传、错误码 |

## 5. 已知技术债与风险

1. **native 只支持 chat wire**：`wire=responses/messages` 的模型不能直接走 native；当前路由不按 adapter 过滤 wire，可能选出 native 不支持的模型。需要后续把 adapter 能力纳入路由过滤，或由 adapter 明确报错。
2. **native 无 streaming、无同 run 内重试**：provider 5xx/超时会让整个 run 以退出码 4 结束，模型没有“换个端点重试一次”的机会；控制面 fallback 能换模型重跑，但要重新开 run、重新编译 packet，比同 run 内退避重试贵。
3. **fallback 会重置单 run 预算**：token/墙钟/成本都是 per-run，切换后新 attempt 拿到一份新预算。链长由 `[routing.fallbacks]` 决定（通常 1），但最坏情况是“每层预算 × (1 + 链长)”。跨层永远不参与，所以成本上限仍由 tier 护栏兜住。
4. **预算执行不一致**：`TaskBudget.max_cost_usd` 目前只有 native 在运行中强制执行；外部 adapter 只能靠回执后对账。
5. **mock adapter 的 usage 是合成的**：`cost_source=provider` 只是模拟，不能用于真实 CPVT/成本结论，只适合契约测试。
6. **失败包与 verify 日志**：`load_failure_pack` 读取上一 run 的完整 `verify.log`，再由 Context Compiler 截断；超大日志先读入内存，长期应改为按需读取/预览。
7. **路由字段未进事件 schema**：`TaskDispatched.data.route` 是自由 JSON；契约稳定前不要依赖字段名做外部工具。
8. **升级历史依赖事件计数**：如果手工删改 `events.jsonl`，升级次数会失真；事件日志仍是唯一事实源。
9. **无并发/锁**：当前默认单写者、单任务派发；M4 的锁、合并队列、2 并行尚未实现，不要同时跑两个写同一 worktree 的任务。
10. **价格表无版本校验**：`pricing_version` 可记录但未强制；价格变更后旧账本不会自动重算。
11. **role→tier 是 opt-in**：未配置 `[routing.roles]` 时仍以 TaskSpec 的 `tier` 为准，不会自动套用文档矩阵；这是为了避免已有项目行为突变。
12. **fallback 只看退出码**：判断依据是 `exit_code == 4 || timed_out`。退出码 4 目前靠 adapter 契约自觉（native 已把 provider 错误映射为 4）；如果某个 adapter 把 provider 错误报成 0，控制面不会切换，只会记成任务失败并可能误触发升级。
13. **`needs_input` / `blocked` 被 verify 记成失败**：`verify` 只把回执 `done` 当作 `claim_done`，其余状态会写 `task.failed`（`code=claim_not_done`），于是 agent 提一个问题也会计入 M3 升级阈值。设计见 [15](15-Agent运行时治理与工程化.md) §2；修之前不要用提问做正常流程。

## 7. 建议顺序

1. 补容器镜像：`goose`、`opencode`（或挂载）、`curl`、可选 LiteLLM。
2. 拿到 GPT + DeepSeek API key，先跑固定任务集的 native-only A/B，确认路由与成本口径。
3. 再跑真实 goose/OpenCode canary，最后才宣称 M1/M2 退出标准完成。
4. M4 之前不要开并发；当前没有锁与合并队列。
5. 先做 `doc/15` 里的 CI bootstrap 与 question protocol（不依赖真实模型），再做 churn 与 skills 评估。

同层 fallback 与 `loom route stats` 已完成，不再是待办。

## 8. 2026-11-07 新发现（设计稿）

以下四项已记录设计，但**未实现**，详见 [15-Agent运行时治理与工程化.md](15-Agent运行时治理与工程化.md)：

1. **写入抖动**：DeepSeek v4.1 flash 出现反复删除/重写；真正的浪费是全文进入 `messages` 后每一步重发，而当前 no-progress 只看 `mutated`。设计以步骤级上下文重编译 + patch-first 为主，不以阻止写入为主。
2. **提问阻塞**：`needs_input` 被 verify 记成 `task.failed`；外部 agent 还可能挂起等 stdin，缺少结构化问题协议。
3. **skills 治理**：未验证 skill 不能全局安装；需要仓库画像、离线目录、按需加载、静态检查与评估后晋升。
4. **本地 CI bootstrap**：`loom init` 只建骨架，不探测技术栈、不生成 acceptance/CI，agent 缺少可信的本地反馈回路。
