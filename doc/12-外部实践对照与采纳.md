# 12 外部实践对照与采纳（2026-11）

> **来源**：两份 2026-11-05 的元宝对话（<https://yb.tencent.com/s/xDULZPSc4rGJ>、<https://yb.tencent.com/s/ayaF5zkD04ow>）。
> 内容是 AI 生成 + 二手整理，模型名、价格、字段名和统计口径都可能过期或错误；本文只提取“对 Loom 有增量”的部分，落地前必须本机核实。
> 与 [11](11-订阅额度与Agent-SDK.md) 重叠的订阅结论不重复展开；本文重点是多模型、并发、观测口径和混合 lane。

---

## 0. 一句话结论

两份材料的共同结论与 Loom 一致：**账单主因是历史重发和工具结果膨胀，不是压缩率；不要自研完整 harness；薄编排 + 状态外置 + 四行回执 + verify 升级是正确方向。**

真正的增量有五个：

1. 并行子 agent 不是越多越好，**先按 2 并发**；
2. 选模型要记录**能力位**（thinking、协议、缓存价），不能只写模型名；
3. 订阅做决策、API 做执行的**混合 lane** 比“全链路套网关”更省；
4. Headroom 的 `WasteSignals` / `agent_usage` / `mode` 有明确的**观测与配置边界**；
5. spec 是**决策工作**，不是文档工作，不能交给“长上下文但事实可靠性弱”的模型直接定稿。

**当前约束（2026-11-05）**：前期可提供 GPT、DeepSeek、Kimi、MiniMax、MiMo 等 **API key**，所以 v1 可以先做 API lane 多 provider：GPT `frontier` + DeepSeek `worker` 起步，其他国产模型按 A/B 逐步接。真正后置的是**订阅套餐对接**和本文的混合 lane，它们不阻塞 M0–M2；前期投入订阅对接不划算。

## 2. 采纳：并发先 2，不先 3

外部材料的公开数据：

- 单 agent 约为单轮对话的 4× token，多 agent 约 15×；
- Claude Code 子代理 fan-out 实测 51.3 万 input token，顺序执行 12.1 万，约 4.2×；跨模型族 2.6–5.9×，且没有更快；
- Codex 团队经验：超过 2 个并行子代理“几乎肯定在烧 token 而不提升质量”；
- 父上下文通常不会吞掉子代理完整 transcript，开销来自**每个子代理都是一套独立 agent loop**，各自重读 system prompt 和工具表。

我们的实测也出现过“prompt 协议降低单次通信 token，但 subagent 并发下降、整体变慢”。两者一致。

### 2.1 规则

- **M4 从“3 并行”改为“2 并行起步”**；
- 3 并行必须同时满足：文件所有权完全不重叠、共享文件已串行化、A/B 证明 `WPT` 与 `CPVT` 不退化；
- 子代理完成时通知一次，**不要轮询进度**；
- 并行 task 的写集必须不相交；`schema`、锁文件、迁移、依赖清单等共享文件由 orchestrator 串行合并；
- 并发上限按 `credential_lane` / `quota_pool` 再收紧，不只看进程数。

### 2.2 落点

- [08](08-设计路线-v0.2.md) M4 退出标准；
- [04](04-上下文与成本模型.md) §4.3；
- TaskSpec 的 `paths` / 写集声明（M1/M4）。

## 3. 采纳：记录模型能力位，不只记模型名

外部材料显示 2026-10 之后模型迭代很快：强制 thinking、`reasoning_content` 必须回传、模型 ID 硬下线、缓存价随时段变化。把模型名写死在调度器里会迅速腐烂。

### 3.1 能力位

| 能力位 | 取值 | 影响 |
|---|---|---|
| `thinking_mode` | `off` / `optional` / `forced` | 强制 thinking 的模型不放进多轮工具链，除非有透传通道 |
| `reasoning_passthrough` | `required` / `optional` | 需要原样回传 `reasoning_content`，压缩器不能改写 |
| `wire` | `chat` / `responses` / `messages` | 决定网关、压缩器、计费是否覆盖 |
| `context_window` / `max_output` | 数值 | 切片与预算 |
| `cache_price` | 数值 | 真实成本主项，不是列表单价 |
| `model_id` | 固定版本或日期 | 变更必须重跑验收基线 |

### 3.2 规则

- 执行层优先选**能关 thinking、协议干净、可无状态一次调用**的模型；
- 强制 thinking 的模型只用于单轮、无状态、可重跑的任务；
- 不一次接四家廉价模型；先 **1 主力 + 1 fallback**，按 task 类型 A/B 后再扩；
- 模型 ID 下线、价格时段变化、缓存价变化都要进版本管理；
- 模型别名必须映射到**真实模型 + 能力位**，账本同时记 alias 和真实模型。

### 3.3 落点

- [04](04-上下文与成本模型.md) §6.5；
- [06](06-技术选型.md) §5.6；
- [11](11-订阅额度与Agent-SDK.md) §5.1（`credential_lane` 增加能力位）。

## 4. 采纳（后置）：混合 lane（订阅决策 + API 执行）

> **优先级：后置。** 当前先用 API key 多 provider，不实现订阅控制面；本节只保留形态，等订阅可用后再评估。

外部材料对“harness → goose → LiteLLM/Headroom → Agents SDK → Codex”的判断是：结构上更费，因为凭证体系把链路劈成两半，多一层 agent 就多一套上下文和缓存，压缩也够不到最终请求。

这与 [11](11-订阅额度与Agent-SDK.md) 的结论一致，但补上了一个有用的形态：

```text
[控制面 / 决策面]
  Codex / Claude 订阅（官方客户端直连，短稳定前缀）
        │  TaskSpec + 验收标准
        ▼
[执行面]
  廉价 API 模型 → Headroom（cache）→ LiteLLM → provider
        │  四行回执 + 文件引用
        ▼
[验收面]
  本地 verify / 廉价模型；只回结构化结果
```

### 4.1 规则

- 订阅 lane **不要**插 LiteLLM；Responses 的 reasoning item 和自定义工具类型翻译会丢结构；
- 执行面才用 `Headroom → LiteLLM`，这里正是压缩和路由的主场；
- 两平面只交换 **TaskSpec + 四行回执 + 文件引用**；执行面的 transcript 不回流控制面；
- 控制面只保留目标、约束、决策、回执索引，不读 diff/日志全文；
- 账本分开记 `api_equiv_usd`、`allowance_burn`、`provider_cache_discount_usd`，不混加；
- 混合 lane 后置，不改变当前“API key 多 provider”的主线；等订阅真正可用再做。

### 4.2 落点

- [11](11-订阅额度与Agent-SDK.md) §6.4；
- [02](02-总体架构.md) 拓扑图（后续补混合 lane）。

## 5. 采纳：Headroom 观测口径

外部材料给出了几条容易踩的坑：

| 现象 | 正确口径 |
|---|---|
| `WasteSignals` 很大 | 是**累计检测量**，不是节省；A/B 只看 `Δ值 / Δrequests` |
| `reread_compressed: 0` | 归因逻辑未落地，不能当“压缩失效”判据 |
| `share_of_saved_percent` >100% | 分母可能用错，禁用 |
| `agent_usage` 有 `codex` / `pi-extension` | 可能来自 `aggregate fallback`；精确归属看 `agents[]` 的 `source` |
| `requests.by_client` | 可能为空，不能当唯一归属来源 |
| `mode` | 进程级配置，不能按请求或 model 切 |
| 客户端分类 | 看 `User-Agent` / `X-Client`，**不看 model** |
| 订阅态压缩 | `AuthMode=Subscription` 时更保守：lossless-only / live_zone_only / `max_lossy_ratio` 更低 |

结论：

- Headroom 继续 `mode=cache`，不按模型切模式；
- 真要两种模式，只能按**客户端 / 端口**在进程边界分实例；
- `provider_cache_discount_usd` 单独记，不与压缩节省相加；
- 订阅请求不能用 LiteLLM 的 `$0` spend 做预算。

落点：[10](10-工具输出协议-v0.1.md) §8.1、[04](04-上下文与成本模型.md) §7.3。

## 6. 采纳：spec 是决策工作

外部材料的一个关键判断：实现者从全新上下文启动，简报里没写的就得重新发现或靠猜；**spec 错了，错误会乘以 task 数量**，而便宜模型只会忠实地把错误实现出来。

### 6.1 规则

- `spec` / 接口契约 / 验收标准由 frontier 定稿；便宜模型只能起草候选，必须过 deterministic verify 或人签核；
- 长上下文模型（如 Gemini Flash 一类）适合做“全仓扫描 → 结构化候选”，**不适合直接产出最终 spec**；
- 扫描结果不进每轮上下文；只把编号化、短、稳定的 AC 放进 TaskSpec；
- AC 至少覆盖：正常路径、失败路径、权限/空状态/重复请求、非目标保护；
- 验收证据必须能映射回 AC 编号。

### 6.2 落点

- [04](04-上下文与成本模型.md) §6.2；
- [08](08-设计路线-v0.2.md) M1 prompt 库、M2 原生执行器。

## 7. 采纳：S 阶段止血清单（单模型也能降）

不改架构、不接多模型，先把“长会话”变成“长任务 + 短上下文”：

1. 主会话只切任务、派发、验收，不直接写代码；
2. 每个实施切片独立上下文；
3. 子代理结尾固定四行回执，其余写文件；
4. 工具结果按引用返回（`wrote 300 lines to ...`），不回贴全文；
5. 合并批量读：一次 grep 带上下文，不“先 grep 再开文件”；
6. 状态文件放 `.loom/`，不放聊天记录；
7. goal / step / token 三重上限；
8. 验收留在下层，只回结构化结果。

验收：同一任务跑两遍，只比 `CPVT` 和 `cache_hit`。先证明“单 GPT + 上下文隔离”有效，再谈多模型。

> 这组动作与 [08](08-设计路线-v0.2.md) 的 M0/M1 一致，区别是它不需要先有完整 CLI；可以作为手工止血清单。

## 8. 不采纳 / 需谨慎

| 观点 | 判断 |
|---|---|
| 双实例 `token` / `cache` 按 model 分流 | **撤回**：`mode` 是进程级，且 Headroom 在 LiteLLM 前看不到最终模型；只能按客户端/端口分实例 |
| 按 `X-Client` 打标“纠正”归属 | 归属已精确时无收益；Subscription 隐身态可能要求不改 UA/不加头，先验证 |
| 把 Gemini 当 spec 最终作者 | 事实可靠性、啰嗦、长上下文加价；只做扫描候选 |
| 一次接四家廉价模型 | 协调税高；先 1 主力 + 1 fallback |
| 强制 thinking 模型进多轮工具链 | `reasoning_content` 缺失可能 400；除非做全量透传通道 |
| 订阅 OAuth token 经第三方代理转发 | 条款/风控风险；v1 不做 |
| 过度压缩工具输出 | 可能引发重取循环，省 token 反而涨账单；用 A/B 验证 |
| 把 Headroom stats 当账单 | 只作诊断；以 provider/LiteLLM 为准 |
| 用模型自评“这题难”触发升级 | 只在 verify 失败时升级 |
| 用 LLM 自评复杂度做自动路由 | M3 之前不做；先固定 tier + 显式规则 |

## 9. 对路线图的影响

| 里程碑 | 改动 |
|---|---|
| **M0** | 不变；把 S 阶段清单写进文档，作为手工止血路径 |
| **M1** | TaskSpec / ledger 增加 `capability`；prompt 库加 AC 模板；telemetry 加观测口径；不实现订阅维度 |
| **M2** | 原生执行器：回执协议、引用返回、批量读、预算；模型能力目录（先 GPT + DeepSeek） |
| **M3** | 多 provider tier 路由：GPT frontier + DeepSeek worker 起步；Kimi/MiniMax/MiMo 按 A/B 扩；1 主力 + 1 fallback |
| **M4** | 2 并行起步；文件所有权；3 并行需 A/B 证明 |
| **后续** | 订阅 lane、混合 lane；不阻塞 M0–M4 |

## 10. 待验证

1. Headroom 原生 `/v1/responses` 对 Codex 订阅的压缩率与头透传；`requires_openai_auth` / `ChatGPT-Account-ID` 是否必须。
2. LiteLLM guardrail 是否真的只覆盖 `/v1/chat/completions` 与 `/v1/messages`，不覆盖 Responses。
3. `X-Client` 在 Subscription 链路是否会被转发、是否破坏上游认证。
4. 强制 thinking 模型的 `reasoning_content` 透传对缓存前缀的影响。
5. 2 并行 vs 3 并行的 `WPT` / `CPVT`；文件所有权冲突率。
6. 模型版本下线、价格时段、缓存价变化对 `CPVT` 的影响；模型 ID 固定策略。
7. “过度压缩导致重取循环”的本机复现：截断阈值与 `reread` 增速的关系。

> 第 1–3 项依赖订阅 lane，等启用后再验证；当前 API key 多 provider 阶段不阻塞。第 5–7 项属于主线。
