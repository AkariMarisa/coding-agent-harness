# 05 实施路线

> **v0.2 修订（2026-11-04）**：S 阶段已由 [08-设计路线-v0.2.md](08-设计路线-v0.2.md) 的 M0 替代；不再先做 pi 插件/手工文件，而是先做独立 CLI + 状态所有权。  
> P0–P4 的验收思路仍可复用，阶段编号与时间以 08 为准。

## 0. 原则

1. **先止血，再自动化，再路由，再并行。** 不跨阶段偷跑。
2. **每阶段可独立回滚**；保留上一版配置、prompt、schema。
3. **每阶段有可测的退出标准**；不达标不进入下一阶段。
4. **单 GPT 也能拿到大部分收益**；多模型是 P2 的事。
5. **不以工具数量衡量进度**；以 CPVT、first-pass verify、cache hit 衡量。

## 1. 阶段总览

| 阶段 | 时间 | 目标 | 新增组件 | 退出标准 |
|---|---|---|---|---|
| S | 0–2 天 | 单 GPT 止血 | `.agent/` + prompt + 手动 subagent | 10 任务全回执；主上下文 ≤30k；基线 CPVT |
| P0 | 第 1 周 | 账本与基线 | C11 + 事件 + 对账 | 100% 归因；误差 <5% |
| P1 | 第 2–3 周 | 薄 runner | C1/C4/C6/C7/C13 | 20 任务；0 未验证合并；可恢复 |
| P2 | 第 4 周 | 路由 | C8 + LiteLLM | worker ≥50%；CPVT −20%；质量不退化 |
| P3 | 第 5–6 周 | 并行 | C10 + 锁 + 合并队列 | 3 并行；无丢更新；合并 <5min |
| P4 | 持续 | 优化 | 看板/A-B/工具治理 | CPVT −60%；cache ≥75%；handoff ≤5% |

## 2. 阶段 S：单 GPT 止血（0–2 天）

**不装 LiteLLM、不接 DeepSeek、不起第二个 proxy、不写 SDK、不调 Headroom 参数。**

### S-1 基线冻结

- 记录 `pi / codex / headroom / 插件` 版本到 `.agent/env.lock`。
- 记录当前配置：`mode=cache`、端口、模型、reasoning level。
- 选 5–10 个近期任务，记录：请求数、输入、缓存、输出、成本、墙钟。
- 计算基线 CPVT（总成本 / 通过验收的任务数）。

**产出**：`runs/baseline-YYYYMMDD/` 快照 + 一页纸基线。

### S-2 状态骨架

创建：

```
.agent/
├── GOAL.md
├── spec.md
├── design.md
├── contracts/
├── tasks.json
├── tasks/
├── receipts/
├── reports/
├── PROGRESS.md
├── DECISION.md
├── budget.json
└── env.lock
```

- 用 03 的模板填一个真实小任务。
- 跑一遍“新会话只读 `.agent/` 能否恢复”。

**退出**：新会话不依赖历史 transcript 能说清目标、任务、验收、进度。

### S-3 Prompt 协议

- orchestrator prompt：只做规划/派发/验收；不写代码；不读 transcript。
- worker prompt：只做切片；只读引用；只回四行；详情写 report。
- judgment prompt：只读证据包；输出 `fix_plan/split/reject/human`。
- 把 prompt 版本化到 `prompts/`。

**退出**：三次派发都能稳定得到四行回执；解析器通过。

### S-4 手动 subagent 派发

- 用现有 `@tintinweb/pi-subagents`（或 Codex subagent）派发。
- 每个 worker 独立上下文；仍用 sol（单模型阶段）。
- orchestrator 只接收四行回执；不接收 worker transcript。
- 每个任务独立 worktree（如果现有工具支持；否则先独立分支）。

**退出**：连续 10 个切片，主会话上下文 ≤30k；无 transcript 回贴。

### S-5 工具结果治理

- 工具结果 > 4k tokens：写文件，返回路径 + 摘要 + 行号。
- 禁止回贴完整 JSON/HTML/日志/diff。
- 合并批量读：一次 grep 带上下文；按 range 读文件。
- 同一文件任务内只读一次；重复读要说明理由。
- 在 worker prompt 中写死这些规则。

**退出**：`json_bloat` / `reread` 的“Δ值/Δrequests”增速下降；主上下文不因工具结果爆掉。

### S-6 Goal 上限

- `pi-goal.json` 设置 `automaticTurns`、`noProgressTurns`；按实际调整。
- 达到上限必须停，输出状态与证据，不无限续跑。
- 预算：单任务/单 run 上限写入 `budget.json`；先人工检查。

**退出**：无“无限续跑”事故；每次停止都有明确原因。

### S-7 每日账本（手动）

- 每天记录：请求数、输入、缓存、输出、成本、通过任务数。
- 计算 CPVT；记录异常（重试、超时、人工介入）。
- 一周后对比基线。

**退出**：有连续 5 个工作日的 CPVT 曲线；能解释主要波动。

### S 阶段总退出标准

- 10 个任务全部有 TaskSpec + 四行回执 + verify 证据。
- 主会话上下文 ≤30k；无 worker transcript 回贴。
- 0 个未验证合并。
- 基线 CPVT 可计算；有 5 天数据。
- 没有改 Headroom 模式/参数；没有接多模型。

## 3. 阶段 P0：账本与基线（第 1 周）

### 目标

把“手动记账”变成“自动账本”，让 CPVT 可信。

### 工作项

1. 定义事件/账本 schema（03 §11–12）。
2. 从 Runtime / LiteLLM / provider 采集 usage；缺失字段标 `unknown`。
3. 实现 `loom ledger`：按 run/task/tier/model/day 聚合。
4. 实现 `loom reconcile`：与 provider 账单对账。
5. 实现 `loom report`：生成 run 报告（CPVT、cache hit、resend、handoff、verify）。
6. 告警：unattributed、成本超 80%、cache 下降 >10pp。

### 退出标准

- 100% 请求有 `run_id` + `task_id`（或明确 `unattributed` 且 <1%）。
- 账本与 provider 账单误差 <5%。
- 每个 run 自动生成报告。
- 能回答：哪个任务最贵、哪个 tier 最贵、重试花了多少。

## 4. 阶段 P1：薄 runner（第 2–3 周）

### 目标

把 S 阶段的手动流程变成可重复的 runner：任务图、派发、verify、预算、升级、恢复。

### 工作项

1. `loom init`：校验 `.agent/`、生成任务图骨架、记录 env.lock。
2. `loom plan`：frontier 产出任务图（或人写，runner 校验）。
3. `loom run`：Scheduler 选 ready → 创建 worktree → 派发 → 收据 → verify → merge。
4. Verify Runner：独立重跑 acceptance；证据落盘；flaky 处理。
5. Budget Governor：派发前估算 + 执行中 usage + 熔断。
6. Escalation：证据包 + judgment + 一次升级。
7. `loom resume`：从事件/状态恢复；不重跑已通过任务。
8. `loom status`：任务图、预算、异常、待人工。

### 退出标准

- 20 个任务连续跑通；0 未验证合并。
- 预算超限能停；重启后 5 分钟内恢复。
- 失败任务有证据包；升级不超过 1 次。
- 人工介入率 ≤30%。
- 主会话上下文仍 ≤30k。

### 明确不做

- 不做多模型路由（P2）。
- 不做并行（P3）。
- 不做复杂 UI；CLI 足够。
- 不做自动改 spec；spec 变更必须人确认。

## 5. 阶段 P2：路由（第 4 周）

### 目标

在不破坏缓存/压缩的前提下，接入 LiteLLM，按显式 tier 路由；验证 worker 模型是否真的降低 CPVT。

### 工作项

1. 部署 LiteLLM（本地/容器）；配置 alias `frontier` / `worker` / `worker-backup`。
2. 拓扑改为 `agent → Headroom → LiteLLM → provider`；保留直连回滚路径。
3. 兼容性矩阵（07）：流式、tool calls、usage、错误、Anthropic/OpenAI/Responses。
4. 在 3 类任务上试点 worker：survey、spec-tests、单模块 implement。
5. 路由护栏：无 verify 不走 worker；规格不清不走 worker；安全/跨模块默认 frontier。
6. 账本记录 alias + 真实模型；按 tier 聚合 CPVT。
7. A/B：同任务集 baseline（全 frontier）vs treatment（worker 试点）。

### 退出标准

- `by_model` 同时出现 frontier 与 worker；`routing` 非空。
- worker 承接 ≥50% 的试点实施任务。
- CPVT 相对 P1 下降 ≥20%（累计相对初始基线约 −40%）。
- first-pass verify 不下降超过 5pp；defect escape 不上升。
- 网关故障可回滚直连；无 tool call/streaming 兼容性事故。

### 明确不做

- 不做 LLM 自动复杂度路由。
- 不做第三档模型。
- 不为每个 provider 起独立 Headroom。
- 不按 `model` 字段切压缩模式。

## 6. 阶段 P3：并行与 worktree（第 5–6 周）

### 目标

在不丢更新、不冲突的前提下，让 2–3 个 worker 并行。

### 工作项

1. 每任务独立 git worktree + 分支；路径短、可清理。
2. 路径锁：读写锁、lease、TTL、owner 校验。
3. 合并队列：串行、rebase、合并前 verify、合并后集成 verify。
4. 任务图去重：相同输入哈希 + 相同输出路径不并行。
5. 冲突处理：小冲突自动 rebase；大冲突转 `human` 或拆任务。
6. 并行预算：run 总预算 + 单任务预算；避免并发放大超支。

### 退出标准

- 3 个 worker 并行跑 10 个任务；无丢更新/覆盖。
- 合并冲突率 <10%；合并时长 <5 分钟。
- 集成 verify 100% 通过；失败可回滚。
- cache hit 不因并行下降 >10pp。

### 明确不做

- 不做跨机器分布式调度。
- 不做自动解决语义冲突。
- 不做无锁并行写同一路径。

## 7. 阶段 P4：优化（持续）

### 工作项

1. 工具结果投影：JSON schema → 只保留字段；日志 → 摘要 + 路径；HTML → 正文。
2. 读缓存/索引：文件哈希、符号索引、增量读取。
3. Prompt 调优：更短的 worker 指令、更明确的输出契约。
4. 模型阶梯：用数据决定是否加第三档；不凭感觉。
5. 看板：CPVT、resend、cache、handoff、verify、escalation、human touch。
6. 每周 A/B；每月对账；每季度架构 review。

### 退出标准

- CPVT 相对基线 −60%。
- TPVT 相对基线 −60%。
- cache hit ≥75%（长期 ≥80%）。
- handoff overhead ≤5%。
- first-pass verify ≥70%。
- 无“优化导致质量下降”的回归。

## 11. 决策记录（与前序讨论的差异）

| 版本 | 原方案 | 修正 | 原因 |
|---|---|---|---|
| v0.1 | 双 Headroom 实例（8787/cache、8788/token），按 model 分流 | **撤回** | `mode` 是进程级；按 model 切不成立；缓存收益远大于压缩 |
| v0.2 | LiteLLM 在 Headroom 之前 | **改为在之后** | Headroom 透明转发；LiteLLM 负责 alias；多 provider 不需要多个 Headroom |
| v0.2 | 6 个 agent / 多档模型 | **收敛为两档** | 实际只有 sol；先证明 worker 收益 |
| v0.3 | `reread_compressed` 作为验收指标 | **禁用** | 归因逻辑未落地；累计量不可直接比较 |
| v0.4 | 先接多模型 | **改为先单 GPT 止血** | 历史重发是主因；单 GPT 也能降 CPVT |
| 本文 | 自研完整 harness | **只自研薄编排层** | Runtime/压缩/路由已有成熟组件 |

## 12. 迁移步骤

1. **冻结基线**：记录版本、配置、5–10 个任务数据。
2. **加 `.agent/`**：不改 runtime、不改 Headroom；只加状态文件与 prompt。
3. **手动派发**：用现有 subagent，跑 10 个切片；验证四行回执。
4. **加账本**：事件/账本/对账；确认 CPVT。
5. **加 runner**：任务图/verify/预算/升级/恢复。
6. **加 LiteLLM**：拓扑改为 Headroom → LiteLLM；小流量 canary。
7. **加并行**：worktree/锁/合并队列。
8. **持续优化**：工具治理、A/B、看板。

每一步都可回滚：保留上一版配置；LiteLLM 故障可直连；runner 故障可回到手动派发。

## 13. 运营手册

### 每日

- `loom status`：running / blocked / needs_input / budget。
- 看异常：失败、超预算、冲突、unattributed。
- 只处理需要人的任务；正常任务不干预。
- 记录当天 CPVT 与异常。

### 每周

- 汇总 CPVT、cache hit、resend、handoff、first-pass verify、escalation。
- 对比上周；解释 >10% 的波动。
- review `DECISION.md`：有没有错误结论被继承。
- 检查 waste signals 增速（Δ/Δrequests），不是累计值。
- 决定是否调整任务粒度/模型映射。

### 每月

- 与 provider 账单对账；误差 >5% 查。
- review 风险登记册；更新触发信号。
- 评估是否进入下一阶段；不达标不跳。
- 清理 worktree/日志；归档 run。

## 14. 完成定义（DoD）

一个阶段“完成”必须同时满足：

- 功能：该阶段 FR 的验收全部通过。
- 成本：CPVT 达到阶段目标，或至少不退化。
- 质量：first-pass verify / defect escape 不退化。
- 可恢复：kill 后能恢复；不重复已通过任务。
- 可审计：每个任务有 TaskSpec、回执、verify 证据、账本。
