# 03 核心协议

> 这份文档是 Loom 的“接口契约”。实现可以换语言、换 runtime，但协议编号与字段语义要保持稳定。所有**跨边界** JSON 都有 `schema_version`，所有跨边界内容都必须可校验。

## 1. `.agent/` 目录布局

```
.agent/
├── GOAL.md                 # 目标、非目标、总验收、预算
├── spec.md                 # 用户需求、场景、边界
├── design.md               # 架构、接口、数据模型、取舍
├── contracts/              # OpenAPI / JSON Schema / TS 类型，冻结接口
├── tasks.json              # 任务图索引（轻量）
├── tasks/
│   └── T-20261104-001.json # 单个 TaskSpec
├── receipts/
│   └── T-20261104-001.json # 结构化回执
├── reports/
│   ├── T-20261104-001.md   # 人读报告（详情）
│   └── T-20261104-001.verify.log
├── PROGRESS.md             # 追加式进度
├── DECISION.md             # 决策日志（ADR）
├── budget.json             # run/任务默认预算
├── env.lock                # 版本锁定
├── escalations/            # 升级证据包
├── locks/                  # 路径/文件锁（临时）
├── runs/                   # 每次 run 的快照（ignored）
├── events.jsonl            # 事件流（ignored）
└── ledger.jsonl            # 请求账本（ignored）
```

### 1.1 提交与忽略

| 路径 | git | 原因 |
|---|---|---|
| `GOAL.md` / `spec.md` / `design.md` | 提交 | 人可读、可 review |
| `contracts/` | 提交 | 接口契约，worker 共享 |
| `tasks.json` / `tasks/` | 提交 | 可审计、可重放 |
| `receipts/` / `reports/*.md` | 提交 | 验收证据 |
| `PROGRESS.md` / `DECISION.md` | 提交 | 决策与进度 |
| `budget.json` / `env.lock` | 提交 | 可复现 |
| `runs/` / `locks/` / `*.log` | 忽略 | 体积大/临时 |
| `events.jsonl` / `ledger.jsonl` | 忽略 | 高频写；需要时归档 |
| 密钥 | 禁止 | 安全 |

## 2. 人类可读文件模板

### 2.1 `GOAL.md`

```markdown
# GOAL G-20261104-auth

## 目标（一句话）
为现有 API 增加用户名/密码登录，支持 session 与回归测试。

## 背景与价值
当前只有注册，没有登录；前端无法完成鉴权闭环。

## 非目标
- 不做 OAuth / SSO
- 不做密码找回
- 不改数据库 schema（复用现有 users 表）

## 总验收（可执行）
- [ ] `pnpm test` 全绿
- [ ] `pnpm tsc --noEmit` 通过
- [ ] 手动 curl 登录成功并拿到 session cookie

## 约束
- 不新增运行时依赖
- 遵循现有错误响应格式
- 所有改动在 `src/api/auth/**`、`tests/api/auth/**`

## 预算
- 总成本 ≤ $5
- 总墙钟 ≤ 4 小时
- 最多 12 个任务

## 决策人 / 升级联系人
- 决策人：@akari
- 升级条件：连续 2 次 verify 失败、规格冲突、预算超限

## 状态
active
```

### 2.2 `spec.md`

```markdown
# SPEC

## 用户故事
作为已注册用户，我可以使用用户名/密码登录，并获得 session。

## 验收场景
### S1 正常登录
Given 已注册用户
When POST /api/auth/login 使用正确凭据
Then 200，Set-Cookie 包含 session

### S2 错误密码
Given 已注册用户
When 使用错误密码
Then 401，错误码 AUTH_INVALID_CREDENTIALS

### S3 缺失字段
When 缺少 password
Then 400，错误码 VALIDATION_ERROR

## 边界与不做
- 不做速率限制（后续任务）
- 不做多设备 session 管理

## 待决问题
- session 过期时间用现有配置还是新配置？
```

### 2.3 `design.md`

```markdown
# DESIGN

## 架构
POST /api/auth/login → AuthController → AuthService → UserRepository → SessionStore

## 接口
见 `.agent/contracts/auth.openapi.yaml`

## 数据模型
复用 `users` 表；session 存现有 `sessions` 表。

## 错误处理
统一 `{ code, message, requestId }`；错误码见 contracts。

## 测试策略
- 单元：AuthService 校验
- 集成：supertest 走真实路由
- 回归：现有 auth 测试全跑

## 取舍
- 不引入 ORM：复用现有 repository
- 不引入新依赖：用现有 crypto/session 库

## 风险
- 现有 session 中间件可能有隐式假设；先读 `src/middleware/session.ts`
```

## 3. 任务图 `tasks.json`

```json
{
  "schema_version": "1.0",
  "goal_id": "G-20261104-auth",
  "updated_at": "2026-11-04T12:00:00Z",
  "tasks": [
    {
      "task_id": "T-20261104-001",
      "title": "冻结 auth 接口契约",
      "status": "merged",
      "tier": "frontier",
      "depends_on": [],
      "spec": ".agent/tasks/T-20261104-001.json"
    },
    {
      "task_id": "T-20261104-002",
      "title": "实现 POST /api/auth/login",
      "status": "ready",
      "tier": "worker",
      "depends_on": ["T-20261104-001"],
      "spec": ".agent/tasks/T-20261104-002.json"
    },
    {
      "task_id": "T-20261104-003",
      "title": "补登录集成测试",
      "status": "pending",
      "tier": "worker",
      "depends_on": ["T-20261104-002"],
      "spec": ".agent/tasks/T-20261104-003.json"
    }
  ]
}
```

**规则**：

- `tasks.json` 只放索引；详情在 `tasks/<id>.json`。
- `status` 由 runner 维护；人不直接改（除人工取消）。
- `depends_on` 必须是同 goal 内的任务；循环依赖拒绝。
- 一个任务一个 `spec` 文件；路径不可复用。

## 4. TaskSpec

### 4.1 字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `schema_version` | string | 是 | 协议版本，如 `1.0` |
| `task_id` | string | 是 | `T-YYYYMMDD-NNN`，全局唯一 |
| `goal_id` | string | 是 | 关联 GOAL |
| `title` | string | 是 | 一句话，≤ 80 字 |
| `role` | enum | 是 | `survey / spec-tests / implement / review / judgment / docs` |
| `tier` | enum | 是 | `frontier / worker` |
| `depends_on` | string[] | 是 | 依赖任务 ID；可为空 |
| `workspace` | object | 是 | worktree/branch/路径权限 |
| `inputs` | object[] | 是 | 文件引用；不是内容 |
| `constraints` | object | 是 | 风格、依赖、最大改动 |
| `acceptance` | object[] | 是 | 至少 1 条 verify |
| `budget` | object | 是 | token/成本/步数/墙钟 |
| `output` | object | 是 | 回执/report/产物 |
| `context_policy` | object | 否 | 读取策略与上限 |
| `notes` | string | 否 | ≤ 500 字；不得替代 spec |

### 4.2 示例

```json
{
  "schema_version": "1.0",
  "task_id": "T-20261104-002",
  "goal_id": "G-20261104-auth",
  "title": "实现 POST /api/auth/login",
  "role": "implement",
  "tier": "worker",
  "depends_on": ["T-20261104-001"],
  "workspace": {
    "mode": "worktree",
    "base_ref": "main",
    "branch": "agent/T-20261104-002",
    "allowed_paths": ["src/api/auth/**", "tests/api/auth/**"],
    "forbidden_paths": ["migrations/**", "package.json", "pnpm-lock.yaml"]
  },
  "inputs": [
    {"path": ".agent/contracts/auth.openapi.yaml", "sha256": "9f2c…", "must_read": true},
    {"path": ".agent/design.md", "sha256": "a71e…", "must_read": true},
    {"path": "src/middleware/session.ts", "range": [1, 200], "must_read": true},
    {"path": "src/api/routes.ts", "range": [1, 160], "must_read": false}
  ],
  "constraints": {
    "max_files_touched": 8,
    "no_new_dependencies": true,
    "style": ["follow existing error envelope", "reuse session store"],
    "notes": "不要改 users 表；不要新增 ORM"
  },
  "acceptance": [
    {"id": "A1", "cmd": "pnpm vitest run tests/api/auth/login.test.ts", "expect_exit": 0, "timeout_s": 300},
    {"id": "A2", "cmd": "pnpm tsc --noEmit", "expect_exit": 0, "timeout_s": 300},
    {"id": "A3", "cmd": "pnpm lint --max-warnings=0", "expect_exit": 0, "timeout_s": 300}
  ],
  "budget": {
    "max_input_tokens": 120000,
    "max_output_tokens": 20000,
    "max_steps": 25,
    "max_wall_s": 1800,
    "max_cost_usd": 0.25
  },
  "output": {
    "receipt": "4-line",
    "report_path": ".agent/reports/T-20261104-002.md",
    "required_artifacts": ["git_diff", "verify_log"]
  },
  "context_policy": {
    "max_must_read_files": 5,
    "max_must_read_tokens": 40000,
    "allow_extra_reads": true,
    "forbid_full_repo_scan": true
  }
}
```

### 4.3 规则

- `inputs` 只传引用；跨边界必须带 `sha256`；大文件用 `range`。
- `must_read` 默认 ≤ 5 个文件 / ≤ 40k tokens；超了说明切片没拆好。
- `allowed_paths` 是白名单；`forbidden_paths` 优先级更高。
- `acceptance` 至少 1 条；每条必须非交互、可重复、有超时。
- `budget` 必填；`max_cost_usd` 可用估算值，执行中按实际 usage 校正。
- `notes` 不是需求；需求只能在 spec/design/contracts 里。
- worker 不得修改 TaskSpec；需要变更时回 `needs_input`，由 orchestrator 重写。

## 5. Receipt（四行回执）

### 5.1 文本格式

worker 结束时**只输出**以下四行，顺序固定：

```
status: done
branch: agent/T-20261104-002@7f3c2a1
verify: A1=pass,A2=pass,A3=pass; log=.agent/reports/T-20261104-002.verify.log
report: .agent/reports/T-20261104-002.md
```

| 字段 | 取值 | 规则 |
|---|---|---|
| `status` | `done / blocked / needs_input / failed / budget_exceeded` | 必填；`done` 不代表 verify 通过，只代表 worker 完成 |
| `branch` | `<branch>@<sha>` | 必须是本任务分支；sha 为 HEAD |
| `verify` | `<id>=pass/fail/skip,...; log=<path>` | 只写结果与日志路径，不贴日志 |
| `report` | `<path>` | 人读详情；≤ 1 行 |

### 5.2 解析规则

- 必须正好 4 行；允许行尾 `\r`；不允许空行、代码块、前言、后记。
- 字段名必须小写；分隔符为 `: `。
- `verify` 中每个 acceptance id 必须出现；缺失视为 `fail`。
- `branch` 的 sha 必须与 worktree HEAD 一致；不一致拒绝。
- 超过 100 tokens 或超过 4 行 → 解析失败，任务标记 `failed`。
- 不解析自然语言；worker 想解释，写 report。

### 5.3 结构化回执

runner 解析四行后，生成 `receipts/<task_id>.json`：

```json

  "head_sha": "7f3c2a1",
```

### 5.4 状态语义

| status | 含义 | orchestrator 动作 |
|---|---|---|
| `done` | worker 认为完成，已跑 verify | 独立重跑 verify；通过才 `passed` |
| `blocked` | 环境/依赖/权限阻塞 | 查锁/环境；可重派或转人工 |
| `needs_input` | 规格不清/需要额外引用 | 补 spec 或追加 `inputs`，重派 |
| `failed` | 主动放弃/无法完成 | 同层重试一次 → 升级 |
| `budget_exceeded` | 超预算中止 | 不自动重试；拆小或人工 |

> **不要用 worker 的 `status=done` 当验收。** 唯一验收是 runner 重跑 acceptance 的结果。

## 6. Verify 契约

### 6.1 基本要求

- 非交互：不读 stdin、不弹窗、不需要人工确认。
- 可重复：同一代码/环境多次运行结果一致。
- 有超时：每条命令必须带 `timeout_s`。
- 可观测：stdout/stderr 写日志文件；回执只带路径。
- 隔离：在任务 worktree 根目录执行；不依赖主工作区未提交改动。
- 退出码：`0 = pass`；非 0 = fail；超时 = fail。

### 6.2 证据

runner 为每条 acceptance 记录：

```json
{
  "id": "A1",
  "cmd": "pnpm vitest run tests/api/auth/login.test.ts",
  "cwd": "/worktrees/T-20261104-002",
  "exit": 0,
  "signal": null,
  "duration_s": 14,
  "timeout_s": 300,
  "log_path": ".agent/reports/T-20261104-002.verify.log",
  "log_sha256": "e3b0…",
  "git_sha": "7f3c2a1",
  "env_hash": "sha256:…",
  "result": "pass"
}
```

### 6.3 验收类型

| 类型 | 示例 | 证据 |
|---|---|---|
| 单元/集成测试 | `pnpm vitest run ...` | exit code + log |
| 类型检查 | `pnpm tsc --noEmit` | exit code + log |
| Lint/格式 | `pnpm lint` | exit code + log |
| 构建 | `pnpm build` | exit code + artifact |
| 接口契约 | `spectral lint openapi.yaml` | exit code |
| 性能 | `node bench.js --max-p95=200` | 输出 + 阈值 |
| 视觉 | Playwright 截图 | 图片 + 哈希 + diff |
| 文档 | markdownlint / link check | exit code |
| 人工验收 | 无法自动化的场景 | 人工签名 + 证据路径 |

### 6.4 反模式

- `verify: 手动看一下` —— 不可执行，拒绝。
- `verify: 跑一下相关测试` —— 不确定，拒绝。
- `verify: 如果失败就重试` —— 非确定性，拒绝。
- `verify: 通过则继续` —— 没有命令，拒绝。
- 把 verify 命令交给 worker 临时决定 —— 拒绝；命令只能来自 TaskSpec。

### 6.5 Flaky 处理

- 已知 flaky：TaskSpec 标记 `flaky: true`，最多重跑 2 次。
- 仍不稳定：任务转 `human`，并记录 flaky 证据。
- 不允许用“重跑到绿”掩盖不稳定测试；连续 flaky 要开修复任务。

## 7. Handoff 规则（跨边界通信）

### 7.1 允许传递

| 内容 | 形式 | 上限 |
|---|---|---|
| TaskSpec | JSON | ≤ 2k tokens（不含引用） |
| 文件引用 | path + sha256 + range | 每个引用 ≤ 1 行 |
| diff | patch 文件路径 + stat | 不贴全文 |
| verify 证据 | 结果 + 日志路径 + sha | 不贴日志 |
| 决策 | Decision ID + 一句话 + 路径 | ≤ 100 tokens |
| report | 路径 | 不贴内容 |
| 接口契约 | `contracts/` 路径 | 不贴全文 |

### 7.2 禁止传递

- 文件全文（除非是 `must_read` 且确实需要，用引用让 worker 自己读）。
- 原始 JSON / HTML / base64 / 大日志。
- worker 的思维链、完整 transcript、上一轮对话。
- 未经验证的结论（“应该可以”“我猜”）。
- 密钥、token、cookie、连接串。
- 其他 worker 的过程日志（只允许结构化回执/决策）。

### 7.3 通信预算

| 通道 | 预算 | 超限处理 |
|---|---|---|
| orchestrator → worker | ≤ 2k tokens | 拆任务/减少引用 |
| worker → orchestrator | ≤ 100 tokens（四行） | 写 report，不回贴 |
| judgment 证据包 | ≤ 20k tokens | 只放必要日志片段 + 路径 |
| 人工升级说明 | ≤ 500 字 | 附证据路径 |

### 7.4 对齐机制

- **单一事实源**：接口以 `contracts/` 为准，需求以 `spec.md` 为准，设计以 `design.md` 为准。
- **冻结接口**：跨模块任务开始前，先有契约任务；契约变更走设计任务，不靠聊天。
- **任务图去重**：相同输入哈希 + 相同输出路径的任务不并行。
- **路径所有权**：同一路径只允许一个写者；需要协作时拆成“写接口/写实现/写测试”。
- **禁止 worker 互聊**：需要协调时，由 orchestrator 创建协调任务或更新共享文件。

## 8. 升级协议

### 8.1 触发条件

只有以下情况允许升级：

1. 同一任务 verify 失败 2 次（首次 + 同层重试 1 次）。
2. `status=needs_input` 且 orchestrator 无法从现有 spec/design 补齐。
3. 路径/接口冲突，无法自动合并。
4. 预算超限，但任务价值高，需要人决定是否加预算。
5. 安全/合规风险。

**不允许**：模型自评“这题难”、模型自评“需要更强模型”、无证据的“可能有问题”。

> 如果 worker 主动回 `failed` 但没有 verify 证据，按 `verify_fail` 处理：允许一次同层重试；仍无证据则转 `human`。

### 8.2 证据包

```
.agent/escalations/T-20261104-002/
├── request.md          # 待决问题，≤ 500 字
├── task.json           # TaskSpec 快照
├── receipt.json        # 最近回执
├── diff.patch          # 代码改动
├── verify.log          # 失败日志（可截断）
├── decisions.md        # 相关决策引用
└── refs.json           # 文件引用 + 哈希
```

### 8.3 judgment 输出

```json
{
  "schema_version": "1.0",
  "escalation_id": "E-20261104-002",
  "decision": "fix_plan",
  "plan": [
    "先补 session 中间件的类型定义",
    "再复用现有 error envelope，不新增错误码"
  ],
  "refs": [".agent/design.md", "src/middleware/session.ts"],
  "max_attempts": 1,
  "human_required": false,
  "evidence_gaps": ["缺少 session TTL 配置的现值"]
}
```

`decision` 枚举：

| 值 | 含义 | 后续 |
|---|---|---|
| `fix_plan` | 有明确修复计划 | 新建 worker 任务，带 plan + 证据引用 |
| `split` | 任务太大/太模糊 | 拆成多个 TaskSpec |
| `reject` | 方案不可行/需求冲突 | 回到 spec/design，必要时找人 |
| `human` | 需要人决策 | 停止自动流程，发升级通知 |

### 8.4 次数限制

- 每个任务最多升级 1 次。
- 每个 goal 最多 3 次自动升级；超过转人工。
- 升级后仍失败 → `human`，不循环。
- 所有升级记录到 `DECISION.md` 与 `events.jsonl`。

## 9. 预算与熔断

### 9.1 `budget.json`

```json
{
  "schema_version": "1.0",
  "run": {
    "max_cost_usd": 5.0,
    "max_input_tokens": 5000000,
    "max_output_tokens": 500000,
    "max_wall_s": 14400,
    "max_tasks": 40,
    "max_escalations": 3
  },
  "defaults": {
    "task": {
      "max_input_tokens": 120000,
      "max_output_tokens": 20000,
      "max_steps": 25,
      "max_wall_s": 1800,
      "max_cost_usd": 0.25
    }
  },
  "tiers": {
    "frontier": {"max_cost_usd_per_task": 1.0},
    "worker": {"max_cost_usd_per_task": 0.25}
  }
}
```

### 9.2 执行点

| 时点 | 检查 | 动作 |
|---|---|---|
| 派发前 | 估算输入/输出/成本 | 超限拒绝派发，转人工/拆任务 |
| 执行中 | usage 流累计 | 80% 告警；100% 立即停止 |
| 回执后 | 实际 usage 对账 | 超限标记 `budget_exceeded` |
| run 结束 | 总成本/任务数 | 生成报告；超限告警 |

> 如果 runtime 不提供实时 usage：派发前用历史均值估算并预留 buffer；执行中用步数/墙钟兜底；回执后按实际 usage 校正。无法实时熔断时，宁可保守低估预算上限，也不要事后才发现超支。

### 9.3 无进展熔断

- 同一任务连续 3 轮无文件改动/无 verify 进展 → 停止。
- 同一错误连续出现 3 次 → 停止，升级。
- 同一文件被反复改回 → 停止，检查规格冲突。
- 熔断后保留 worktree、日志、回执；不自动重跑。

## 10. 错误分类

| code | 含义 | 可重试 | 默认动作 |
|---|---|---|---|
| `verify_fail` | 验收命令非 0 | 是（1 次） | 同层重试 → 升级 |
| `timeout` | 墙钟/命令超时 | 是（视原因） | 重试/拆任务 |
| `budget_exceeded` | 超 token/成本/步数 | 否 | 人工/拆小 |
| `tool_error` | 工具崩溃/权限/依赖缺失 | 是（1 次） | 修环境/重派 |
| `conflict` | 路径/合并冲突 | 否 | 人工/重排 |
| `ambiguous_spec` | 规格不清 | 否 | 补 spec/升级 |
| `env_error` | 环境/版本/网络问题 | 是 | 修环境 |
| `flaky_verify` | 测试不稳定 | 是（≤2 次） | 标记/修测试 |
| `security_blocked` | 命令/路径/密钥违规 | 否 | 人工审计 |
| `provider_error` | 429/5xx/鉴权 | 是 | 退避/同层 fallback |
| `parse_error` | 回执/schema 不合法 | 是（1 次） | 重派/修复模板 |
| `unknown` | 未分类 | 否 | 保留现场，人工 |

**原则**：错误必须分类后入库；`unknown` 比例 > 10% 说明协议或工具需要修。

## 11. 事件协议

### 11.1 事件格式

```json
{
  "ts": "2026-11-04T12:00:00.000Z",
```

### 11.2 事件类型

| 类型 | data 关键字段 |
|---|---|
| `run.started` | `goal_id`, `budget` |
| `goal.loaded` | `goal_path`, `spec_path`, `design_path` |
| `task.created` | `spec_path`, `depends_on` |
| `task.ready` | `deps_done` |
| `task.dispatched` | `tier`, `model`, `worktree`, `budget` |
| `task.started` | `pid`, `started_at` |
| `task.receipt` | `status`, `branch`, `head_sha` |

| `task.failed` | `code`, `verify_ids` |

### 11.3 写入规则

- 只追加；不修改历史。
- 事件写入失败不阻塞主流程，但必须告警。
- 每个事件有 `run_id`；跨 run 的任务用 `parent_run_id`。
- 敏感字段脱敏后再写。

## 12. 账本协议

### 12.1 请求级记录

```json
{
  "ts": "2026-11-04T12:01:02.000Z",
  "run_id": "R-20261104-001",
  "task_id": "T-20261104-002",
  "attempt": 1,
  "tier": "worker",
  "model_alias": "worker",
  "model_real": "deepseek-v4-flash",
  "provider": "deepseek",
  "input_tokens": 48210,
  "cached_input_tokens": 32000,
  "output_tokens": 5120,
  "reasoning_tokens": 1800,
  "cost_usd": 0.031,
  "source": "litellm",
  "latency_ms": 13900,
  "status": 200
}
```

### 12.2 归因规则

- 每个请求必须有 `run_id` + `task_id`；缺失进 `unattributed` 并告警。
- `source` 优先级：`provider > litellm > runtime > headroom`。
- `cost_usd` 用 provider 价格表计算；价格表版本写入 `env.lock`。
- 缓存 token 单独记；不要把 cached 当免费，也不要把未缓存价套到 cached。
- 重试/fallback 各记一行；不要合并成一行。

### 12.3 对账

- 每日/每周与 provider 账单对账；误差 > 5% 查。
- Headroom stats 只用于诊断：请求数、压缩率、waste signals、延迟。
- 不用 lifetime 累计值做 A/B；用“Δ值 / Δrequests”。
- 账本保留原始行；聚合结果可重算。

## 13. 锁与并发

### 13.1 锁文件

```json
{
  "path": "src/api/auth",
  "mode": "write",
  "owner_task": "T-20261104-002",
  "owner_pid": 12345,
  "lease_until": "2026-11-04T12:30:00Z"
}
```

### 13.2 规则

- 写锁按路径前缀；同一前缀只允许一个 owner。
- 读锁可共享；写锁独占。
- lease 到期可回收；回收前检查 owner 是否还活着。
- 获取锁失败 → 任务 `blocked`，不强行写。
- 合并队列本身持有全局写锁；合并期间暂停写任务。
- 锁文件不提交；进程退出时尽量清理，残留由 `loom doctor` 处理。

## 14. 版本与迁移

### 14.1 版本号

- 协议版本：`schema_version`，semver。
- 组件版本：`.agent/env.lock`。
- Prompt 版本：`prompts/<role>@<version>.md`；实际使用版本写入事件。
- 价格表版本：`pricing@YYYY-MM-DD`；写入账本。

### 14.2 兼容策略

- 读取时先校验 `schema_version`；不兼容直接拒绝，不猜。
- minor 升级保持向后兼容；major 升级提供迁移脚本。
- 迁移脚本必须可 dry-run，并保留备份。
- 旧事件/账本不重写；查询层做兼容映射。

### 14.3 升级窗口

- 关键组件（pi / codex / headroom / litellm / 插件）升级前：
  1. 记录当前版本与基线；
  2. 跑兼容性清单（见 07）；
  3. 小任务 canary；
  4. 观察 1 天 CPVT / cache hit / 错误率；
  5. 再全量。
- 升级失败回滚版本 + 配置；不要在生产 run 中途升级。

## 15. 端到端示例

目标：给现有 API 增加登录。

### 15.1 任务图

| 任务 | 角色 | tier | 依赖 | 验收 |
|---|---|---|---|---|
| T-001 冻结 auth 契约 | spec-tests | frontier | — | OpenAPI lint + 人审 |
| T-002 实现 login | implement | worker | T-001 | 单测 + tsc + lint |
| T-003 补集成测试 | spec-tests | worker | T-002 | 集成测试 + tsc |
| T-004 安全 review | review | frontier | T-003 | checklist + diff review |

### 15.2 流程

1. `loom run G-20261104-auth`：
   - 读 GOAL/spec/design；
   - 校验任务图；
   - 创建 run 目录与账本。
2. T-001 派发到 frontier：
   - 读 spec/design；
   - 写 `contracts/auth.openapi.yaml`；
   - 跑 `spectral lint`；
   - 四行回执。
3. runner 重跑 lint；通过 → merge；更新 PROGRESS。
4. T-002 派发到 worker：
   - 读 contracts + design + session 中间件；
   - 在 worktree 实现；
   - 跑 A1/A2/A3；
   - 四行回执。
5. runner 重跑 A1/A2/A3；通过 → merge。
6. T-003 类似；T-004 由 frontier review diff + checklist。
7. 最后跑集成 verify；生成 run 报告：
   - 任务数、通过率、CPVT、cache hit、升级次数、人工介入次数。

### 15.3 失败路径

- T-002 A1 失败：
  - 同层重试 1 次（带失败日志路径）；
  - 仍失败 → 证据包 → frontier judgment；
  - judgment 输出 `fix_plan` → 新 worker 任务（带 plan）；
  - 仍失败 → `human`。
- T-002 超预算：
  - 停止；保留 worktree；
  - 人决定拆任务/加预算/放弃。

## 16. 反模式清单

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 把整段对话粘给子 agent | 重复计费、目标漂移 | TaskSpec + 文件引用 |
| 子 agent 回贴完整 diff/日志 | 主上下文爆炸 | 四行回执 + report 路径 |
| 用“我完成了”当验收 | 假通过、返工 | runner 重跑 verify |
| 模型自评“这题难”就升级 | 升级滥用、成本失控 | 只在 verify 失败时升级 |
| 多个 agent 同时改同一文件 | 冲突、覆盖 | 路径锁 + 单写者 |
| 中途改 system prompt/工具 | 缓存失效 | run 内稳定前缀 |
| 用 lifetime 累计值做 A/B | 结论错误 | Δ值/Δrequests |
| 把 Headroom stats 当账单 | 成本误判 | provider/LiteLLM 为准 |
| 为了压缩率切 token 模式 | 丢缓存、成本上升 | 保持 cache |
| 任务没有 verify 就派发 | 无法验收 | 先写 spec-tests/acceptance |
| 子 agent 互相聊天对齐 | token 爆炸、不可审计 | hub-and-spoke + contracts |
| 一次派发 10 个文件的大任务 | 上下文超限、失败率高 | 1–4 小时/≤8 文件切片 |
