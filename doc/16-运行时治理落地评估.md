## 0. 结论

四个方向都能在当前架构内落地，但不该按 15 的 P0/P1 平铺推进。当前最贵的问题不是缺功能，而是三处语义错误会让后续所有度量失真：

1. `verify` 只把 `ReceiptStatus::Done` 当作完成，`needs_input`、`blocked`、`budget_exceeded` 最终都会写成 `task.failed(code=claim_not_done)`。agent 提一个问题，会被记成一次失败，并可能触发 worker→frontier 升级。见 `src/crates/loom-cli/src/verify_cmd.rs:108`、`:216`。
2. `verify` 在读取 `outbox/receipt.json` 后，用验收回执覆盖同一路径。原始 claim 丢失，之后无法回答“worker 当时是提问、阻塞还是预算耗尽”。见 `verify_cmd.rs:181`。
3. 本地 CI 配置如果放进 `.loom/`，会被整体 ignore；git worktree、队友和服务器都看不到，行为无法复现。它必须叫 `.loom.ci.toml`，放在目标项目根目录并纳入 git；`.loom/ci/` 只放运行日志和报告。

外部方案给出的最重要结论不是“抄哪个框架”，而是三条边界：

- **提问是返回值，不是暂停。** LangGraph、OpenAI Agents SDK、Temporal 都先把状态持久化，再由外部事件恢复；没有一家靠保持一个进程/聊天窗口等人。Loom 已有的“进程 + 文件 + JSON + exit code”就是正确方向，缺的是状态、事件和视图。
- **上下文优化不是删得越多越好。** Chroma 的 context rot 说明长输入会稳定退化；Anthropic 的 context editing 又说明清 tool result 会让 prompt cache 失效。投影必须有阈值，不能每一步都清。
- **skill 是干预，不是配置。** SkillsBench 的平均提升伴随很大方差；SWE-Skills-Bench 里 98 个 skill 有 92 个没有统计显著效果，少数还有害。v1 应默认 advisory、按项目启用、做配对评估，而不是“装得越多越好”。

推荐顺序：

| 顺序 | 工作 | 依赖 | 粗略人日 | 退出标准 |
|---|---|---|---:|---|
| 0 | `verify` 状态与 claim 快照修复 | 无 | 2–3 | `needs_input`/`blocked`/`budget_exceeded` 不再写 `task.failed`；重复 verify 不丢 claim |
| 1 | 最小 attention inbox + footer | 0 | 3–4 | TTY 下每条人类命令能看到待办；`--json` 不被污染；`--check` 可脚本化 |
| 2 | 本地 CI 核心 | 无（可与 1 并行） | 5–7 | `.loom.ci.toml` 可解析、可执行、可诊断；失败摘要有界 |
| 3 | question protocol | 0、1 | 3–4 | 脚本化 provider 能完成 ask → exit 2 → inbox → answer → 新 run → verify |
| 4 | CI hooks / safe fix / report | 2 | 3–4 | hooks 幂等、fail-open、不自动 stage；同 tree 证据可校验 |
| 5 | churn 步骤级投影 + write 守卫 | 0、度量 | 5–7 | 重写场景 input 有界；tool_call 配对正确；A/B 不退化 |
| 6 | skills lock + 静态检查 | 无 | 1–2 | lock 可复现；描述预算和触发边界可检查 |
| 之后 | L2 评估、服务器跳过、act/workflow 模拟、review/skill job | 真实模型/签名/服务器数据 | 后置 | 见 §11 |

如果只能做一件事：修 `verify`。如果能做两件：再加 attention。如果能做三件：再加本地 CI 核心。question protocol、churn 和 skills 都建立在这三件事提供的状态、可见性和度量之上。

| 仓库中没有 `ci` / `inbox` / `skill` 模块或命令 | `grep src/crates schemas` | 三个方向都是从零开始，不是改几行 |
| native 每步 `provider.complete(messages.clone())`，`messages` 只增不减 | `src/crates/loom-native/src/run.rs:217` | churn 的输入复利是确定事实 |
| native `write` 可直接覆盖已存在文件，没有 `mode` 或 `expected_sha256` | `src/crates/loom-native/src/tools.rs:230` | 整文件重写没有工具层约束（2026-11-09 已加 `mode` 门禁，`expected_sha256` 仍未做） |
| native `edit` 是 `old`/`new` 搜索替换，支持 `replace_all` | `tools.rs:197` | patch-first 已有半个基础；缺失败后的精确重读引导（2026-11-09 已补） |
| native `parse_finish` 接受 `needs_input`，退出码 2 | `run.rs:414` | 但不会生成 `questions.json`，提问只有状态，没有可回答内容 |
| `UsageRecord` 没有 step 维度 | `src/crates/loom-core/src/usage.rs:92` | churn 归因需要补可选字段或独立 step 日志（2026-11-09 已加可选 `step` 与归因字段） |
| event/receipt/usage schema 都是 `additionalProperties: false` | `schemas/event.v1.json:6`、`schemas/receipt.v1.json:6`、`schemas/usage-record.v1.json:8` | 任何新增字段都要同步 schema，否则校验端会拒绝 |
| 五个项目级 skill 已存在，但 Loom 没有 skill 运行时 | `.opencode/skills/*/SKILL.md` | v1 不应再造一套加载器；先做 lock 和静态检查 |

由这些事实可以推出一组硬约束：

1. **先修状态，再做视图。** 否则 inbox 会把错误状态可视化，只是让错误更显眼。
2. **先做 claim 快照，再做 question。** 否则回答后无法证明“当时问的是什么”。
3. **footer 不能每命令全量重放事件。** 需要 `.loom/inbox.json` 视图和 `size/mtime/sha256` 失效判断。
4. **CI bootstrap 不能放进 `loom-store`。** `loom-store` 不应该依赖 `loom-ci`；由 CLI 调用 `loom_ci::bootstrap`，`Project::init` 保持只建骨架。
5. **write 守卫是行为变更。** 必须同时改工具 schema、测试和错误提示，不能悄悄拒绝旧调用。
6. **新增字段优先可选。** 破坏性变更升 v2；消费端忽略未知字段。

## 2. 外部方案对照

### 2.1 可借用与不可借用

| 来源 | 关键事实 | 采纳 | 拒绝 / 边界 |
|---|---|---|---|
| [LangGraph interrupts](https://docs.langchain.com/oss/javascript/langgraph/interrupts) | interrupt 需要 checkpointer；resume 用同一 `thread_id` + `Command(resume=...)`；node 会从头重跑，interrupt 前的副作用必须幂等 | “提问是返回值”；问题 ID 稳定；回答幂等；新 run 恢复，不保持进程 | 不引入 checkpointer/thread 作为主状态。Loom 的状态是 `events.jsonl` + 文件 + exit code |
| [OpenAI Agents SDK HITL](https://openai.github.io/openai-agents-python/human_in_the_loop/) | approvals 以 `interruptions` 暴露；`RunState` 可序列化恢复；反序列化不认证快照；批准不等于 exactly-once | 显式 pending item；按 ID 回答；答案与快照分开存储；不可信本地文件不能授权 | 不把 `RunState` 当事实源；不做进程内 pause/resume |
| [Temporal HITL](https://docs.temporal.io/ai-cookbook/human-in-the-loop-python) | Signal + `wait_condition`；durable timer；等待数小时/数天不占计算资源 | 长等待是正常状态；TTL/到期由事件和视图表达；不需要常驻 daemon | 不引入 workflow engine；不做长轮询进程 |
| [Anthropic Agent Skills](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview) | L1 metadata 常驻；L2 `SKILL.md` 触发时加载，建议 <5k tokens；L3 资源按需读取 | 只广告索引；正文按需读；单 skill/总 skills 硬预算 | 不做全局安装；不把大 bundle 当默认能力 |
| [Aider edit formats](https://aider.chat/docs/more/edit-formats.html) | whole 简单但输出整文件；diff/udiff 只输出改动；不同模型适配不同格式；leaderboard 把“格式正确率”单独统计 | `edit` 为主，`write` 为回退；单独度量格式失败率；弱模型允许 whole | 不假设所有模型都能稳定输出 diff；不为了 patch 而 patch |
| [Chroma context rot](https://research.trychroma.com/context-rot) | 18 个模型随输入增长一致退化，且可能早于名义窗口；distractor 会放大问题 | 有界历史；投影旧 payload；把“窗口够大”当成反模式 | 不用“1M context”替代上下文治理 |
| [Anthropic context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing) | 清 tool result 会让 cached prefix 失效；`clear_at_least` 用来确保清得够多、值得破坏缓存 | 投影设阈值；稳定前缀不动；估算 cache invalidation 成本 | 不每一步清；不把“省下的 input”只算一半 |
| [pre-commit](https://pre-commit.com/) / [lefthook](https://lefthook.dev/) | hook 是本地便利层；pre-commit 会 stash 未暂存改动，部分暂存/冲突场景恢复复杂；lefthook 也需要处理已有 hook 与 `core.hooksPath` | 自己写薄 hook；显式安装；fail-open；不依赖 hook 做安全边界 | 不引入 hook 框架依赖；不修改全局 git config |
| [nektos/act](https://nektosact.com/usage/runners.html) / [Dagger](https://dagger.io/learn/run-github-actions-locally) | act 运行 workflow YAML，但默认 runner 镜像和 GitHub 语义不完整；Dagger 主张把步骤抽成可移植命令，workflow 只调用同一命令 | `.loom.ci.toml` 作为可移植命令源；服务器 workflow 调用同一命令 | v1 不模拟 GitHub Actions；不解析任意 workflow YAML |
| [SLSA verifying artifacts](https://slsa.dev/spec/v1.2/verifying-artifacts) | 未签名 provenance 不能作为信任根；L2 需要签名，L3 需要受信构建平台 | v1 只生成证据；`verify-attest` 只校验一致性 | 不用本地 attestation 授权服务器跳过 CI |
| [OpenAI apply_patch](https://developers.openai.com/api/docs/guides/tools-apply-patch) | V4A 结构化 patch，适合多文件/机械修改；由应用端应用 | 作为 `edit` 之后的候选；先度量格式失败率 | v1 不默认引入；不让模型直接执行任意 patch shell |
| [SkillsBench](https://arxiv.org/abs/2602.12670) | 87 任务、18 个配置；curated skills 平均 33.9%→50.5%（+16.6pp），但配置间增益 +4.1 到 +25.7pp；聚焦 ≤3 模块优于大 bundle | 小、聚焦、可关闭的 skill；配对评估 | 不预置大而全的 skill 包 |
| [SWE-Skills-Bench](https://arxiv.org/abs/2603.15401) | 98 个 skill、3920 次配对评估；92/98 无统计显著效果；平均 76.6%→76.9%；少数有害 skill 会覆盖任务显式指令（最多 -17.0pp） | 默认 advisory/opt-in；配对评估；有害 skill 可立即停用 | 不把“装了 skill”当成能力提升；不让 skill 覆盖 TaskSpec |

### 2.2 三条外部教训

**第一，长期等待是状态问题，不是进程问题。** LangGraph 用 checkpointer，OpenAI 用 `RunState`，Temporal 用事件历史和 durable timer，三者都没有让 agent 进程保持交互。Loom 的 `exit 2 + questions.json` 方向是对的，缺的是把“谁在等、等什么、谁答了、下一步是什么”写进事件和视图。回答必须幂等：同一个 `question_id` 重复提交相同答案不应产生两次状态迁移。

**第二，上下文治理要算缓存账。** Chroma 说明长上下文本身会让模型退化；Anthropic 又说明清 tool result 会破坏 prefix cache。两条合起来，正确策略不是“每步重编译”，而是“超过阈值才投影，且一次至少清够值得破坏缓存的量”。这直接决定了 §8 的 `min_clear_tokens` 和“稳定前缀不动”。

**第三，skill 需要配对评估，不是静态审查。** SkillsBench 的平均增益掩盖了很大方差；SWE-Skills-Bench 说明大多数 skill 没有显著效果，少数还有害。v1 可以做 lock、静态检查和触发边界，但不能宣称“skill 提升能力”；L2 评估必须等真实模型、固定任务集和账单。

## 3. 总取舍与度量

### 3.1 做什么，不做什么

| 方向 | v1 做 | v1 不做 | 停止条件 |
|---|---|---|---|
| 状态/回执 | claim 快照；`needs_input` 状态；状态映射；schema 漂移测试 | 不改 adapter 输出路径；不重命名 `receipt.json` | 如果状态映射仍会产生 `task.failed`，不进入 attention |
| attention | 事件 + `.loom/inbox.json` 视图 + TTY footer + `--line`/`--check` | 不做 TUI、桌面端、常驻 daemon、聊天/工单线程 | 如果一周内没有 blocking 事项，不投入更多 UI |
| question | `ask` 工具、`questions.json`、`.loom/answers/`、`loom answer`、packet 注入 | 不做交互等待；v1 不做自动 LLM 回答 | 如果回答后首过率没有改善，不扩大自动回答范围 |
| 本地 CI | `loom-ci` crate、`.loom.ci.toml`、plan/run/doctor、日志预算、report | 不做服务器跳过、act 模拟、嵌套容器、review/skill job | 如果本地 CI 不能减少服务器重跑或缩短反馈，不做 hooks/review |
| churn | step 维度、阈值投影、write 守卫、churn 统计 | 不做每步清缓存、不做硬拦、不做软重启、不默认引入 apply_patch | 如果 A/B 首过率下降超过 2pp，关闭投影 |
| skills | 现有项目级试点、`skills.lock`、静态检查、描述预算 | 不做第二套运行时、不做全局安装、不做 L2 晋升 | 如果配对评估无显著收益，降级为显式调用 |

### 3.2 度量口径

优化目标是**每个成功任务的总成本**，不是“本地跑了多少次检查”或“重写次数”。

| 指标 | 定义 | 用途 |
|---|---|---|
| `CPVT` | 总成本 / 通过任务数 | 主成本指标；必须和首过率一起看 |
| `TPVT` | 总 token / 通过任务数 | 没有账单时的近似；标 `estimated` |
| `WPT` | 墙钟 / 任务，至少 P50/P95 | 反馈速度；本地 CI 的主要收益 |
| `first_pass_rate` | 首次 verify 通过比例 | 质量护栏 |
| `blocked_age` | attention 事项从 open 到 resolved 的时间 | 可见性是否真的减少等待 |
| `time_to_first_ack` | 人第一次看到/确认的时间 | footer 是否有用 |
| `server_reruns_avoided` | 本地拦截后未在服务器重跑的 job 次数/分钟 | 本地 CI 的收益；v1 只能估算 |
| `wasted_tokens_est` | 重写输出 + 历史携带 + 重试，估算 | churn 主指标；标 `estimated` |
| `cache_hit_ratio` | `cached_input_tokens / input_tokens` | 投影是否破坏缓存 |
| `skill_delta` | 同任务集 paired 的 pass rate / CPVT 差值 | 决定 skill 是否保留 |

反模式：用 `write_passes`、`churn_ratio`、job 数量、skill 数量当主 KPI。它们只能解释原因，不能证明收益。

## 4. A. 状态与回执正确性（先修）

### 4.1 当前链路

```text
adapter 退出 2 / final.md 声明 needs_input
  -> normalize 生成 ReceiptStatus::NeedsInput
  -> dispatch 写 task.receipt（状态 receipt）
  -> verify 读取 claim，claim_done=false
  -> 仍跑 acceptance；无论结果如何，写 task.failed(code=claim_not_done)
  -> route 的 history 把这次 task.failed 计入升级阈值
  -> 用户只能在对话历史/日志里看到这次提问
```

三个独立缺陷：状态错误、证据丢失、可见性缺失。第一个和第二个必须在 attention 之前修。

### 4.2 claim 快照

adapter 契约保持不变：仍然写 `outbox/receipt.json`。`verify` 在覆盖前做快照：

1. 读取 `outbox/receipt.json`。
2. 如果 `.loom/runs/<id>/logs/claim.json` 不存在，把原始回执字节复制过去；存在则从 `logs/claim.json` 读取 claim。
3. 校验 claim；解析失败按 `claim_invalid` 处理，不猜。
4. 默认只对 `Done` 跑 acceptance；`NeedsInput`/`Blocked`/`BudgetExceeded` 跳过，`--run-verify` 可强制跑，但仍不得标记 `passed`。
5. 写最终 `outbox/receipt.json`，增加可选字段 `claim_status`，并在 `task.verify` 事件里记录同一个值。
6. 重复 verify 从 `logs/claim.json` 取原始 claim，不把上一次 verify 回执当成 claim。

不建议把 verify 回执改到 `verify.json` 再保留原 `receipt.json`：会改变 dispatch/status/canary 对 `receipt.json` 的假设，迁移成本高于收益。

### 4.3 状态映射

| claim 状态 | acceptance | 写事件 | 任务状态 | 退出码 |
|---|---|---|---|---|
| `Done` | 全过 | `task.verify` + `task.passed` | `passed` | 0 |
| `Done` | 有失败 | `task.verify` + `task.failed(code=verify_fail)` | `failed` | 1 |
| `NeedsInput` | 默认不跑 | `task.needs_input` + `attention.opened` | `needs_input` | 2 |
| `Blocked` | 默认不跑 | `task.blocked(code=blocked)` + `attention.opened` | `blocked` | 2 |
| `BudgetExceeded` | 不跑 | `budget.exceeded` + `task.blocked(code=budget_exceeded)` + `attention.opened` | `blocked` | 3 |
| `Failed` | 不跑 | `task.failed(code=claim_failed)` | `failed` | 1 |
| 无 claim / 解析失败 | 不跑 | `task.failed(code=claim_missing/claim_invalid)` | `failed` | 1 |

说明：

- `needs_input` 不是失败，不计入升级历史；`route` 只看 `task.failed`，所以不会误升级。
- `blocked` 不是失败，也不计入升级；它表示依赖、环境或预算阻塞。用 `data.code` 区分原因。
- `budget_exceeded` 写 `budget.exceeded` 事件，任务状态用 `blocked`，不写 `task.failed`。如果后续统计需要单独状态，再升 `TaskStatus`，不要在 v1 混用。
- `verify` 回执的 `status` 反映最终状态，不再永远只写 `Done`/`Failed`。
- 退出码 `0/1/2/3` 是 `loom verify` 的新增语义；`main` 仍把内部错误映射为 4。它不是全局 CLI 约定，不能和另外两套混用：

| 命令族 | 0 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|---|
| `loom verify`（本方案） | 通过 | 验收或 claim 失败 | `needs_input` / `blocked` | 预算/超时 | 内部错误 |
| `loom tool`（[10](10-工具输出协议-v0.1.md) §5） | 成功 | — | 参数错误 | 超时/预算 | 内部错误 |
| adapter（[08](08-设计路线-v0.2.md) §7.1） | 成功 | — | 需人工 | 预算/超时 | adapter 故障 |

需要在 `loom verify --help`、CLI 文档和测试里同时写明，避免调用方把 `needs_input` 当成参数错误。

### 4.4 `TaskStatus::NeedsInput`

建议语义：

- `satisfies_dependency() == false`；
- `is_terminal() == false`；
- `is_open() == true`，这样 `loom status`/`loom resume` 能看到“还在等回答”的任务；
- `dispatch` gate 不放行 `needs_input`；只有 `loom answer` 把全部 blocking 问题回答后写 `task.ready`，才回到可派发状态；
- `resume --dispatch` 只派发 `ready`，不会把 `needs_input` 自动跑掉；pretty 输出提示“有问题待回答”。

同时把 `Blocked` 加进 `is_open()`。当前 `Blocked` 既不是 open 也不是 terminal，`resume` 看不到它；这是一个已有的显示缺口，和 `needs_input` 一起修。

### 4.5 事件与 schema

新增：

- `task.needs_input`：`data.question_ids`、`data.blocking`、`data.scopes`；
- `task.answered`：见 §6；
- `attention.opened` / `attention.updated` / `attention.resolved` / `attention.expired`：见 §5。

同步位置：

1. `EventType` 的枚举、`as_str`、`FromStr`；
2. `Event::validate` 的 `needs_task`；
3. `schemas/event.v1.json` 的 `enum`；
4. `doc/03` §11.2 的事件表；
5. 至少一个事件重放测试。

新增一个 schema 漂移测试：读取 `schemas/event.v1.json` 的 `enum`，与 `EventType::all()` 的字符串集合比较。当前没有这层保护，新增事件很容易只改 Rust 类型。

### 4.6 离线测试

不需要真实模型：

- `NeedsInput` claim 经 verify 后状态是 `needs_input`，没有 `task.failed`；
- `Blocked`/`BudgetExceeded` 不再写 `claim_not_done`；
- 重复 verify 从 `logs/claim.json` 取 claim，原始字节不变；
- `route history` 对 `needs_input` 不增加失败计数；
- 事件 schema 漂移测试失败时能指出缺哪个事件；
- `--run-verify` 跑 acceptance 但不把 `needs_input` 标成 `passed`。

### 4.7 风险

| 风险 | 缓解 |
|---|---|
| 旧 adapter 不写 `questions.json` | 仍然进入 `needs_input`，同时开 `operation` 事项，不猜问题 |
| 退出码变化影响脚本 | 先只在 `verify` 增加 2/3，文档和测试同步；其他命令保持 |
| claim 快照被手工改 | `logs/claim.json` 只是证据，事实源仍是事件；`verify-attest` 不把它当信任根 |
| `Blocked` 加入 `is_open` 改变 resume 展示 | 只影响展示，不改变派发；加测试固定行为 |

## 5. B. Attention inbox

### 5.1 事件是事实源，视图是缓存

`attention.*` 事件写进 `events.jsonl`；`.loom/inbox.json` 只读、可重建，不手改。

| 事件 | 必需 data | 效果 |
|---|---|---|
| `attention.opened` | `item_id`、`kind`、`source`、`severity`、`dedupe_key`、`title` | 新建事项；同 `dedupe_key` 未关闭时只累加 `occurrences` |
| `attention.updated` | `item_id`、`changes` | 更新 `severity`/`detail`/`defer_until`/`occurrences`，不改变身份 |
| `attention.resolved` | `item_id`、`by`、`reason` | 关闭事项 |
| `attention.expired` | `item_id`、`policy`、`reason` | 只允许可逆/提醒类过期；blocking 不允许静默过期 |

`attention.*` 不要求 `task_id`：缺工具、缺 key、CI 首次接入都是项目级事项。不要把它们加进 `Event::validate` 的 `needs_task`。

### 5.2 事项模型

| 字段 | 约束 |
|---|---|
| `id` | `A-` + `sha256(kind + "\0" + dedupe_key)` 前 8 位；确定性，重放稳定 |
| `kind` | `question` / `approval` / `operation` / `review` / `reminder` |
| `severity` | `blocking` / `soon` / `info` |
| `status` | `open` / `acked` / `deferred` / `resolved` / `expired` |
| `title` | ≤120 字符，禁止控制字符和 ANSI |
| `summary` | ≤2KB；长文落 `.loom/attention/<id>.md`，事件只存路径/哈希 |
| `source` | `task` / `ci` / `env` / `git` / `human` / `agent` |
| `task_id` / `run_id` | 可空 |
| `dedupe_key` | 未关闭事项内唯一；例如 `task:T-001:question:Q1`、`env:missing-tool:goose`、`ci:clippy:<tree>` |
| `actions` | 最多 8 条，只做文本建议，永不自动执行、不做 shell 求值 |
| `created_at_ms` / `updated_at_ms` / `expires_at_ms` | 生命周期 |
| `resolved_by` / `resolved_reason` | 审计 |

原则：

- `acked` 只表示“已看到”，不关闭事项、不降低 `blocking` 计数；
- `defer` 只允许 `soon`/`info`，不能把 `blocking` 藏起来；
- 自动 resolve 只用于确定性条件：工具已安装、同 tree CI 已通过、问题已回答；
- 事项文本来自 agent/仓库，视为不可信输入：截断、转义、`refs` 不跟随 symlink 到仓库外。

### 5.3 视图与缓存

`read_events` 是全量读取，footer 每条命令都跑一次会放大开销。视图缓存规则：

1. `.loom/inbox.json` 保存 `events_size`、`events_mtime_ms`、`events_sha256`、`generated_at_ms`、`items`、`counts`。
2. 读取时先 `stat`；size/mtime/sha256 未变则直接用视图。
3. 变了则全量重放，原子写回（temp + rename）。
4. 事件被截断/手工修改时 size 可能变小；必须全量重放，不能增量追加。
5. 视图写失败不影响命令；footer 静默跳过。
6. `loom inbox --json` / `--check` 可强制重放，避免脏缓存影响决策。

### 5.4 固定角落

v1 只做两个出口：TTY footer 和 `loom inbox --line`。不绑定某个 UI，后续 TUI/桌面端复用同一视图。

| 出口 | 内容 | 约束 |
|---|---|---|
| 每条人类命令的 footer | `attention: 2 blocking, 1 soon | loom inbox --line | A-7f3: ...` | 只写 stderr；仅 TTY；非 `--json`；非 `loom inbox` 自身；失败吞掉 |
| `loom inbox --line` | 单行，供 statusline/tmux/starship 轮询 | 只读、无副作用、开销固定 |
| `loom inbox --check` | 有 `blocking` 时退出 2 | 给脚本/hook 用，不打印大段内容 |
| `loom inbox list/show/ack/defer/resolve` | 完整列表与操作 | `ack` 不关闭；`defer` 只作用于 soon/info |

配置：

```toml
[attention]
footer = "tty"              # tty | always | off
include_in_packet = "off"   # off | counts
dedupe_cooldown_s = 600
retain_resolved_days = 7
```

footer 规则：

- 没有待办时不打印，避免噪声；
- 单行 ≤160 字符，取最高优先级事项标题并截断；
- 禁止 ANSI 注入；只写 stderr；不改变退出码；
- `LOOM_NO_INBOX=1` 或 `--no-inbox` 关闭；
- 默认不把 inbox 注入模型上下文。需要时只注入计数，受硬预算约束。

### 5.5 第一批来源

| 来源 | kind | 触发 |
|---|---|---|
| `verify` | `question` | claim `NeedsInput` 且有 blocking 问题 |
| `verify` | `operation` | claim `Blocked`，例如缺工具/缺 key |
| `doctor` | `operation` | 缺 podman/docker/cargo/goose/opencode 等 |
| `ci` | `review` / `operation` | job 失败；首次接入需要人确认 |
| `route` | `approval` | 成本护栏拒绝或需要升级确认 |
| `human` | `reminder` | `loom inbox add` 后置 |

即使没有 agent 提问，用户也能在 footer 看到“需要装工具/需要确认 CI”这类操作事项。这是 attention 独立于 question 的价值。

### 5.6 风险

| 风险 | 缓解 |
|---|---|
| footer 性能 | 视图缓存 + size/mtime/sha256；失败静默 |
| 事项刷屏 | `dedupe_key` + cooldown + `occurrences`，不重复开 |
| `acked` 被当成完成 | 文档和测试固定：ack 不降 blocking 计数 |
| 用户不看 footer | `--check` 给脚本；后续 TUI/桌面端后置 |
| 自动 resolve 误判 | 只自动关确定性条件；需要判断的显式 resolve |

## 6. C. Question protocol

### 6.1 契约

adapter 需要输入时：

- 写 `outbox/questions.json`；
- `final.md` 状态行写 `needs_input`；
- 退出码 2；
- 进程以 `stdin = /dev/null` 启动，交互式询问立即 EOF，不挂起。

native 增加 `ask` 工具，或允许 `finish(status="needs_input", questions=[...])`。建议用 `ask`：一个工具调用可以带多个问题，且不需要把数组塞进 `finish`。`ask` 写 `outbox/questions.json`，设置 `Finish { status: "needs_input" }`，退出码 2。若 `finish` 声明 `needs_input` 但没有 `questions.json`，不猜问题，开 `operation` 事项提示协议。

### 6.2 `questions.json` v1

```json
{
  "v": 1,
  "task_id": "T-20261107-001",
  "run_id": "R-20261107-001",
  "questions": [
    {
      "id": "Q1",
      "text": "迁移脚本是否需要兼容旧版 schema？",
      "kind": "choice",
      "options": [
        {"id": "A", "label": "兼容旧版，双写一个版本", "consequence": "多 1 次迁移，回滚安全"},
        {"id": "B", "label": "只支持新版", "consequence": "改动小，旧客户端会失败"}
      ],
      "blocking": true,
      "scope": "design",
      "recommended": "A",
      "default": "A",
      "reversible": false,
      "evidence": ["src/db/migrate.rs:40-90", "artifact:read-3"],
      "ttl_s": 86400
    }
  ]
}
```

约束：

- 最多 5 个问题，其中最多 3 个 blocking；超过则合并或拆任务；
- `text` ≤1KB；`options` ≤8；`evidence` ≤8 条，只放路径/artifact 引用；
- `id` 在 task 内唯一，建议 `Q1`、`Q2`；
- `kind`：`choice` / `text` / `confirm`；
- `scope`：`implementation` / `design` / `contract` / `security` / `budget` / `scope`；
- `ttl_s` 最大 30 天；`blocking` 不允许自动过期，到期转为 attention `review`；
- 不接受任意 shell 命令或 URL 作为 action。

### 6.3 回答存储

回答写 `.loom/answers/<task_id>.jsonl`，追加式，不写旧 run 的 outbox：

```json
{"v":1,"question_id":"Q1","answer":"A","source":"human","by":"local-user","rationale":"保留回滚能力","answered_at_ms":0,"answer_sha256":"..."}
```

规则：

- `source`：`human` / `policy` / `judgment` / `spec`；v1 只开放 `human` 和显式 `--assume`；
- 同一 `question_id` 重复提交相同 `answer_sha256` 是幂等，不重复写状态；
- 不同答案默认拒绝，`--replace` 才追加一条带 `supersedes` 的记录；事件保留全部历史；
- 回答内容不放进旧 run 的 outbox，避免事后改历史。

### 6.4 状态机

```text
receipt -> needs_input
            |
            +-- 所有 blocking 问题都有答案 -> task.ready -> dispatch 新 run
            |
            +-- 只答了部分 -> 保持 needs_input
```

- `task.answered` 本身不直接改状态，否则多问题场景会提前放行；
- 每次回答写 `task.answered`，并 resolve 对应 `question` 事项；
- 当所有 blocking 问题都有答案时，命令追加 `task.ready`；
- 非 blocking 问题可带默认值继续，同时写 `assumptions.jsonl`。

### 6.5 attempt 语义

回答后开新 run，**递增 `attempt`**，因为这是一次新的执行；但在 `TaskDispatched.data` 和 run meta 里记录 `question_round` 与 `reason=answer`。升级计数只看 `task.failed`，不看 `attempt`，所以“提问不是失败”仍然成立。15 §2.6 的“attempt 不变”需要按这个定义修正，避免同一个 attempt 对应多个 run。

### 6.6 packet 注入

下一次 dispatch 的 Context Compiler 读取最新问题和答案，作为独立小节注入：

- 只注入 blocking 问题的 Q/A 摘要和未回答问题；
- 已答问题保留一行 `Q1=A` 和理由，不重发完整选项；
- 总预算 ≤4KB；超限先裁非 blocking 和旧问题，不裁 AC/constraints；
- 不注入 attention inbox 全文；需要时只注入计数。

### 6.7 授权矩阵

| scope | v1 谁能答 | 说明 |
|---|---|---|
| `implementation`，可逆 | 人；可显式 `--assume` | assumption 记录，低置信开 review 事项 |
| `design`，可逆 | 人；judgment 后置 | v1 不做自动 LLM 回答 |
| `contract` / AC 语义 | 人 | 改 AC/目标必须人确认 |
| `security` / 数据删除 / 不可逆迁移 | 人 | 不允许 assumption 绕过 |
| `budget` / 跨 tier / 扩大范围 | 人 | 走 approval 事项 |

v1 明确不调用 LLM 自动回答问题。确定性策略只能处理“缺工具/缺 key”这类 operation，不处理语义问题。

### 6.8 离线测试

- 脚本化 provider 调用 `ask` → `questions.json` → exit 2 → `loom inbox` 可见；
- `loom answer` 后新 run 收到答案，verify 通过；
- 多 blocking 问题只答 1 个时仍为 `needs_input`；
- 重复提交相同答案幂等；冲突答案默认拒绝；
- 无 `questions.json` 时不猜问题，开 operation 事项；
- 回答不进入失败计数，`attempt` 递增但 `task.failed` 不增加。

## 7. D. 本地 CI

### 7.1 作用对象与权威

本地 CI 的对象是 **Loom 管理的目标项目**，不是 Loom 自身。Loom 仓库用同一套机制属于 dogfood，`./scripts/dev.sh` 只是 Loom 的 runner 示例，不能写死成产品默认。

| 层次 | 负责什么 | 权威性 |
|---|---|---|
| TaskSpec acceptance | 这个任务是否完成约定目标 | `loom verify`，任务级权威 |
| 仓库本地 CI | 这个仓库当前是否健康、能否提交/推送 | `loom ci run`，本地闸门与反馈 |
| 服务器 CI | 跨平台、集成、发布、安全与合规 | 服务器，最终权威 |

v1 不根据本地 attestation 跳过服务器 job。本地 CI 的收益是减少重复失败、缩短反馈、给 agent 一个统一入口，不是替代服务器。

### 7.2 配置位置

- `.loom.ci.toml`：目标项目根目录，**tracked**，团队共享，worktree 继承，PR 可审查；
- `.loom/ci/`：运行时日志、report、attestation，**ignored**；
- `.loom/config.toml`：`[ci]` 全局偏好（默认 profile、hook 策略），运行时配置。

为什么必须 tracked：

| 需求 | 不 tracked 会怎样 |
|---|---|
| 团队共享同一套检查 | 每人各自一套，PR 无法审查检查变更 |
| git worktree 继承 | worker worktree 里没有配置，`loom ci` 行为不一致 |
| 服务器/attestation 引用 | 配置哈希无法复现，报告无法对应同一 tree |
| agent 修改检查 | diff 不可见，容易成为隐藏后门 |

个人覆盖 `.loom/ci.local.toml` 后置，且只能加个人 profile/超时，不能关闭团队 gate。

### 7.3 锁定的 schema

15 §4.5 仍用 `[jobs.<id>] + cmd` 的示例，与本文锁定的 `[[jobs]] + argv` 不同。实现形态以本文为准：`[[jobs]]` + `argv` + `[runner]`；15 的示例只作字段语义参考。不要同时支持两套。

```toml
version = 1

# 目标项目可留空；Loom dogfood 用容器脚本，避免宿主 cargo。
[runner]
argv = ["./scripts/dev.sh"]

[profiles]
pre-commit = ["fmt-fix", "skills-check"]
pre-push = ["fmt-check", "clippy", "test"]
fast = ["fmt-check", "clippy"]
full = ["fmt-check", "clippy", "test", "build"]

[[jobs]]
id = "fmt-check"
argv = ["cargo", "fmt", "--all", "--", "--check"]
timeout_s = 120
local_sufficient = true

[[jobs]]
id = "fmt-fix"
argv = ["cargo", "fmt", "--all", "--", "--check"]
fix_argv = ["cargo", "fmt", "--all"]
fix_safe = true
timeout_s = 120

[[jobs]]
id = "clippy"
argv = ["cargo", "clippy", "--workspace", "--all-targets", "--", "-D", "warnings"]
timeout_s = 600
local_sufficient = true

[[jobs]]
id = "test"
argv = ["cargo", "test", "--workspace"]
needs = ["clippy"]
timeout_s = 900
local_sufficient = true

[[jobs]]
id = "skills-check"
argv = ["./scripts/check-skills.sh"]
timeout_s = 30
```

字段：

| 字段 | 必填 | 语义 |
|---|---|---|
| `version` | 是 | 只能为 1 |
| `runner.argv` | 否 | argv 前缀；最终命令 = `runner.argv + job.argv` |
| `profiles.<name>` | 是 | job id 数组；顺序执行 |
| `jobs[].id` | 是 | 唯一、非空 |
| `jobs[].argv` | 是 | 非空数组，不经 `sh -c` |
| `jobs[].timeout_s` | 是 | 1–3600；超时杀进程组 |
| `jobs[].cwd` | 否 | 相对仓库根，不得逃逸 |
| `jobs[].needs` | 否 | job 依赖；v1 只用于顺序约束，不做并行 |
| `jobs[].fix_argv` | 否 | `--fix` 时执行；之后重跑 `argv` 验证 |
| `jobs[].fix_safe` | 否 | 只有显式 true 才允许 `--fix`；必须同时有 `fix_argv` |
| `jobs[].required_tools` | 否 | 无 runner 时检查 `argv[0]`；有 runner 时只检查 runner |
| `jobs[].env_pass` | 否 | 从宿主透传的变量名 allowlist；只存名字，不存值；默认拒绝 `*_API_KEY`/`*_TOKEN`/`*_SECRET` |
| `jobs[].local_sufficient` | 否 | 仅作证据标记；v1 不授权服务器跳过 |

v1 不提供 `kind`、自由 `env` 键值对和 `network` 字段。review/skill job 后置；环境变量只允许默认 allowlist 加 `env_pass` 名称列表，不存值，避免把 token 写进仓库；网络隔离 v1 不声称支持，需要联网的 job 由人决定。

校验规则：

- `version == 1`；
- job id 唯一、非空；
- `argv` 非空，`argv[0]` 非空；
- `cwd` 不逃逸仓库根；
- `timeout_s` 在 1–3600；
- profile 引用的 job 必须存在；
- `needs` 引用的 job 必须存在，且无环；
- `fix_safe` 必须有 `fix_argv`；
- `env_pass` 只能是 `^[A-Za-z_][A-Za-z0-9_]*$`，且不得匹配 `*_API_KEY`/`*_TOKEN`/`*_SECRET`/`*_PASSWORD`；
- `local_sufficient` 只对确定性命令为 true；
- 未知字段直接报错（`deny_unknown_fields`）；
- 文件大小上限 256KB。

### 7.4 执行语义

- 最终 argv = `runner.argv + job.argv`；不经过 shell，避免引号和注入；
- `cwd` 默认仓库根；所有路径解析后必须仍在根内；
- `stdin = null`；
- stdout/stderr 流式写 `.loom/ci/<run>/<job>.log`，内存只保留头尾摘要；
- 超时用 `process_group(0)` + 先 `SIGTERM` 后 `SIGKILL`，避免 `podman run` 子进程残留；
- 环境默认只传 `PATH`、`HOME`、`LANG`、`TERM`、`CARGO_HOME`、`RUSTUP_HOME` 等 allowlist，剔除 `*_API_KEY`、`*_TOKEN`、`*_SECRET`；`env_pass` 只列名字，不存值；
- 设置 `NO_COLOR=1`、`TERM=dumb`、`LOOM_CI=1`；落盘前剥离 ANSI；
- 记录 argv、cwd、退出码、signal、耗时、日志 hash；`--version` 可选，失败不阻塞；
- 默认第一个失败即停；`--keep-going` 跑完；
- v1 顺序执行，不做并行和 affected-only。

### 7.5 命令与退出码

```text
loom ci plan [--profile <name>] [--json]
loom ci run  [--profile <name>] [--keep-going] [--fix] [--json]
loom ci doctor [--json]
loom ci report [--run <id>] [--json]
loom ci verify-attest <path> [--json]
loom ci install-hooks --profiles pre-commit,pre-push
loom ci remove-hooks
```

退出码：

- `0`：所有 job 通过；
- `1`：有 job 失败；
- `2`：需要人处理（缺工具、缺 runner、需要确认），不是代码失败；
- `3`：超时/预算；
- `4`：配置/执行错误。

`--json` 的 stdout 只有 JSON；进度和摘要走 stderr 或字段。

`--fix` 只执行 `fix_safe = true` 的 job：先跑 `fix_argv`，再重跑 `argv` 验证；展示 `git diff --stat` 和 patch 路径；**不 stage、不 commit**；有改动时提示重新 `git add`。

### 7.6 `loom init` 探测

v1 只做单栈、根目录探测，避免过早处理 monorepo：

| 证据 | 生成 |
|---|---|
| 根 `Cargo.toml` 或 `src/Cargo.toml`（workspace） | `cargo fmt/clippy/test` |
| `scripts/dev.sh` | `runner.argv = ["./scripts/dev.sh"]` |
| `Makefile` 有 `check`/`test`/`fmt` | 采纳已有 target，不重复发明 |
| `package.json` / `pyproject.toml` / `go.mod` | 后置，不猜 |

生成策略：

- `--dry-run` 打印将写入的内容，不落盘；
- 已有 `.loom.ci.toml` 默认保留并提示；
- `--force` 覆盖前备份 `.loom.ci.toml.bak.<ts>`；
- 没有足够证据时只打印建议，不写配置；
- 不自动生成 workflow，不改 `.github/`；
- `Project::init` 继续只建 `.loom` 骨架；CLI 调用 `loom_ci::bootstrap`，避免 `loom-store -> loom-ci` 反向依赖。

### 7.7 hooks

- 只由 `loom ci install-hooks` 显式安装，不静默改 `.git/hooks` 或全局 `core.hooksPath`；
- 写入带 `# loom-managed` 标记的 `pre-commit` / `pre-push`；
- 已存在非 Loom hook：默认拒绝；`--force` 先备份为 `<hook>.bak.<timestamp>`；
- hook 只调用 `loom ci run --profile ... --from-hook`，不内联业务命令；
- pre-commit 目标 ≤30 秒，pre-push 目标 ≤5 分钟；长任务留给服务器；
- `loom` 不存在、config 非法、runner 缺失时 fail-open + 警告，避免新克隆无法提交；
- `LOOM_CI_SKIP=1` 显式跳过，只写本地诊断，不作为证据；
- `hooks_fix_safe` 默认 **false**；开启后先跑 safe fix 再重跑检查，有改动时退出 1 并提示重新 `git add`，不自动 stage/commit；
- **`--no-verify` 无法被 hook 观测**，不承诺记录 bypass；只记录 hook 实际运行/跳过原因；
- 不修改全局 git config。

### 7.8 report 与 attestation

`report.json`：

```json
{
  "v": 1,
  "run_id": "CI-...",
  "profile": "pre-push",
  "ci_toml_sha256": "...",
  "tree": {
    "head": "abc123",
    "dirty_sha256": "...",
    "untracked_sha256": "...",
    "dirty": true
  },
  "started_at_ms": 0,
  "duration_ms": 0,
  "jobs": [
    {
      "id": "fmt",
      "argv": [],
      "cwd": ".",
      "exit": 0,
      "signal": null,
      "timed_out": false,
      "duration_ms": 0,
      "log_path": "...",
      "log_sha256": "..."
    }
  ],
  "ok": true,
  "local_sufficient": true,
  "advisory": false
}
```

tree 计算：`HEAD` + `git diff --binary` 的哈希 + 未跟踪文件按路径排序后的路径/大小/内容哈希。不要为了 attestation 执行 `git write-tree`，会碰 index。同一 tree 的校验必须包含未跟踪文件，否则“本地跑过”可能漏掉新文件。

`attestation.json` 是 report 的摘要 + 可校验字段：

- v1 不签名，`signature = "none"`；
- `loom ci verify-attest` 只能证明“这份文件和这个 tree 对得上”；
- 服务器跳过需要 HMAC/受信 runner/受保护分支，后置；
- 在完成前，服务器 CI 继续跑安全/发布/矩阵。

### 7.9 与 attention 的衔接

- CI 失败开 `review` 事项，`dedupe_key = ci:<job>:<tree>`；
- 缺工具/runner 开 `operation`；
- 同一 tree 成功后自动 resolve 对应 `review`；
- `loom inbox --check` 可在提交前提示未处理失败；
- report 里的 job 结果不作为 TaskSpec acceptance；`verify` 仍是任务权威。

### 7.10 离线测试

临时目录 + 假命令即可覆盖：

- 解析/校验：良好配置、重复 id、缺失 job、逃逸 cwd、非法 timeout、`fix_safe` 无 `fix_argv`、未知字段；
- 执行：临时 `sh -c 'exit 1'`，检查退出码、日志、摘要；
- 超时：`sleep` 子进程被杀，进程组无残留；
- `--fix`：假的 fix 命令改文件，检查不 stage、diff 可见；
- hooks：临时 git 仓库，幂等、非 Loom hook 拒绝、备份、fail-open；
- report/attestation：同 tree 通过、不同 tree 失败、脏文件/未跟踪文件改变哈希；
- `--json` stdout 纯 JSON；
- init 探测：临时 Rust workspace + `scripts/dev.sh`，生成预期配置；已有配置不覆盖。

### 7.11 风险

| 风险 | 缓解 |
|---|---|
| 配置不进仓库 | 根目录 `.loom.ci.toml`，tracked |
| 假阳性“本地过了” | tree 含未跟踪；doctor 检查环境；服务器仍跑最终门禁 |
| attestation 被伪造 | 只做证据；不授权跳过 |
| hooks 阻塞新克隆 | fail-open + 警告 |
| 超时残留 | 进程组 kill；日志流式 |
| 命令漂移 | 采纳已有 Makefile target；doctor 提示 |
| 生成配置过度自信 | v1 只做单栈根目录，没证据不写 |
| `--no-verify` | 无法观测；不承诺记录，服务器兜底 |

## 8. E. Churn

> `max_history_bytes` / `keep_recent_turns` / `min_clear_tokens`，env 名
> `LOOM_NATIVE_HISTORY_BYTES` / `LOOM_NATIVE_KEEP_TURNS` / `LOOM_NATIVE_MIN_CLEAR`，
> 0 关闭），见 `doc/15` §1 实现状态与 `scripts/smoke-churn.sh`。

> `loom churn stats [--by model]` 均已接线；真实 A/B 数字见本节末尾。

### 8.1 token 账

churn 的浪费不在磁盘，而在请求历史：

| 费用 | 来源 | 治理 |
|---|---|---|
| 输出 token | 模型重新生成整个文件，放进 `tool_calls.arguments` | patch-first、write 守卫 |
| 输入复利 | 旧全文留在 `messages`，后续每一步重发 | 阈值投影 |
| 缓存失效 | 投影/清 tool result 破坏 prefix cache | 稳定前缀、`clear_at_least` |
| 重试 | acceptance 回灌、整 run 重开 | 失败包、止损 |

一个示意：8KB 文件约 2k tokens；同一文件重写 5 次，后续还剩 20、16、12、8、4 步，旧版本被重发的 input 约 `2k × (20+16+12+8+4) ≈ 120k` tokens。这个数字不是实测，只用于说明为什么“阻止第 N 次写入”只省一次输出，而“旧版本不再进入后续请求”才是主杠杆。

### 8.2 阈值投影

在每次 `provider.complete` 前做确定性投影，但只在必要时：

1. **稳定前缀不动**：system + packet 保持字节级稳定，保护 prefix cache。
2. **触发条件**：动态尾部超过 `max_history_bytes`（默认 24KB）或估算 input 超过上限，且预计能清掉至少 `min_clear_tokens`（默认 2000）。清得不够多就不清，避免为了省一点 input 破坏缓存。
3. **保留最近 K 个完整 turn**（默认 4–6），包括 assistant tool_calls 和对应 tool results。
4. **旧 assistant tool_calls 投影**：
   - `write(content=...)` → `{path, bytes, sha256, mode}`；
   - `edit(old,new)` → `{path, old_bytes, new_bytes, old_sha, new_sha}`；
   - `bash(cmd)` → 命令摘要 + artifact 路径。
5. **旧 tool results 投影**：保留一行结果 + artifact 路径，不保留完整日志。
6. **never orphan tool result**：按完整 turn 裁剪，或同时保留 `tool_call_id` 对应的 assistant 消息。
7. **当前工作集**：在投影后的历史后追加确定性的 worktree 状态（变更文件、diffstat、最近 verify 失败），不放完整文件。
8. **硬预算**：超限从最旧 turn 开始丢，直到满足。
9. **失败包只保留最新**：旧 verify 反馈被替换，不累积。
10. **不做模型摘要**：投影是确定性规则，不能为了省 token 再调一次 LLM。

配置：

```toml
[churn]
project = "auto"             # auto | off
max_history_bytes = 24576
keep_recent_turns = 4
min_clear_tokens = 2000
write_guard = "create"       # create | off
```

`auto` 表示“超过阈值才投影”，不是“每步都投影”。

### 8.3 patch-first 与 write 守卫

- `edit` 保持主路径：`old` 必须唯一或 `replace_all`；失败时提示“先 read 精确区间”，不要提示“重写整个文件”；
- `write` 增加 `mode`：
  - 默认 `create`：只允许创建不存在的文件；
  - 覆盖已存在文件必须 `mode="replace"`；
  - 没有 `mode` 的覆盖用短错误拒绝，并提示 `edit`；
  - `expected_sha256` 可选，后置用于并发保护；
- `write` 单次内容上限（例如 16KB），超过要求 patch 或分块；
- v1 不默认引入 `apply_patch`。先度量 `edit` 失败率；如果失败率持续高，再引入 V4A 结构化 patch。外部 adapter 只能靠 prompt 和选型，不能从 Loom 侧投影它的历史；
- system prompt 和失败包明确“优先 edit，不要整文件重写”。

**实现（2026-11-09）**：`tools.rs` 的 `write` 默认 `mode=create`，覆盖已存在
文件必须 `mode=replace`，否则返回短错误并提示 `edit`；单次内容上限 64KB；
同一文件第 N 次整文件覆盖在 observation 里标 `full rewrite #N`。`edit` 未命中
时错误信息指向“read 该文件的 1-based 区间并复制当前文本，不要重写整个文件”。
`tool_schema()` 与 `default_system()` 同步要求“优先 edit”。测试覆盖：mode
门禁、拒绝后文件不变、重复重写计数、超限拒绝、edit 失败提示。

### 8.4 token 归因

- `UsageRecord` 增加可选 `step`，同步 `schemas/usage-record.v1.json`；这是增量字段，不破坏旧数据；
- 每次调用记录 `step`、input/cached/output、tool_names、history_bytes、projected_bytes、write_paths、rewrite_count；
- `logs/churn.json` 汇总：
  - `rewrite_output_tokens`：重复写同一文件的输出；
  - `history_carry_tokens`：旧版本在后续请求中的估算；
  - `avoided_input_tokens`：投影后少发的估算；
  - `cache_invalidation_cost_est`：破坏 prefix cache 的估算（金额，不并入 token）；
  - `wasted_tokens_est` = `max(0, rewrite_output_tokens + history_carry_tokens − avoided_input_tokens)`；
  - `wasted_cost_usd_est`：按模型价格表计算，未知标 `unknown`；
  - `write_passes` / `churn_ratio`：诊断，不作为主 KPI；
  - 所有估算标 `estimated: true`，以账单/usage 为准。

`loom churn stats [--by model]` 第一屏 token/成本，第二屏才写次数。

**实现（2026-11-09）**：`AdapterUsageRow` 与 `UsageRecord` 增加可选
`step` / `model_id` / `tool_names` / `write_paths` / `rewrite_count` /
`history_bytes` / `projected_bytes`（同步 `schemas/adapter-usage.v1.json`、
`schemas/usage-record.v1.json`）。native 每步先算投影前后序列化历史字节，
工具执行完再落 usage 行，因此行里能带上本步工具与写入路径；run 结束写
`logs/churn.json`，其中 `rewrite_output_tokens` 按重复写入的 payload 估算，
`history_carry_tokens` 按“写于第 S 步 × 剩余步数”估算，`avoided_input_tokens`
按每步 `(history_bytes - projected_bytes) / 4` 估算，`cache_invalidation_cost_est`
只在能力位有 `cache_write_usd_per_mtok` 时给出，否则 0。价格未知时
`wasted_cost_usd_est` 为 `null`（unknown），不猜。`loom churn stats` 聚合
`.loom/runs/*/logs/churn.json`，`--by model` 按 alias + provider id 分组。

### 8.5 成本感知重启

后置到有 A/B 数据之后：

- 触发：同一文件重写 ≥N 次，或 `wasted_tokens_est` 超阈值；
- 动作：重建 `messages`，只带 system + packet + worktree 摘要 + churn 摘要 + 最新失败；
- 限制：每 run 最多 1 次；共享原预算；记录 `task.churn` 或 churn 日志；
- 风险：丢关键上下文导致质量下降；没有真实 A/B 前不默认开启。

### 8.6 离线测试

- 脚本化 provider 连续 5 次写同一 8KB 文件；记录每次实际发送的 `messages` 字节数；无投影时随步数增长，有投影时有界；
- 构造超长历史，断言裁剪后没有 orphan tool result；
- `write` 覆盖守卫：第二次覆盖被短错误拒绝；`edit` 成功；
- churn 统计用合成 usage 行，断言字段与 `estimated` 标记；
- 投影不改变 system/packet 前缀（字节比较）；
- acceptance 仍能通过；重启最多 1 次。

### 8.7 风险与停止条件

| 风险 | 缓解 |
|---|---|
| 质量回退 | 保留最近 turn + worktree 摘要；A/B 首过率下降 >2pp 关闭投影 |
| 前缀缓存失效 | 稳定前缀字节不变；`min_clear_tokens` 阈值 |
| tool_call 配对错误 | 按完整 turn 裁剪 + 测试 |
| 指标误导 | 标 `estimated`；以账单/usage 为准 |
| 外部 adapter 不可控 | 只做 watchdog/选型，不承诺投影 |
| 过早硬拦 | 先投影；write 守卫只拒绝无 `mode` 覆盖 |

### 8.8 真实 A/B：投影关 vs 开（2026-11-09）

用官方 `deepseek-flash`（wire `chat`，usage 可信）跑同一 fixture、同一任务：
`src/data.txt` 约 8KB，任务 = read → write 第一行 → finish。两臂各自在临时仓库从
同一提交开始，唯一差异是投影参数：

- `off`：`LOOM_NATIVE_HISTORY_BYTES=0`；
- `on`：`LOOM_NATIVE_HISTORY_BYTES=4096`、`LOOM_NATIVE_KEEP_TURNS=1`、
  `LOOM_NATIVE_MIN_CLEAR=200`（比默认 24KB / keep 4 / clear 2000 激进，
  目的是让 4–5 步的任务里就能看到杠杆）。

总计：

| arm | steps | input | cached | output | total tokens | cost_usd | wall |
|---|---|---|---|---|---|---|---|
| off | 4 | 14,747 | 9,728 | 876 | 15,623 | 0.001308 | 7s |
| on | 5 | 13,875 | 9,984 | 899 | 14,774 | 0.001153 | 9s |

逐请求（`history_bytes` 是投影前全文，`sent` 是实际发送）：

| step | off: full→sent / input | on: full→sent / input |
|---|---|---|
| 1 | 3,818 → 3,818 / 1,826 | 3,817 → 3,817 / 1,826 |
| 2 | 5,759 → 5,759 / 2,352 | 15,195 → 15,195 / 4,764 |
| 3 | 16,822 → 16,822 / 5,213 | 16,278 → 5,754 / 2,332 |
| 4 | 17,392 → 17,392 / 5,356 | 16,637 → 6,113 / 2,426 |
| 5 | — | 16,986 → 6,462 / 2,527 |

结论（n=1，只说明机制，不说明首过率）：

- 同样是约 16–17KB 的完整历史，`off` 每步 5.2–5.4k input，`on` 只有 2.3–2.5k，
  单步 input 降 46%–55%；`churn.json` 报 `avoided_input_tokens=7893`（按
  `(history−projected)/4` 估），与实测三步约 8.4k 的差额同量级，估算口径可用。
- `on` 用更少的累计 input 多跑了一步（5 步 13,875 input vs 4 步 14,747），
  单步 token 3,906 → 2,955（−24%），单步成本 $0.000327 → $0.000231（−29%）。
- 两臂都因任务预算 `max_input_tokens=12000` 在末尾记为 `budget_exceeded`，
  acceptance 本身已通过；因此这组数字比较的是**每请求体积**，不是任务成功率。
- `wasted_tokens_est=0` 是正确结果：本次没有重复整文件写入，投影收益只体现在
  `avoided_input_tokens`；写抖动与投影是两个独立杠杆，不能只看 `churn_ratio`。
- 默认参数（24KB / keep 4 / clear 2000）在 4 步任务里不会触发；真实 #24 任务
  每步 12–31k，投影触发更早、绝对收益更大，但需要下一轮真实任务集验证首过率。

复现：`scripts/ab-churn.sh --arm off|on`，`--report` 出上面的表；脚本自带
`LOOM_AB_MAX_TOKENS`（默认 30k，两臂合计）上限。注意 `scripts/dev.sh` 只透传
白名单 env，覆盖端点要在容器内 `export`，否则会静默回落到 `.env.local` 的官方端点。

## 9. F. Skills

### 9.1 当前试点事实

五个项目级 skill 已存在并通过 OpenCode 自动发现：

| ID | 作用 | 自动广告 | 正文约 |
|---|---|---|---|
| `docs-writing` | 文档写作、结构、Markdown、去 AI 味 | 是 | 0.6K tokens |
| `code-quality-review` | 架构边界、依赖、code smell、重构评估 | 是 | 1.2K tokens |
| `architecture-design` | 模块边界、接口、seam、ADR | 是 | 0.8K tokens |
| `refactor-code` | 行为保持的清理、去重、简化 | 是 | 0.8K tokens |
| `format-code` | Rust/YAML/SQL/JSON/Markdown/Shell/TOML 格式化 | 是 | 0.6K tokens |

五个描述合计约 300 tokens/step；50 步会话约 15K tokens 固定广告成本。正文只在触发时加载，参考文件按需读取。试点说明和第三方许可见 `.opencode/skill-pilot/`。

### 9.2 判断：v1 不再造第二套 skill 运行时

理由：

- OpenCode 已经提供项目级发现、按需加载和描述广告；再写 `loom skill` 会重复实现，并制造两个事实源；
- 当前没有第二个外部 adapter 需要 Loom 自己加载 skill；
- L2 评估依赖真实模型、固定任务集和账单，当前不具备；
- SWE-Skills-Bench 和 SkillsBench 都说明 skill 的收益高度异质，先做治理比做加载器更重要。

v1 只做三件事：

1. `.opencode/skills.lock`（tracked）记录每个 skill 的路径、sha256、license、来源、描述长度；
2. `scripts/check-skills.sh` 做静态检查，作为 `.loom.ci.toml` 的 `skills-check` job；
3. 触发预算：单个 description ≤400 字符，五个合计 ≤1500 字符；必须写“不要用于什么”。

### 9.3 静态检查

`scripts/check-skills.sh` 至少检查：

- 每个 `SKILL.md` 有合法 frontmatter，`name` 与目录一致；
- `description` 非空、≤400 字符、包含触发条件和“不要用于”；
- 正文 ≤5k tokens（按字节估算），参考文件路径存在且不逃逸；
- 没有 symlink 指向仓库外；
- 没有可执行脚本、网络调用、secret 模式（当前试点没有脚本；有则人工复核）；
- 与 `skills.lock` 的 sha256 一致；
- 许可证文件存在，第三方来源记录在 `THIRD_PARTY_NOTICES.md`。

`skills.lock` 示例：

```json
{
  "v": 1,
  "skills": [
    {
      "id": "docs-writing",
      "path": ".opencode/skills/docs-writing/SKILL.md",
      "sha256": "...",
      "license": "MIT",
      "source": "internal adaptation",
      "description_chars": 280
    }
  ]
}
```

lock 放 `.opencode/` 下并 tracked，不能放 `.loom/`。如果以后支持外部 adapter 加载，再考虑根目录 `skills.lock` 或 `loom skill` 命令。

### 9.4 L2 评估协议（后置）

等真实模型、固定任务集和账单：

- 同一任务集、同一模型、同一预算，paired 跑“加载/不加载”；
- 指标：首过 verify、CPVT、TPVT、WPT、触发率、误触发成本；
- 每个 skill 至少 20–30 个任务；报告差值置信区间；
- 只有“无质量回退且 CPVT 不升”才从 `experimental` 升为 `project`；
- 有害 skill（覆盖显式指令、导致回退）立即停用；
- 不做全局安装、不做联网自动安装、不做 embedding 检索。

### 9.5 风险

| 风险 | 缓解 |
|---|---|
| 描述过宽，频繁误触发 | 描述预算 + 触发/不触发样例 + 静态检查 |
| skill 覆盖 TaskSpec | 正文视为不可信输入；系统约束优先；有害即停用 |
| 固定广告成本 | 五个描述约 300 tokens/step；超过预算先压缩描述 |
| 评估不可做 | 先 lock/静态检查，L2 后置；不宣称能力提升 |
| 第二套事实源 | v1 不写 `loom skill` 加载器 |

## 10. 横向契约与测试

任何事件/状态/配置变更，按 `AGENTS.md` §4 同时完成：

1. `loom-core` 类型与穷举 `match`；
2. `schemas/*.json`（事件 enum、字段、`additionalProperties`）；
3. 文档：`doc/03` §11.2、`doc/10`（输出/退出码）、`doc/15`、本文；
4. 至少一个单元/集成测试；
5. CLI `--help`、退出码、`--json` 纯度；
6. 旧数据兼容：新增字段可选 + `serde(default)`；破坏性变更升 v2。

建议新增两个防漂移测试：

- 读取 `schemas/event.v1.json` 的 `enum`，与 `EventType` 字符串集合比较；
- 读取 `schemas/receipt.v1.json` / `usage-record.v1.json` 的 `required`/properties，与 Rust 类型做最小一致性检查（至少保证新增字段已写入 schema）。

`Config` 增加 `deny_unknown_fields` 是有意的行为变更：旧配置里的未知 section 会从“静默忽略”变成“明确报错”。这是好事，但要在 release note/`doctor` 里给出清晰错误。

测试入口：

```bash
make check
./scripts/dev.sh bash /work/scripts/smoke.sh
./scripts/dev.sh bash /work/scripts/smoke-native.sh
```

新增测试尽量用临时目录、假命令、脚本化 provider，不依赖宿主机仓库内容。

## 11. 分期与验收

### 阶段 0：状态与 claim（2–3 人日）

范围：`TaskStatus::NeedsInput`、claim 快照、verify 映射、退出码、事件 schema 漂移测试。

验收：

- `needs_input` 经 verify 后仍为 `needs_input`，不产生 `task.failed`；
- `blocked` / `budget_exceeded` 不再写成 `claim_not_done`；
- 重复 verify 不丢 claim；
- 升级计数不增加；
- schema 漂移测试通过。

### 阶段 1：attention 可见性（3–4 人日）

范围：`attention.*` 事件、`.loom/inbox.json` 缓存、`loom inbox list/show/ack/defer/resolve/--line/--check`、TTY footer、doctor 事项。

验收：

- TTY 下执行 `loom status`/`dispatch`/`verify` 后 stderr 出现一行待办；
- `--json` stdout 无 footer；
- 非 TTY/CI 默认不打印；
- `--check` 有 blocking 时退出 2；
- ack 不关闭事项；resolve 才关闭；
- footer 失败不影响原命令退出码。

### 阶段 2：本地 CI 核心（5–7 人日）

范围：`loom-ci` crate、根目录 `.loom.ci.toml`、探测/生成、plan/run/doctor、runner/argv、日志预算、report。

验收：

- 在临时目标项目生成 `.loom.ci.toml`；Loom 自身 dogfood 使用 `./scripts/dev.sh` 另行验证；
- `loom ci run --profile pre-commit` 在格式错误时失败；
- `--json` 纯 JSON；日志落盘且摘要有界；
- doctor 能报缺容器引擎/runner；
- 不覆盖已有配置；
- 没有证据时不猜配置。

### 阶段 3：question protocol（3–4 人日）

范围：native `ask` 工具、`questions.json` 校验、`.loom/answers/`、`loom answer`、Context Compiler 注入、assumptions。

验收：

- 脚本化 provider 调用 `ask` → exit 2 → inbox 可见 → answer → ready → 新 run 收到答案 → verify 通过；
- 多 blocking 问题未答完前不放行；
- 无 `questions.json` 时不猜问题；
- 回答不进入失败计数。

### 阶段 4：CI hooks / safe fix / report（3–4 人日）

范围：install-hooks、pre-commit/pre-push、`--fix`、diff 展示、report/attestation、verify-attest。

验收：

- hooks 幂等、非 Loom hook 拒绝、备份；
- `--fix` 不 stage/commit，改动可见；
- 同 tree attestation 通过，不同 tree 失败；
- `--no-verify` 不伪装成已记录；
- 服务器跳过**不在本阶段**。

### 阶段 5：churn（5–7 人日）

范围：步骤级投影、usage step、churn 统计、write 守卫、`edit` 强化；soft restart 可选。

验收：

- 5 次重写场景 input 有界；
- tool_call 配对正确；
- churn 字段完整且标 estimated；
- acceptance 不退化；
- 前缀字节稳定；
- A/B 首过率下降 >2pp 时关闭投影。

### 阶段 6：skills 治理（1–2 人日）

范围：`skills.lock`、`scripts/check-skills.sh`、CI `skills-check` job。

验收：

- lock 与文件 sha256 一致；
- 描述长度和触发边界检查通过；
- 不做 `loom skill` 运行时；L2 后置。

### 后置

- 真实 goose/OpenCode canary：需要容器内二进制；
- native vs adapter A/B、真实 CPVT/TPVT/WPT：需要 provider key、账单、固定任务集；
- 服务器按 attestation 跳过：需要签名/受信 runner；
- skills L2 评估：需要真实模型和任务集；
- act/workflow 模拟、嵌套容器 CI、review/skill job、并行 CI：不在 v1。

### 并行建议

- 阶段 1 和阶段 2 文件边界基本不重叠，可以并行；如果只有一个实现者，先做 0，再按 1→2 或 2→1 均可。
- 阶段 3 依赖阶段 1 的 inbox；不要提前做自动回答。
- 阶段 5 依赖阶段 0 的状态和 usage step；不要在 verify 语义未修时做 churn 统计。
- 阶段 6 独立，可以随时插入，但不要扩成 skill 运行时。

## 12. 需要确认的决策

1. **CI 配置位置**：确认根目录 `.loom.ci.toml` tracked，`.loom/ci/` ignored。
2. **attestation 授权**：确认 v1 不根据本地 attestation 跳过服务器 CI，只做证据/度量。
3. **verify 退出码**：确认 `0/1/2/3`（2 = needs_input/blocked，3 = budget）。
4. **`needs_input` 状态**：确认新增独立 `TaskStatus`，不复用 `blocked + code`。
5. **attempt 语义**：回答后新 run 是否递增 attempt（建议递增，另记 `question_round`）。
6. **答案存储**：确认 `.loom/answers/<task_id>.jsonl` 作为本地内容存储，事件只存哈希/元数据。
7. **footer 默认**：确认 TTY 默认开启，`LOOM_NO_INBOX=1` 关闭，非 TTY 默认关闭。
8. **CI schema**：确认 `[[jobs]] + argv + [runner]`，v1 不支持 `[jobs.<id>] + cmd`，也不支持 `kind`/`env`/`network`。
9. **hooks 默认**：确认 `hooks_fix_safe` 默认 false；safe fix 需要显式开启。
10. **churn 默认**：确认 `write_guard = "create"`、`project = "auto"`；`apply_patch` 后置。
11. **skills v1**：确认不写 `loom skill` 运行时，只做 lock + 静态检查；L2 后置。
12. **CI 探测范围**：确认 v1 只做 Rust 单栈 + `scripts/dev.sh` + Makefile，其他栈后置。

在确认这些决策前，不进入代码实施。本文只做评估，不改实现。
