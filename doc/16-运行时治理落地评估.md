# 16 运行时治理落地评估

> 状态：**评估稿，未改实现代码**（2026-11-07）。
> 范围：只评估 [15-Agent运行时治理与工程化.md](15-Agent运行时治理与工程化.md) 中四个方向的落地性——attention inbox / question protocol、本地 CI、churn、skills。

## 0. 结论

四个方向都能在当前架构内落地，但有三处设计需要先修正，否则实现后会得到“看起来能用、实际不可信”的结果：

1. **配置要叫 `.loom.ci.toml`，并且不能放在 `.loom/` 里。** `.loom/` 是运行时状态，被整体 ignore；`.loom.ci.toml` 是**项目策略**，应放在目标项目根目录并纳入 git。它不是“因为 `.loom/` 被 ignore 才要提交”，而是因为它需要被团队共享、被 git worktree 继承、被服务器/attestation 引用、被 PR 审查。若只是个人本地偏好，才可以不提交，但那样不能用于团队闸门/服务器证据；个人覆盖可后置 `.loom/ci.local.toml`（ignored）。运行时日志仍放 `.loom/ci/`。
2. **本地 attestation 不能直接授权服务器跳过 CI。** 本地文件可伪造；在 v1 没有签名/受信 runner 的前提下，attestation 只能作证据与度量，不能作授权。服务器跳过应后置到有 HMAC/受信执行环境之后。
3. **`verify` 必须先停止覆盖 claim 回执，并停止把 `needs_input` / `blocked` / `budget_exceeded` 写成 `task.failed`。** 当前实现会丢失回执状态、污染升级计数；这是 attention/question 的前置正确性修复，不是可选项。

优先级建议：

| 顺序 | 工作 | 理由 | 离线可验证 | 粗略人日 |
|---|---|---|---|---:|
| A | `needs_input` 正确性修复 + 最小 attention | 修 bug；是所有后续可见性的地基 | 是 | 2–3 |
| B | attention inbox + footer | 满足“至少一个角落能看到待办”；不依赖模型 | 是 | 3–4 |
| C | question protocol + `loom answer` | 让提问成为可恢复流程 | 是（脚本化 provider） | 3–4 |
| D | 本地 CI 核心（`.loom.ci.toml` + plan/run/doctor） | 高价值、独立、可先做 | 是 | 5–7 |
| E | hooks + safe fix + report | 把检查前移；依赖 D | 是 | 3–5 |
| F | churn 步骤级投影 + token 归因 | 省 token 的主杠杆；需要 A/B | 部分 | 4–6 |
| G | patch-first / write 守卫 | 工具层改动明确 | 是 | 2–3 |
| H | skills scan/catalog/lock/按需加载 | 结构先立；评估后置 | 是 | 5–8 |

结论是**可行，但不要把 15 里的工作量估计当作承诺**：把事件、状态、schema、CLI、测试和回执兼容一起算进去，attention + questions 的现实成本约 8–11 人日，而不是 4–5 人日；CI 核心约 5–7 人日。

## 1. 评估基线：当前代码事实

以下事实均来自当前工作树，不是设计假设。

| 事实 | 位置 | 影响 |
|---|---|---|
| `EventType` 有 19 种事件，`schemas/event.v1.json` 用 `enum` 白名单 | `loom-core/src/event.rs`、`schemas/event.v1.json` | 新增 `attention.*` / `task.needs_input` / `task.answered` 必须四处同步 |
| `TaskStatus` 有 11 种，**没有 `needs_input`** | `loom-core/src/task.rs` | `status_after_event`、`FromStr`、`is_open`/`is_terminal` 都要扩展 |
| `ReceiptStatus` 已有 `Done`/`Blocked`/`NeedsInput`/`Failed`/`BudgetExceeded` | `loom-core/src/receipt.rs` | 回执层已能表达提问，缺的是控制面状态与流程 |
| `verify` 只把 `ReceiptStatus::Done` 视为 `claim_done`，其余一律写 `task.failed`（`code=claim_not_done`） | `loom-cli/src/verify_cmd.rs` | `needs_input`、`blocked`、`budget_exceeded` 被误判成失败 |
| `verify` 读取 `outbox/receipt.json` 后，**用验收回执覆盖同一路径** | `verify_cmd.rs`、`loom-store/src/run.rs::receipt_path` | adapter 的 claim 状态在 verify 后不可追溯；需要 claim 快照 |
| `dispatch` 在 adapter 返回后无条件写 `task.receipt`，而 `status_after_event(TaskReceipt) = Receipt` | `dispatch_cmd.rs` | 即使回执是 `needs_input`，任务状态也先变成 `receipt` |
| `route` 的失败历史只数 `task.failed` | `route_cmd.rs::history` | 只要 verify 继续误写 failed，提问就会触发升级 |
| `dispatch` 只接受 `pending/ready/failed/escalated` | `dispatch_cmd.rs::prepare` | 没有 `needs_input` 的恢复入口；回答后必须回到 `ready` |
| `Config` 顶层只有 `#[serde(default)]`，**没有 `deny_unknown_fields`** | `loom-core/src/config.rs` | 新增 `[attention]`/`[ci]` 时，拼错的 section 会被静默忽略 |
| `read_events` 每次全量读取并解析 JSONL，损坏行直接报错 | `loom-store/src/events.rs` | footer 若每命令调用会放大开销；需要缓存视图 |
| `Project::init` 只建 `.loom/` 骨架、`config.toml`、`goal.md`、`constraints.md` 和 `.gitignore` | `loom-store/src/project.rs` | CI bootstrap 没有落点；`.loom/` 被整体忽略 |
| 仓库中没有任何 `ci` / `inbox` / `skill` 模块或命令 | `grep src/crates schemas` | 三个方向都是从零开始，不是改几行 |
| native 每步 `provider.complete(messages.clone())`，`messages` 只增不减 | `loom-native/src/run.rs` | churn 的输入复利是确定事实 |
| native 已有 `edit`（old/new），`write` 可直接覆盖整文件 | `loom-native/src/tools.rs` | patch-first 已有半个基础；缺 write 守卫与 diff 工具 |
| native `parse_finish` 接受 `needs_input`，退出码 2，但不会生成 `questions.json` | `loom-native/src/run.rs` | 提问只有状态，没有可回答的内容 |
| `UsageRecord` 没有 step 维度 | `loom-core/src/usage.rs` | churn 归因需要补字段或独立 step 日志 |
| event/receipt/task/usage 等 schema 都是 `additionalProperties: false` | `schemas/*.json` | 任何新增字段都要同步 schema，否则消费端/校验端会拒绝 |

这组事实决定了实现顺序：**先修状态与回执语义，再做视图和 CI；churn 与 skills 放在有度量之后。**

## 2. attention inbox 与 question protocol

### 2.1 当前流程与缺陷

当前一次“提问”实际走成：

```text
adapter 退出 2 / final.md 声明 needs_input
  -> normalize 生成 ReceiptStatus::NeedsInput
  -> dispatch 写 task.receipt（状态 Receipt）
  -> loom verify 读取 claim，claim_done=false
  -> 仍跑 acceptance；无论结果如何，写 task.failed(code=claim_not_done)
  -> route 的 history 把这次 task.failed 计入升级阈值
  -> 用户只能在对话历史/日志里看到这次提问
```

这里有三个独立缺陷：

1. **状态错误**：`needs_input` 不是失败；它不应进入升级计数。
2. **证据丢失**：verify 覆盖 `receipt.json`，之后无法知道 adapter 当时是提问、阻塞还是预算超限。
3. **可见性缺失**：即使状态正确，也没有一个独立于聊天历史的待办出口。

### 2.2 最小契约变更

| 组件 | 变更 | 必改位置 |
|---|---|---|
| 事件 | 新增 `task.needs_input`、`task.answered`、`attention.opened`、`attention.updated`、`attention.resolved`、`attention.expired` | `EventType`、`as_str`、`FromStr`、`Event::validate`、`schemas/event.v1.json` |
| 状态 | 新增 `TaskStatus::NeedsInput` | `as_str`、`FromStr`、`status_after_event`、`is_open`/`is_terminal`（新增 `is_parked` 可选） |
| 回执 | 保留 claim 证据；verify 回执增加可选 `claim_status` | `Receipt`、`schemas/receipt.v1.json`、verify 写入逻辑 |
| 配置 | 新增 `[attention]`、`[questions]`；`Config` 增加 `deny_unknown_fields` | `loom-core/src/config.rs` |
| CLI | `loom inbox list/show/ack/defer/resolve`、`--line`、`--check`；`loom answer` | `loom-cli/src/main.rs` + 新模块 |
| 视图 | `.loom/inbox.json` 只读缓存 | 新 `attention` 模块；由事件重放生成 |

`EventType` 的穷举 `match` 会让漏改在编译期失败；`schemas/event.v1.json` 不会，所以必须加一个**schema 漂移测试**：读取 schema 的 `enum`，与 `EventType::all()` 的字符串集合比较。当前没有这层保护，新增事件很容易只改 Rust 类型。

`TaskStatus::NeedsInput` 的语义建议：

- `satisfies_dependency() == false`；
- `is_terminal() == false`（可以恢复）；
- `is_open() == true`（它仍是未结束任务，`resume` 应能看到，但不应自动重派）；
- `dispatch` 的 gate **不放行** `needs_input`；只有 `loom answer` 把全部 blocking 问题回答后写 `task.ready`，才回到可派发状态；
- `resume --dispatch` 不应把 `needs_input` 当成 ready 自动跑；应提示“有问题待回答”。

### 2.3 回执快照：先解决 verify 覆盖 claim

推荐最小方案：

1. adapter 仍写 `outbox/receipt.json`，契约不变。
2. `verify` 在覆盖前，如果 `logs/claim.json` 不存在，就把原始回执复制到 `.loom/runs/<id>/logs/claim.json`。
3. `verify` 写回 `outbox/receipt.json` 时，增加可选字段 `claim_status`，并在事件 data 里记录 `claim_status`。
4. 重复执行 verify 时，从 `logs/claim.json` 读原始 claim，避免把上一次 verify 回执当成 claim。

这样：

- 不改变 adapter 的输出路径；
- 不把 `logs/claim.json` 当事实源（事实源仍是事件）；
- 用户能追溯“当时 worker 说了什么”；
- 后续 `loom status` / inbox 不需要重新猜。

不建议把 verify 回执改到 `verify.json` 再保留原 `receipt.json`：会改变现有 `dispatch`/`status`/canary 对 `receipt.json` 的假设，收益不抵迁移成本。

### 2.4 verify 的状态映射

`verify` 应按 claim 状态分流，而不是一律 `TaskFailed`：

| claim 状态 | acceptance | 写事件 | 任务状态 | 退出码 |
|---|---|---|---|---|
| `Done` | 全过 | `task.verify` + `task.passed` | `passed` | 0 |
| `Done` | 有失败 | `task.verify` + `task.failed(code=verify_fail)` | `failed` | 1 |
| `NeedsInput` | 不跑（默认） | `task.needs_input` + `attention.opened` | `needs_input` | 2 |
| `Blocked` | 不跑（默认） | `task.blocked` + `attention.opened` | `blocked` | 2 |
| `BudgetExceeded` | 不跑 | `task.failed(code=budget_exceeded)` | `failed` | 3 |
| 无 claim / 解析失败 | 不跑 | `task.failed(code=claim_missing)` | `failed` | 1 |

说明：

- `NeedsInput` / `Blocked` 默认**不跑 acceptance**：worker 已明确说没完成或缺条件，跑测试只会制造噪声和额外成本。需要证据时可加 `--run-verify`，但仍不得因此标记 passed。
- `BudgetExceeded` 是否计入升级可以再议；建议先写 `task.failed` 但 `data.code=budget_exceeded`，让路由历史能区分“真失败”和“预算耗尽”，后续可单独统计。
- 退出码 2/3 是新增语义；当前 `verify` 只返回 0/1，`main` 把错误映射为 4。需要同步 CLI 文档与测试，避免现有脚本把 2 当成未知错误。
- `verify` 回执的 `status` 应反映最终状态（`Done`/`Failed`/`NeedsInput`/`Blocked`/`BudgetExceeded`），而不是永远只写 Done/Failed。

`dispatch` 侧也应配合：保留 `task.receipt` 作为“adapter 已返回”的历史事件，然后根据回执状态追加 `task.needs_input` / `task.blocked`。这样状态重放的最终值正确，同时保留回执时间点。不要直接把 `TaskReceipt` 的 `status_after_event` 改成依赖 data；`status_after_event(current, event)` 不接收 data，改签名会波及所有调用。

### 2.5 questions.json 与 answer

`questions.json` 建议结构（放 `outbox/`，由 adapter 或 native 的 `ask` 工具写）：

```json
{
  "v": 1,
  "task_id": "T-20261107-001",
  "attempt": 1,
  "questions": [
    {
      "id": "Q-1",
      "text": "是否允许删除旧迁移文件？",
      "kind": "choice",
      "options": ["允许", "保留并新增迁移"],
      "blocking": true,
      "scope": "task",
      "default": "保留并新增迁移",
      "confidence": "medium",
      "evidence": [".loom/runs/R-.../outbox/final.md"]
    }
  ]
}
```

约束：

- 最多 5 个问题；`text` ≤ 1KB；`options` ≤ 8；`id` 在 task 内唯一；
- 不接受任意 shell 命令或 URL 作为 action；
- `blocking=true` 才进入 `needs_input`；非 blocking 可只开 `info` 事项；
- 文件不存在或非法时，不自动猜问题；按 `claim_missing` / `verify_fail` 处理，并在 `next_hint` 提示协议。

native 侧需要新增 `ask` 工具（或 `finish(status=needs_input, questions=[...])`）：

- 在工具 schema 中声明 `ask`；
- 在 `run.rs` 的工具循环里像 `finish` 一样拦截，写 `outbox/questions.json`，设置 `Finish { status: "needs_input" }`；
- 退出码 2，`write_final` 仍写摘要；
- 脚本化 provider 可以测试整条链路。

回答侧建议：

- `loom answer T-001 --question Q-1 --text ...` / `--option ...` / `--assume ...` / `--defer ...`；
- 答案内容写 `.loom/answers/<task_id>.jsonl`（本地状态，不放进旧 run 的 outbox，避免事后改历史）；
- 每次回答写 `task.answered` 事件，data 含 `question_id`、`answer_source`（human/assumption/parent）、`answer_sha256`、`answered_by`；
- 当所有 blocking 问题都有答案时，追加 `task.ready`；`task.answered` 本身**不直接改状态**，否则多问题场景会提前放行；
- `attempt` 建议递增（每次 dispatch/verify/回执需要唯一 attempt），另在事件 data/run meta 里记录 `question_round`；把“attempt = 第几次执行”与“失败次数”分开。15 §8 的“回答不递增 attempt”需要修正为“不把回答计入失败次数”，而不是复用 attempt。
- 下一次 dispatch 的 Context Compiler 读取最新答案与 assumptions，作为独立小节注入，受硬预算限制；
- `assumptions.jsonl` 记录“没问但假设了”的内容；低置信 assumption 开 `review` 事项，不阻塞。

### 2.6 attention 数据模型

事项（item）建议字段：

| 字段 | 说明 |
|---|---|
| `id` | 稳定 id，建议 `A-<hash>`，由 `kind + dedupe_key` 生成 |
| `kind` | `question` / `approval` / `operation` / `review` / `reminder` |
| `severity` | `blocking` / `action` / `info` |
| `status` | `open` / `acked` / `deferred` / `resolved` / `expired` |
| `title` / `summary` | 短文本，受 200B / 2KB 限制 |
| `source` | `verify` / `doctor` / `ci` / `route` / `human` / `agent` |
| `task_id` / `run_id` | 可空；operation 类事项可以没有 task |
| `dedupe_key` | 去重键，例如 `task:T-001:question:Q-1` |
| `actions` | 只做提示，不自动执行；最多 8 条 |
| `detail_path` | 长内容落 `.loom/attention/<id>.md` 或 JSON |
| `created_at_ms` / `updated_at_ms` / `expires_at_ms` | 生命周期 |
| `resolved_by` / `resolved_reason` | 审计 |

原则：

- **事件是事实源**：`attention.opened/updated/resolved/expired`；`.loom/inbox.json` 只是视图。
- `attention.*` 事件不应强制要求 `task_id`（缺工具、缺 key 是项目级事项）；`Event::validate` 的 `needs_task` 列表不要把这些事件加进去。
- 事件 data 只放短字段；长正文落 artifact，事件里放路径/哈希。
- `acked` 不等于 `resolved`；`defer` 只能作用于 `action/info`，不能把 `blocking` 藏起来。
- 自动 resolve 只用于确定性条件（工具已安装、同 tree CI 已通过、问题已回答）；需要判断的事项不自动关。

### 2.7 视图缓存与 footer

`read_events` 当前全量读取。footer 每条命令都跑一次会放大开销，尤其事件日志很长时。建议：

1. `.loom/inbox.json` 保存 `events` 的 `size`、`mtime_ms`、`sha256`（或至少 size+mtime）、`generated_at_ms`、`items`、`counts`。
2. 读取时先 `stat`；size/mtime 未变则直接用视图。
3. 变了则重放事件并原子写回（temp + rename）；写失败不影响命令，footer 静默跳过。
4. 事件被截断/手工修改时，size 可能变小；此时必须全量重放，不能做增量追加。
5. 视图只是缓存；`loom inbox` 在 `--json`/`--check` 时可以强制重放，避免脏缓存影响决策。

footer 接入点：

- `main()` 在调用 `run(cli)` 前保存 `format`、`root`、`command` 的标签；`run` 返回后（包括 `Err`）尝试打印 footer。
- 条件：stderr 是 TTY、非 `--json`、非 `loom inbox` 自身、非 CI 环境、`[attention].footer` 未关闭、`LOOM_NO_INBOX=1` 未设置。
- 只写 stderr；单行 ≤ 160 字符；内容类似：
  `attention: 2 blocking, 1 review | loom inbox --line | A-7f3: 是否允许删除旧迁移文件？`
- 没有待办时不打印，避免噪声。
- footer 失败绝不能改变退出码；所有错误吞掉。
- `loom inbox --line` 供 statusline/脚本轮询；`--check` 有 blocking 时退出 2；两者都不等待。

不要用后台 daemon：v1 的“常驻”是“每条命令都能看到 + 一个可轮询命令”，不是常驻进程。

### 2.8 attention 来源

第一批应产生事项的地方：

| 来源 | kind | 触发 |
|---|---|---|
| `verify` | `question` | claim `NeedsInput` 且有 blocking 问题 |
| `verify` | `operation` | claim `Blocked`，例如缺工具/缺 key |
| `doctor` | `operation` | 缺 podman/docker/cargo/goose/opencode 等 |
| `ci` | `review` / `operation` | job 失败；首次接入需要人确认 |
| `route` | `approval` | 成本护栏拒绝或需要升级确认 |
| `human` | `reminder` | 手工创建；`loom inbox add` 可后置 |

这样即使没有 agent 提问，用户也能在 footer 看到“需要装工具/需要确认 CI”这类操作事项。

### 2.9 离线测试

不需要真实模型即可覆盖：

- verify 收到 `NeedsInput`/`Blocked`/`BudgetExceeded` claim → 不写 `task.failed`，状态/退出码正确；
- 重复 verify 不丢 claim，`logs/claim.json` 保留原始回执；
- `attention.opened` → `.loom/inbox.json` 可见 → `ack` 不改 `resolved` → `answer` 后 resolve；
- footer：TTY 模拟困难时把“是否打印”抽成纯函数测试；`--json` stdout 纯 JSON；
- `loom inbox --check` 退出码 2；
- 脚本化 provider 调用 `ask` → questions.json → exit 2 → answer → 新 run 收到答案 → verify 通过；
- 多问题：只回答 1 个 blocking 时仍为 `needs_input`，全部回答后才 `ready`；
- 事件 schema 漂移测试。

### 2.10 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 状态/事件扩散 | 新增 6 种事件 + 1 种状态，涉及多处穷举 | 编译器 + schema 漂移测试 |
| 旧 adapter 不写 questions.json | 只有状态没有内容 | 明确协议；缺失时开 `operation` 事项，不猜 |
| footer 性能 | 每命令重放事件 | 缓存 + size/mtime 失效 + 失败静默 |
| 退出码变化 | 现有脚本把 2 当未知 | 文档 + 测试；先只在 `verify` 增加，不改变其他命令 |
| 回答存储位置 | outbox 属于 run，事后写会污染历史 | `.loom/answers/` 独立存储 |
| 多问题状态 | `status_after_event` 无 data | 由命令在“全部答完”时追加 `task.ready` |
| 用户忽略 dashboard | 只有 CLI footer | 先保证 footer 可见；TUI/桌面后置 |

## 3. 本地 CI

### 3.0 作用对象：目标项目，不是 Loom 自身

这是 15 最容易误读的地方：文档里的 Rust、`cargo`、`./scripts/dev.sh` 看起来像“Loom 仓库自己的 CI”，但产品意图是**Loom 管理的目标项目**。

| 层面 | 配置归属 | 说明 |
|---|---|---|
| Loom 自身开发 CI | Loom 仓库根目录 `.loom.ci.toml` | dogfood；验证 Loom 源码，用容器 runner |
| 目标项目 CI | 目标项目根目录 `.loom.ci.toml` | 产品功能；`loom ci` 在 `--root` 指向的项目运行 |
| 运行时状态 | `.loom/ci/` | 日志、report、attestation；不提交 |

同一个 schema，两个不同项目的实例。生成器不能把 Loom 自己的 `cargo`/`./scripts/dev.sh` 写死成目标项目默认值；目标项目可能是 Node、Python、Go、Makefile，runner 也可能为空（直接宿主执行）或 `uv`/`pnpm`/`docker compose`。

### 3.1 当前基线

- `loom init` 只建 `.loom/` 骨架、`config.toml`、`goal.md`、`constraints.md`，并更新 `.gitignore`；
- `loom doctor` 只检查 `.loom`、git、config、tasks/runs 等，不检查仓库级检查命令；
- 没有 `ci` 模块、`.loom.ci.toml`、hooks、report/attestation；
- 现有本地检查靠 `Makefile` + `scripts/dev.sh`，且必须在容器内跑。

### 3.2 必须先修正的设计点

1. **配置位置**：`.loom.ci.toml` 放仓库根目录，纳入 git；`.loom/ci/` 放运行日志和报告，保持忽略。
2. **执行环境**：runner 是目标项目的配置，不是产品默认。以 Loom 自身为例，它不能在宿主机直接跑 `cargo`，所以示例用 `["./scripts/dev.sh"]` 前缀；普通目标项目可以让 `runner` 为空，直接执行 argv，也可以用 `uv`/`pnpm`/`docker compose`。job 用 argv 数组而不是裸 shell 字符串。
3. **attestation 不是授权**：v1 只生成可校验的证据；服务器跳过后置。没有签名时，本地文件无法证明“真的跑过”。
4. **`--no-verify` 不可观测**：git 不会告诉 hook 自己被绕过。不要承诺记录 bypass；只能记录 hook 实际运行的结果。服务器最终门禁仍保留。
5. **hooks fail-open**：新克隆没有 `loom` 时不能阻止提交；打印警告并放行。服务器仍做最终检查。
6. **进程与日志**：CI 可能跑几分钟并产生大输出。必须流式写文件、限制内存、超时杀进程组；不能复用 verify 当前“全读进内存 + 只 kill sh”的做法。

**为什么 `.loom.ci.toml` 要提交**：

| 需求 | 不提交会怎样 |
|---|---|
| 团队共享同一套检查 | 每人各自一套，PR 无法审查检查变更 |
| git worktree 继承 | `.loom.ci.toml` 是 untracked，worker worktree 里没有，`loom ci` 行为不一致 |
| 服务器/attestation 引用 | 配置哈希无法复现，报告无法对应到同一 tree |
| 新人/新克隆 onboarding | 需要额外口口相传或脚本复制 |
| agent 修改检查 | diff 不可见，无法 review，容易成为隐藏后门 |

反过来，如果它只是个人偏好（比如“我只想本地跑 clippy，不想让别人也跑”），那就不必提交；但此时不能把它当团队闸门、服务器证据或 attestation 依据。v1 建议只做 tracked 主配置；个人覆盖 `.loom/ci.local.toml` 后置，且只能加个人 profile/超时，不能关闭团队 gate。

### 3.3 crate 边界

建议新增 `src/crates/loom-ci`：

```text
loom-cli  -> 只解析参数、调用 loom-ci、格式化输出
loom-ci   -> .loom.ci.toml 解析/校验、探测、plan、run、doctor、report、attestation
loom-core -> 共享类型/预算/哈希/时间；不放进程执行
loom-store-> 路径、config、事件；不依赖 loom-ci
```

`Project::init` 继续只建 `.loom` 骨架；`loom init` 在 CLI 层调用 `loom_ci::bootstrap` 生成 `.loom.ci.toml`，把结果追加到输出。这样避免 `loom-store -> loom-ci` 的反向依赖，也避免把 `ci` 逻辑塞进 CLI。

如果不想新增 crate，次选是 `loom-cli/src/ci/` 多文件模块；但这会让 CLI 承担执行/解析/报告，和“CLI 只做参数与输出”的边界冲突。新增 crate 更干净。

### 3.4 `.loom.ci.toml` 建议形态

```toml
version = 1

# 示例：Loom 自身用容器脚本，避免宿主 cargo。
# 目标项目可留空，或换成 uv/pnpm/docker compose 等 runner。
[runner]
argv = ["./scripts/dev.sh"]

[profiles]
pre-commit = ["fmt"]
pre-push = ["fmt", "clippy", "test"]
full = ["fmt", "clippy", "test", "build"]

[[jobs]]
id = "fmt"
argv = ["cargo", "fmt", "--all", "--", "--check"]
timeout_s = 120
local_sufficient = true
fix_argv = ["cargo", "fmt", "--all"]
fix_safe = true

[[jobs]]
id = "clippy"
argv = ["cargo", "clippy", "--workspace", "--all-targets", "--", "-D", "warnings"]
timeout_s = 600
local_sufficient = true

[[jobs]]
id = "test"
argv = ["cargo", "test", "--workspace"]
timeout_s = 900
local_sufficient = true
```

设计要点：

- **argv 数组优先**：不经过 `sh -c`，避免引号/注入问题，也便于 doctor 检查首命令；
- `runner` 是 argv 前缀；job 最终命令 = `runner.argv + job.argv`；`cwd` 默认仓库根；
- `fix_argv` 单独声明；只有 `fix_safe = true` 才允许 `--fix` 自动执行；
- `local_sufficient` 只对确定性 job 为 true；review/安全/发布/矩阵永远 false；
- `needs` 可做 job 依赖，但 v1 顺序执行，不做并行；
- `kind = "review"` / `kind = "skill"` 后置；v1 只做 `command`；
- `env` 不提供任意键值（避免把 token 写进仓库）；执行时继承必要环境，剔除 `*_API_KEY`、`*_TOKEN`、`LOOM_API_KEY` 等。

校验规则：

- `version == 1`；
- job id 唯一、非空；
- `argv` 非空，`argv[0]` 非空；
- `cwd` 不得逃逸仓库根；
- `timeout_s` 有上下限（例如 1–3600）；
- profile 引用的 job 必须存在；
- `local_sufficient` 只能用于 `kind=command`；
- 生成 `.loom.ci.toml` 时不覆盖已有文件。

### 3.5 `loom init` 探测

v1 只做**单栈、根目录**探测，避免过早处理 monorepo：

| 证据 | 生成 |
|---|---|
| 根 `Cargo.toml` 或 `src/Cargo.toml`（workspace） | `cargo fmt/clippy/test` |
| `scripts/dev.sh` | `runner.argv = ["./scripts/dev.sh"]` |
| `Makefile` 有 `check`/`test`/`fmt` | 优先采纳已有 target，不重复发明 |
| `package.json` scripts | `npm/pnpm run ...`（P1，可选） |
| `pyproject.toml` / `go.mod` | 后置 |

生成策略：

- `--dry-run` 打印将写入的内容，不落盘；
- 已有 `.loom.ci.toml` 默认保留并提示；
- `--force` 覆盖前先备份 `.loom.ci.toml.bak.<ts>`（或直接拒绝，二选一，倾向备份）；
- 生成后在 `doctor` 里校验 `runner` 是否可执行、容器引擎是否存在；
- 不自动生成 workflow，也不改 `.github/`；服务器跳过属于 P3。

### 3.6 `loom ci` 命令

MVP：

```text
loom ci plan [--profile pre-push] [--json]
loom ci run  [--profile pre-commit] [--keep-going] [--fix] [--json]
loom ci doctor [--json]
loom ci report [--run <id>] [--json]
loom ci verify-attest --report <path> [--json]
```

行为：

- `run` 顺序执行 profile 内 job；默认第一个失败即停；`--keep-going` 跑完；
- 每个 job 写 `.loom/ci/<run>/logs/<job>.log`，观察摘要受 8KB/24KB/128KB 预算约束；
- 退出码：`0` 全过、`1` 有 job 失败、`3` 超时/预算、`4` 配置/执行错误；
- `--json` 的 stdout 只有 JSON；进度/摘要走 stderr 或字段；
- `--fix` 只执行 `fix_safe` job，展示 `git diff --stat` 与 patch 路径；**不 stage、不 commit**；有改动时提示重新 `git add`；
- `doctor` 检查 config 可解析、runner 存在、容器引擎可用、job argv[0] 可找到；不实际跑 job；
- `report` 读 `.loom/ci/<run>/report.json`，不重新执行；
- `verify-attest` 校验 tree、`.loom.ci.toml` 哈希、job 结果摘要。

### 3.7 执行器细节

- `stdin = null`；`stdout/stderr` 流式写文件，只保留头尾摘要；
- `CommandExt::process_group(0)` + 超时杀整个进程组（Linux 容器环境；避免 `podman run` 子进程残留）；
- 设置 `NO_COLOR=1`、`CARGO_TERM_COLOR=never`、`TERM=dumb`，输出落盘前剥离 ANSI；
- 剔除 API key/token 环境变量；
- 记录 `argv`、`cwd`、退出码、耗时、工具版本（`--version` 可选，失败不阻塞）；
- v1 不声称网络隔离；需要联网的 job 标 `needs_network=true`，由人决定；
- 不自动修改 CI 命令；`.loom.ci.toml` 是人工/生成器产物，agent 只能建议。

### 3.8 hooks

- `loom ci install-hooks` 写 `.git/hooks/pre-commit` / `pre-push`；
- 文件带 `# loom-managed` 标记；已存在且非 Loom 管理时拒绝，`--force` 先备份；
- hook 内容只调用 `loom ci run --profile ... --from-hook`，不内联业务命令；
- `loom` 不存在、config 非法、runner 缺失时 fail-open + 警告；
- 幂等：重复安装不重复追加；
- 提供 `LOOM_CI_SKIP=1` 显式跳过（本地调试用），记录在 report 里；
- **不修改全局 git config**，不写 `core.hooksPath`；
- `--no-verify` 不承诺记录；只在 report 里记录 hook 实际运行/跳过原因。

### 3.9 report 与 attestation

`report.json` 建议字段：

```json
{
  "v": 1,
  "run_id": "CI-...",
  "profile": "pre-push",
  "ci_toml_sha256": "...",
  "tree": {
    "head": "abc123",
    "dirty_sha256": "...",
    "untracked_sha256": "..."
  },
  "started_at_ms": 0,
  "duration_ms": 0,
  "jobs": [
    {"id": "fmt", "argv": [], "exit": 0, "duration_ms": 0, "log_path": "...", "log_sha256": "..."}
  ],
  "local_sufficient": true,
  "advisory": false
}
```

tree 计算建议：`HEAD` + `git diff --binary` 的哈希 + 未跟踪文件的路径/大小/哈希排序；不要为了 attestation 执行 `git write-tree`（会碰 index）。同一 tree 的校验必须包含未跟踪文件，否则“本地跑过”可能漏掉新文件。

`attestation.json` 是 report 的摘要 + 可校验字段，不是授权：

- v1 不签名；
- `loom ci verify-attest` 只能证明“这份文件和这个 tree 对得上”；
- 服务器跳过需要 HMAC/受信 runner/受保护分支，属于后续安全设计；
- 在完成前，服务器 CI 应继续跑安全/发布/矩阵；本地 CI 的价值是**减少重复失败和反馈时间**，不是替代服务器。

### 3.10 与 attention 的衔接

- CI 失败：开 `review`（需要人看）或 `operation`（缺工具/配置）事项；
- 同一 tree 成功后自动 resolve 对应事项；
- `loom inbox --check` 可以在提交前提示“有未处理的 CI 失败”；
- report 里的 job 结果不作为 TaskSpec acceptance；`verify` 仍是任务权威。

### 3.11 离线测试

临时目录 + 假 runner 即可覆盖大部分：

- 解析/校验：良好配置、重复 id、缺失 job、逃逸 cwd、非法 timeout、`local_sufficient` 用于 review；
- 执行：真跑 `sh -c 'exit 1'` 的临时 job，检查退出码、日志、预算；
- 超时：`sleep` 子进程被杀，进程组无残留（至少检查父进程退出）；
- `--fix`：假的 fix 命令改文件，检查不 stage、diff 可见；
- hooks：临时 git 仓库，重复安装幂等、非 Loom hook 拒绝、备份；
- report/attestation：同 tree 通过、不同 tree 失败、脏文件/未跟踪文件改变哈希；
- `--json` stdout 纯 JSON；
- init 探测：临时 Rust workspace + `scripts/dev.sh`，生成预期配置；已有 `.loom.ci.toml` 不覆盖。

### 3.12 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 配置不进仓库 | `.loom.ci.toml` 放 `.loom/` | 放根目录并提交 |
| 假阳性“本地过了” | 环境漂移、未跟踪文件 | tree 含未跟踪；doctor 检查环境；服务器仍跑最终门禁 |
| attestation 被伪造 | 本地文件可改 | 不用于授权；后续签名 |
| hooks 阻塞新克隆 | 无 loom/无容器 | fail-open + 警告 |
| 超时残留 | `sh -c` 子进程 | 进程组 kill；日志流式 |
| 命令漂移 | `.loom.ci.toml` 与 Makefile 不一致 | 采纳已有 target；doctor 提示 |
| 生成配置过度自信 | 多栈/monorepo | v1 只做单栈根目录，其他提示手工 |
| `--no-verify` | 无法观测 | 不承诺记录；服务器兜底 |

## 4. churn

### 4.1 当前事实

- `messages` 只增不减；每一步把完整历史重发；
- `write` 的完整 `content` 在 assistant `tool_calls.arguments` 里，之后每一步都计入 input；
- 已有 `edit(old,new)`，但没有统一 diff/patch 工具；
- no-progress 只看 `mutated`，不看重写次数/token；
- usage 是 per-call，没有 step 维度；无法直接算“某次重写让后续每一步多花多少”。

### 4.2 步骤级上下文投影

native 自己拥有 `messages`，这是最可行的落点。建议在每次 `provider.complete` 前做一次确定性投影：

1. **稳定前缀不动**：`system` + 初始 packet 保持字节级稳定，保护 provider 前缀缓存。
2. **保留最近 K 个完整 turn**（例如 4–6 步），包括 assistant tool_calls 和对应 tool results。
3. **旧 assistant tool_calls 投影**：
   - `write(content=...)` → `{path, bytes, sha256, mode}`，去掉完整内容；
   - `edit(old,new)` → `{path, old_bytes, new_bytes, old_sha, new_sha}`，去掉全文；
   - `bash(cmd)` → 保留命令摘要与 artifact 路径，去掉长输出。
4. **旧 tool results 投影**：保留一行结果 + artifact 路径；不要保留完整日志。
5. **never orphan tool result**：裁剪时以完整 turn 为单位，或同时保留 `tool_call_id` 对应的 assistant 消息；否则 provider 会拒绝。
6. **当前工作集**：在投影后的历史后追加一个确定性的“worktree 状态”小节（变更文件、diffstat、最近 verify 失败），不放完整文件。
7. **硬预算**：用 `estimate_tokens` 或字节上限（例如 `max_history_tokens`）约束；超限时从最旧的 turn 开始丢，直到满足。
8. **失败包只保留最新**：旧的 verify 反馈被替换，不累积。
9. **不做模型摘要**：投影是确定性规则，不能为了省 token 再调一次 LLM。

投影的收益点不是“少存磁盘”，而是“旧全文不再进入后续每一步的 input”。

### 4.3 patch-first

- 已有 `edit`，优先强化它：`old` 必须唯一或 `replace_all`；错误信息提示“先 read 再 edit”；
- `write` 增加守卫：
  - 默认只允许创建不存在的文件；
  - 覆盖已存在文件需要 `mode="replace"`（或 `expected_sha256`）；
  - 没有 `mode` 的覆盖直接短错误拒绝，并提示 `edit`；
- 可选新增 `apply_patch`（unified diff）；v1 可以先不做，靠 `edit` + write 守卫拿到大部分收益；
- 工具描述和 system prompt 明确“优先 edit，不要整文件重写”；
- 外部 adapter 只能靠 prompt 和选型；不能从 Loom 侧投影它的历史。

### 4.4 token 归因

建议：

- `UsageRecord` 增加可选 `step`（或独立 `.loom/runs/<id>/logs/steps.jsonl`，避免改公共 schema）；如果改 `UsageRecord`，同步 `schemas/usage-record.v1.json`。
- 每次调用记录：`step`、`input`、`cached`、`output`、`tool_names`、`history_bytes`、`projected_bytes`、`write_paths`、`rewrite_count`。
- `logs/churn.json` 汇总：
  - `rewrite_output_tokens`：重复写同一文件的输出；
  - `history_carry_tokens`：旧版本在后续请求中的估算；
  - `avoided_input_tokens`：投影后少发的估算；
  - `wasted_tokens_est` / `wasted_cost_usd_est`，必须标 `estimated`；
  - `write_passes` / `churn_ratio` 只做诊断，不做主 KPI。
- `loom churn stats [--by model]` 第一屏 token/成本，第二屏才写次数。

### 4.5 成本感知重启

这是 P2，不应先做：

- 触发条件：同一文件重写 ≥ N 次，或 `wasted_tokens_est` 超阈值；
- 动作：重建 `messages`，只带 system + packet + worktree 摘要 + churn 摘要 + 最新失败；
- 限制：每 run 最多 1 次；共享原预算；必须记录 `task.churn` 事件或 churn 日志；
- 风险：丢失关键上下文导致质量下降；没有真实 A/B 前不要默认开启。

### 4.6 离线测试

- 脚本化 provider 连续 5 次写同一 8KB 文件；记录每次实际发送的 `messages` 字节数；无投影时应随步数增长，有投影时有界；
- 构造超长历史，断言裁剪后没有 orphan tool result；
- `write` 覆盖守卫：第二次覆盖被短错误拒绝；`edit` 成功；
- churn 统计用合成 usage 行，断言字段与 `estimated` 标记；
- acceptance 仍能通过；重启最多 1 次；
- 投影不改变 system/packet 前缀（字节比较）。

### 4.7 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 质量回退 | 投影掉模型仍需的上下文 | 保留最近 turn + worktree 摘要；A/B 后再默认 |
| 前缀缓存失效 | 投影改了前缀 | system/packet 字节稳定，只投影后半段 |
| tool_call 配对错误 | 裁剪产生 orphan | 按完整 turn 裁剪 + 测试 |
| 指标误导 | 估算当真实 | 标 `estimated`；以账单/usage 为准 |
| 外部 adapter 不可控 | 历史不在 Loom | 只做 watchdog/选型，不承诺投影 |
| 过早硬拦 | 模型换写法重试 | 投影优先；write 守卫只拒绝无 `mode` 覆盖 |

## 5. skills

可先做的部分（不依赖真实模型）：

- `loom skill scan`：扫描仓库/项目级目录，输出标签与证据文件；
- `loom skill add/show/verify`：项目级目录 + `skills.lock` + 内容哈希 + 静态检查；
- 按需加载：Context Compiler 只注入索引行；正文由 `loom skill show` 读取，受 4KB/8KB 预算；
- 静态检查：路径逃逸、symlink、大小上限、frontmatter、允许的工具、禁止的 shell/网络声明；
- CI 集成：`kind=skill` 只能加载 lock 内、通过静态检查的 skill，不能关闭 gate，不能定义任意命令。

需要修正的点：

- `skills.lock` 如果放 `.loom/`，同样不会进仓库；项目级 skill 的 lock 应 tracked（根目录 `skills.lock` 或明确 negation）。这与 `.loom.ci.toml` 是同一类问题。
- L2 评估/晋升依赖真实模型、固定任务集、账单；当前环境不具备，继续后置。
- 不做 embedding/联网目录。

粗略工作量：scan/catalog/lock/load 5–8 人日；L2 评估另计且当前不可做。

## 6. 横向契约检查清单

任何事件/状态/配置变更，按 `AGENTS.md` §4 同时完成：

1. `loom-core` 类型与穷举 `match`；
2. `schemas/*.json`（事件 enum、字段、`additionalProperties`）；
3. 文档：`doc/03` §11.2、`doc/10`（输出/退出码）、`doc/15`、本评估；
4. 至少一个单元/集成测试；
5. CLI `--help`、退出码、`--json` 纯度；
6. 旧数据兼容：新增字段用可选 + `serde(default)`；破坏性变更才升 v2。

建议新增两个防漂移测试：

- 读取 `schemas/event.v1.json` 的 `enum`，与 `EventType` 字符串集合比较；
- 读取 `schemas/receipt.v1.json` / `usage-record.v1.json` 的 `required`/properties，与 Rust `deny_unknown_fields` 类型做最小一致性检查（至少保证新增字段已写入 schema）。

`Config` 增加 `deny_unknown_fields` 是有意的行为变更：旧配置里的未知 section 会从“静默忽略”变成“明确报错”。这是好事，但要在 release note/`doctor` 里给出清晰错误。

## 7. 分阶段 MVP 与验收

### 阶段 A：attention 正确性（2–3 人日）

范围：`TaskStatus::NeedsInput`、事件、verify/dispatch 状态映射、claim 快照、退出码、测试。

验收：

- `needs_input` 经 verify 后仍为 `needs_input`，不产生 `task.failed`；
- 升级计数不增加；
- `blocked` / `budget_exceeded` 不再写成 `claim_not_done`；
- 重复 verify 不丢 claim；
- schema 漂移测试通过。

### 阶段 B：inbox 可见性（3–4 人日）

范围：`attention.*` 事件、`.loom/inbox.json` 缓存、`loom inbox list/show/ack/defer/resolve/--line/--check`、TTY footer、doctor 事项。

验收：

- TTY 下执行 `loom status`/`dispatch`/`verify` 后 stderr 出现一行待办；
- `--json` stdout 无 footer；
- 非 TTY/CI 默认不打印；
- `--check` 有 blocking 时退出 2；
- ack 不关闭事项；resolve 才关闭；
- footer 失败不影响原命令退出码。

### 阶段 C：question protocol（3–4 人日）

范围：native `ask` 工具、`questions.json` 校验、`.loom/answers/`、`loom answer`、Context Compiler 注入、assumptions。

验收：

- 脚本化 provider 调用 `ask` → exit 2 → inbox 可见 → answer → ready → 新 run 收到答案 → verify 通过；
- 多 blocking 问题未答完前不放行；
- 无 questions.json 时不猜问题；
- 回答不进入失败计数。

### 阶段 D：本地 CI 核心（5–7 人日）

范围：`loom-ci` crate、根目录 `.loom.ci.toml`、探测/生成、plan/run/doctor、runner/argv、日志预算、report。

验收：

- 在一个临时目标项目生成 `.loom.ci.toml`；Loom 自身 dogfood 使用 `./scripts/dev.sh` 另行验证；
- `loom ci run --profile pre-commit` 在格式错误时失败；
- `--json` 纯 JSON；日志落盘且摘要有界；
- doctor 能报缺容器引擎/runner；
- 不覆盖已有配置。

### 阶段 E：hooks + safe fix + report（3–5 人日）

范围：install-hooks、pre-commit/pre-push、`--fix`、diff 展示、report/attestation、verify-attest。

验收：

- hooks 幂等、非 Loom hook 拒绝、备份；
- `--fix` 不 stage/commit，改动可见；
- 同 tree attestation 通过，不同 tree 失败；
- `--no-verify` 不伪装成已记录；
- 服务器跳过**不在本阶段**。

### 阶段 F/G：churn（6–9 人日）

范围：步骤级投影、usage step、churn 统计、write 守卫、`edit` 强化；soft restart 可选。

验收：

- 5 次重写场景 input 有界；
- tool_call 配对正确；
- churn 字段完整且标 estimated；
- acceptance 不退化；
- 前缀字节稳定。

### 阶段 H：skills（5–8 人日）

范围：scan/catalog/lock/load/静态检查；L2 后置。

## 9. 需要确认的决策

1. **CI 配置位置**：确认改为根目录 `.loom.ci.toml`（tracked），而不是 `.loom/ci.toml`；并确认它是项目策略，不是运行时状态。
2. **attestation 授权**：确认 v1 不根据本地 attestation 跳过服务器 CI；只做证据/度量。
3. **verify 退出码**：是否接受 `0/1/2/3` 新语义（2 = needs_input/blocked，3 = budget）。
4. **`needs_input` 状态**：是否新增独立 `TaskStatus`，而不是复用 `blocked + code`。
5. **attempt 语义**：回答后的新 run 是否递增 attempt（建议递增，另记 `question_round`）。
6. **答案存储**：是否接受 `.loom/answers/<task_id>.jsonl` 作为本地内容存储，事件只存哈希/元数据。
7. **footer 默认**：TTY 默认开启，`LOOM_NO_INBOX=1` 关闭；非 TTY 默认关闭。
8. **patch-first 范围**：v1 只做 `edit` 强化 + `write` 守卫，还是同时做 `apply_patch`。
9. **CI 探测范围**：v1 只做 Rust 单栈 + `scripts/dev.sh`，其他栈后置。
10. **skills lock 位置**：确认项目级 lock 需要 tracked，不能放 `.loom/`。

---

## 10. 建议

**先把 A+B 提前到 CI 核心之前。** 理由：

- 它们修的是当前已经存在的正确性缺陷，不是新功能；
- 不依赖真实模型、容器或外部二进制；
- 一旦有了 inbox，后续 CI 失败、缺工具、需要审批都能立刻有出口；
- 成本可控（约 5–7 人日），风险低。

然后做 D（CI 核心），再做 C（questions），最后 F/G（churn）与 H（skills）。E 可以在 D 之后独立推进。

在用户确认 §9 的决策前，不进入代码实施。
