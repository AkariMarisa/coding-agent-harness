# Loom（暂定名）

> 面向软件设计、架构与开发的 token 高效 Agent Harness  
> 核心命题：**长任务，短上下文。**

> **v0.2 修订（2026-11-04）**：设计路线以 [08-设计路线-v0.2.md](08-设计路线-v0.2.md) 为准。  
> pi 从“主路径”降为“可选 adapter”；核心改为**独立 CLI/daemon + 进程级执行器契约**。  
> 01–04 仍然有效；05/06 中与 08 冲突的部分，以 08 为准。

## 1. 一句话

不重写 Agent Runtime，也不替换 Headroom。把 Loom 做成独立编排内核，agent 只是可替换的执行器：

- 状态从对话搬到 `.loom/` 文件；orchestrator 是唯一写者，worker 只写 `outbox/`；
- 实施切成独立、短生命周期的 worker 上下文；
- Agent 之间只传 **TaskSpec + 四行回执 + 文件引用**，不传 transcript；
- 用可执行 `verify` 作为唯一验收与升级信号；
- 执行器通过**进程 + 文件 + JSON + exit code**接入，不依赖任何插件 API；
- 网关层保持透明：Headroom 负责缓存/压缩，LiteLLM 负责模型路由。

目标不是“让模型更便宜”，而是**让每个 token 都花在有效工作上**。

## 2. 为什么现在需要它

前序实测（2026-11，单机 Headroom 快照）：

| 指标 | 实测 | 含义 |
|---|---:|---|
| 计费输入 / 真实新增 | 154.0M / 5.94M ≈ **25.9×** | 主因是历史重发，不是单价 |
| 1,322 次请求的压缩节省 | 1.17M tokens，**0.70%** | 压缩层已接近上限 |
| 前缀缓存折扣 | **$270.63** | 缓存收益远大于压缩 |
| `json_bloat` | **60.6M** | 工具结果按值回贴是最大浪费源 |
| `reread` | **5.67M** | 重复读取没有治理 |
| `by_model` | 仅 `gpt-6.1-sol` | 多模型从未真正接上 |
| `routing` | `null` | 没有任务级路由 |

三条结论：

1. **主战场是上下文生命周期与工具结果，不是压缩率。**
2. **多模型是二阶杠杆。** 先把长会话拆成短上下文，再谈便宜模型；否则便宜模型多跑几轮，`cost per successful task` 反而更高。
3. **最值得自研的只有薄编排层。** Runtime、沙箱、压缩、路由都有成熟组件，重写是纯损耗。

## 4. 八条设计结论

1. **状态外置**：`.loom/` 的事件日志与任务记录是唯一事实源，Markdown 只是生成视图，聊天只是控制通道。
2. **切片派发**：控制面只做规划、派发、验收；实施在独立 worktree + 独立上下文完成，结束即散。
3. **按引用交付**：跨边界只传路径、哈希、行号、diff、verify 日志路径，不传全文、不传原始 JSON/HTML、不传 transcript。
4. **验证驱动**：`verify` 是唯一验收与升级信号；不做模型自评“这题难”，不因自评升级。
5. **网关透明**：压缩与路由解耦；Headroom 保持 `cache` 模式，LiteLLM 放在 Headroom 之后；成本以 provider/LiteLLM 账单为准，Headroom stats 只作诊断。
6. **执行器可替换**：稳定契约是进程 + 文件 + JSON + exit code；不把任何 agent 的插件 API 作为核心依赖。
7. **工具端先减肥**：工具输出默认“摘要 + 地址 + artifact 引用”，单次/单 run 有硬上限；能在工具边界裁掉的 token，不留给 Headroom。检索 v1 不引入 embedding，见 [09](09-代码检索与知识库.md)。
8. **认证/计费分平面**：API 与订阅是两条 lane；订阅不假设能透明穿过 Headroom/LiteLLM，不静默回退到 API，见 [11](11-订阅额度与Agent-SDK.md)。

## 5. 非目标

- 不自研 Agent Runtime、沙箱、IDE、TUI。
- 不追求无人值守的全自动大任务；v1 允许人在异常点介入。
- 不以“压缩率”作为核心 KPI，而以“每个已验证任务的成本”作为核心 KPI。
- 不在 v1 做“LLM 自动判断任务复杂度并路由”；只做显式任务类别 → 模型层级映射。
- 不替换 pi / Codex / Headroom；它们是可替换的执行端与网关。
- 不做多租户、云端 SaaS、团队权限体系（后续可选）。

## 6. 需要搭建什么（最小集）

| 类别 | 内容 | 自研/复用 | 说明 |
|---|---|---|---|
| 状态协议 | `.loom/` 目录、事件日志、TaskSpec、Receipt、Decision | **自研** | 唯一事实源；orchestrator 单写者；见 03/08 |
| 编排器 | 任务图、调度、预算、升级、恢复 | **自研** | 确定性优先，薄层；见 02/08 |
| 上下文编译 | 每次调用重新编译有界上下文 | **自研** | token 收益的核心；见 08 §6 |
| 工具 I/O 预算 | 限额、结构化、落盘、去重 | **自研** | 优先于网关压缩；见 09 §8 |
| 验收器 | 执行 acceptance、收集证据、flaky 处理 | **自研** | 独立重跑，不信 worker 自述 |
| 账本 | 请求/任务/成本/指标 | **自研** | JSONL 事实源 + SQLite 索引；见 03/04 |
| Prompt 库 | orchestrator / worker / judgment / review | **自研** | 版本化，派发时渲染；见 07 |
| Runtime / 执行器 | goose / OpenCode / native / pi / Aider | **复用/可替换** | 进程级 adapter；首个接 goose |
| 压缩/缓存 | Headroom（cache） | **复用** | 不调参、不叠压缩器 |
| 路由 | LiteLLM（M3 起） | **复用** | 放在 Headroom 之后 |
| 隔离 | git worktree + 分支 | **复用** | 每任务一个；M4 并行 |
| 旁路 | Aider | **可选** | 只做 A/B / diff 生成 |

**不需要自研**：完整 Agent Runtime、沙箱、IDE/TUI、压缩器、provider 路由、多租户平台。  
**可选自研**：一个极简 native executor（bash/read/edit/search），用于完全掌控工具结果与上下文；它不是完整 runtime。

## 7. 最小闭环（M0，2–3 天）

1. `loom init` 建 `.loom/` 骨架，填入一个真实小任务的 goal/constraints。
2. `loom task add` 创建 1 个切片；人写验收命令。
3. `loom dispatch T-001 --adapter goose` 派发；worker 只写代码 + 最终消息，adapter 归一化回执。
4. `loom verify T-001` 独立重跑 acceptance；通过则记事件。
5. `loom status` 看板；`kill -9` 后 `loom resume` 能继续。
6. 记录一次 CPVT/TPVT/WPT；重复 10 次，再谈自动规划、路由、并行。

能跑通这个闭环，就已经拿到大部分 token 收益；`context compiler`、`router`、并行都是后面的放大器。
