# 01 问题、需求与验收

## 0. 文档目的

定义 Loom 要解决的问题、系统边界、功能/非功能需求与验收口径。后续架构、协议、路线图都以本文的 **FR/NFR 编号**为准，避免“讨论很热闹、落地无追踪”。

## 1. 用户与场景

### 1.1 用户画像

- 独立开发者或小团队技术负责人，同时负责软件设计、架构、前后端实现。
- 已有 specs 工作流，习惯把大任务交给 agent 连续推进。
- 对 token 成本和月度账单敏感，希望用低价模型承接部分实施工作。
- 当前环境以 Windows + PowerShell 为主，路径可能含空格；同时有 Linux/WSL 场景。
- 当前主力工具链：
  - `pi` 1.5.0 + `@tintinweb/pi-subagents` + `@narumitw/pi-goal` + `@casualjim/pi-headroom` + 其他上下文/记忆插件；
  - Codex CLI；
  - 常驻 `headroom proxy`，当前 `--mode cache`；
  - 主力模型 `gpt-6.1-sol`，reasoning level `medium`；
  - 尚未真正接入 `deepseek-v4-flash` 等 worker 模型。

### 1.2 典型工作流（As-Is）

1. 人写 specs / 设计文档。
2. 交给主 agent，开启 goal mode 连续跑。
3. agent 读文件、改代码、跑测试、修错误。
4. 人在同一个长会话里纠偏、补充上下文、重新验收。
5. 轮次越多，历史重发越贵；子 agent 之间靠自然语言转述，目标和验收逐渐漂移。

### 1.3 目标工作流（To-Be）

1. 人写 `GOAL.md`、`spec.md`、`design.md`，定义可执行验收。
2. orchestrator 拆任务图，为每个切片生成 `TaskSpec`。
3. worker 在独立 worktree / 独立上下文中执行，只读必要引用。
4. worker 跑 `verify`，输出四行回执；详情写 report 文件。
5. orchestrator 只读回执与 verify 结果，决定合并、重试、升级或找人。
6. 人只看异常、关键决策和最终验收，不再在长会话里“陪跑”。

## 3. 问题定义

### P1 长会话的二次方重发

每一轮都把 system prompt、工具 schema、全部历史重新发一遍。T 轮的总输入近似：

```
BilledInput(T) = T·(P + U) + (U + A)·T(T−1)/2
```

其中 `P` 是 system + tools，`U` 是任务内容，`A` 是每轮新增内容。T 越大，二次方项越主导。实测 25.9× 重发就是它的结果。

**影响**：主账单；且换便宜模型只能降低单价，不能消除重发面积。

### P2 工具结果膨胀

`json_bloat` 累计 60.6M，占全部 waste signal 的 83%。大量原始 JSON、日志、HTML、base64 直接进入 toolResult，而压缩器因 `size_floor` 跳过约 71% 的零散小结果。

**影响**：上下文被低价值内容占满，轮次增加，重发进一步放大。

### P3 重复读取

`reread` 累计 5.67M。典型坏习惯：先 `grep` 一次，再打开整个文件；同一文件在多个任务/多轮中反复读取。

**影响**：重复输入；worker 之间重复劳动。

### P4 子 agent 通信按值传递

主 agent 把父会话摘要、文件全文、上一轮对话粘给子 agent；子 agent 又把过程日志回贴给主 agent。每次派发和回收都重复计费。

**影响**：多 agent 不但没有省 token，反而引入额外通信开销。

### P5 目标与验收漂移

验收标准只存在于对话里；子 agent 靠自然语言理解“做完”；主 agent 靠子 agent 自述“完成了”。没有可执行 verify，也没有结构化回执。

**影响**：返工、重复沟通、假通过；`cost per successful task` 不可见。

### P6 单模型与无路由

`by_model` 只有 `gpt-6.1-sol`，`routing` 为 `null`。所有任务——包括机械实现、测试补齐、文档——都走前沿模型。

**影响**：单价浪费；也无法按任务风险选择模型。

### P7 压缩 ROI 错配

压缩只省 0.70%（$2.35），而前缀缓存折扣 $270.63。`--mode token` 会重写历史、破坏前缀稳定，用 $270 的缓存收益去换几分钱压缩，是负收益。

**影响**：继续调压缩参数是错误方向；应治理工具层与上下文生命周期。

### P8 缺少成本/质量闭环

没有 per-task、per-model、per-attempt 的账本；只有 lifetime 累计计数器；没有 `cost per successful task`，也没有“失败升级是否值得”的数据。

**影响**：无法判断优化是否有效，也无法决定是否该接便宜模型。

## 4. 根因

| 编号 | 根因 | 对应问题 |
|---|---|---|
| R1 | 上下文生命周期 = 会话生命周期 | P1、P3 |
| R2 | 状态存在对话里，而不是文件里 | P1、P5 |
| R3 | Agent 之间按值通信，而不是按引用 | P2、P4 |
| R4 | 优化目标错位：压峰值，而不是降面积 | P1、P7 |
| R5 | 验收不可执行，升级靠自评 | P5、P8 |
| R6 | 模型选择是全局的，不是任务级的 | P6 |
| R7 | 工具层没有结果治理（投影、截断、缓存、引用） | P2、P3 |

**一句话**：不是模型不够便宜，是上下文被当成了无限资源，状态被当成了聊天记录。

## 5. 目标与非目标

### 5.1 目标

| 编号 | 目标 | 度量 | 目标值（首期） |
|---|---|---|---|
| G1 | 降低每个已验证任务的成本 | `CPVT = 总成本 / 通过 verify 的任务数` | 相对基线 **−40%**（4 周内）；−60%（8 周内） |
| G2 | 主会话上下文有界 | orchestrator 输入 tokens | **≤ 30k**，且不随任务总时长增长 |
| G3 | 降低 Agent 间通信开销 | `handoff_overhead = handoff tokens / 总 tokens` | **≤ 5%** |
| G4 | 保住前缀缓存收益 | `cache_hit = cached_input / input` | **≥ 75%**，且不下降超过 10pp |
| G5 | 验收可执行、可审计 | 有 verify 证据的合并比例 | **100%**；0 个未验证合并 |
| G6 | 让 worker 模型承接合适任务 | worker tier 完成的实施任务占比 | P2 后 **≥ 50%**，且 CPVT 更低、质量不退化 |
| G7 | 降低每个已验证任务的 token 用量 | `tokens_per_verified_task = billed_input / verified_tasks` | 相对基线 **−50%**（8 周内） |

> G1 是成本主 KPI，G7 是 token 主 KPI。两者一起看：如果 token 降了但成本没降，说明模型/缓存用错了；如果成本降了但 token 没降，说明只是换了便宜模型，浪费仍在。

### 5.2 非目标

| 编号 | 非目标 | 原因 |
|---|---|---|
| N1 | 自研 Agent Runtime、沙箱、编辑器、TUI | 成熟组件已足够；重写是纯损耗 |
| N2 | 无人值守的全自动大任务 | 没有 verify 兜底时，自动化只会放大错误 |
| N3 | 以“压缩率”或“token 单价”作为核心 KPI | 压缩省 0.70%，缓存省 $270；单价不等于 CPVT |
| N4 | v1 做 LLM 自动复杂度路由 | 不可解释、易漂移；先用显式任务类别映射 |
| N5 | 替换 pi / Codex / Headroom | 它们是可替换执行端与网关，不是要重写的对象 |
| N6 | 多租户、云端 SaaS、团队权限 | 首期是单机/单用户工作台 |
| N7 | 让所有任务都走便宜模型 | 便宜模型只放在“短、可验证、可重跑”的切片上 |

## 6. 用户故事

### US1 长任务续跑

作为开发者，我把 `GOAL.md` 和一个大任务交给 orchestrator；它拆成任务图并逐片派发。即使跑了几十片，主会话上下文仍然只有目标、任务图摘要和最近几条回执。

**验收**：连续完成 10 个切片后，orchestrator 输入 ≤ 30k；不需要把 worker transcript 读回主会话。

### US2 多模型各司其职

作为开发者，我让前沿模型做设计、拆解、判断；让 worker 模型做实现、补测试、机械重构。每个任务在 `TaskSpec.tier` 里显式指定层级，而不是让模型自评。

**验收**：`by_model` 中同时出现 frontier 与 worker；worker 任务的 verify 通过率不低于基线的 95%；CPVT 下降。

### US3 子 agent 目标与验收对齐

作为开发者，每个 worker 拿到的 TaskSpec 都包含：输入引用、允许修改的路径、验收命令、预算、输出契约。worker 之间不直接聊天；接口契约冻结在 `contracts/`。

**验收**：同一任务重复派发时，两个 worker 的验收标准完全一致；无“口头补充需求”。

### US4 成本可见

作为开发者，我能看到每个任务、每次尝试、每个模型的输入/缓存/输出/成本，以及失败重试和升级的成本。

**验收**：账本可按 `run_id / task_id / tier / model / attempt` 聚合；与 provider 账单误差 < 5%。

### US5 失败可恢复

作为开发者，worker 崩溃、超预算、verify 失败时，系统能保留现场（worktree、日志、回执），从断点恢复或升级，而不是重跑整个长会话。

**验收**：kill -9 后 5 分钟内可恢复；恢复不重复已通过的任务。

### US6 异常才找人

作为开发者，我只在 `ambiguous_spec`、`conflict`、连续 verify 失败、预算超限时被呼叫；正常路径不需要我陪跑。

**验收**：人工介入率（human touch rate）≤ 30%（首期），且每次介入都有明确的待决问题与证据包。

### FR-01 状态外置与单一事实源

**需求**：目标、规格、设计、任务图、进度、决策、回执、报告必须落在 `.agent/` 下的文件里；聊天不作为状态存储。

**验收**：
- 新会话只读 `.agent/` 即可恢复任务，不依赖历史 transcript。
- 每个文件有 schema 版本与单一写者。
- `GOAL.md`、`spec.md`、`design.md`、`PROGRESS.md`、`DECISION.md`、`tasks.json` 缺一不可。

### FR-02 任务切片与任务图

**需求**：大任务必须拆成可独立验证的切片；切片之间有显式依赖，形成 DAG。

**验收**：
- 每个 TaskSpec 有 `depends_on`、`inputs`、`allowed_paths`、`acceptance`、`budget`。
- 切片粒度默认 1–4 小时、≤ 8 个文件；超过则必须再拆。
- 任务图可视化/可查询，能列出 ready / running / blocked。

### FR-03 类型化派发（TaskSpec）

**需求**：orchestrator 只能通过结构化 TaskSpec 派发；禁止自然语言“顺便把 X 也做了”。

**验收**：
- TaskSpec 通过 JSON Schema 校验；未知字段拒绝。
- `tier` 必填；`acceptance` 至少 1 条；`budget` 必填。
- 派发内容 ≤ 2k tokens（不含引用文件本身）。

### FR-04 四行回执

**需求**：worker 结束时只输出固定四行回执；详情写 report 文件。

**验收**：
- 四行分别为 `status / branch / verify / report`；解析器拒绝多余行。
- 回执 ≤ 100 tokens；不含 diff、文件内容、日志、思维链。
- 状态枚举：`done / blocked / needs_input / failed / budget_exceeded`。

### FR-05 按引用交付

**需求**：跨边界只传路径、sha256、行号、diff、日志路径；不传全文、不传原始 JSON/HTML/base64、不传 transcript。

**验收**：
- TaskSpec 的 `inputs` 是引用列表，不是内容。
- Receipt 的 `artifacts` 是路径 + 哈希 + 字节数。
- 工具结果默认返回“已写入 <path>，N 字节”，而不是回贴内容。

### FR-06 禁止 transcript 中继 / worker 网状通信

**需求**：worker 之间不直接通信；所有协调经 orchestrator 与共享状态文件。接口契约在 `contracts/` 冻结，变更走设计任务。

**验收**：
- 代码/配置中不存在 worker → worker 的消息通道。
- 两个 worker 对同一接口的实现以 `contracts/` 为准，不靠聊天对齐。
- orchestrator 不把 worker transcript 注入另一个 worker。

### FR-07 Verify 契约

**需求**：每个实施任务必须有可执行、非交互、可重复的验收命令；verify 结果是唯一通过依据。

**验收**：
- `acceptance[]` 包含 `cmd / expect_exit / timeout_s`。
- 命令在 worktree 根目录执行，输出写日志文件，回执只带路径。
- 退出码 0 = pass；非 0 = fail；超时 = fail。
- 没有 verify 的代码任务不可派发；探索任务用“产物 + 引用”验收，且不能合并代码。

### FR-08 失败升级一次

**需求**：verify 失败先同层重试一次；再失败升级到 frontier `judgment`；judgment 输出 `fix_plan / split / reject / human`；每个任务最多升级一次。

**验收**：
- 升级只由 verify 失败、`ambiguous_spec`、`conflict` 触发，不由模型自评触发。
- 升级证据包包含：TaskSpec、Receipt、diff、verify 日志、相关决策、文件引用。
- 升级后仍失败 → `human`，不无限循环。

### FR-09 预算与熔断

**需求**：每个任务、每个 run 都有 token / 成本 / 步数 / 墙钟上限；超限立即停止并保留现场。

**验收**：
- 超限回执 `status=budget_exceeded`；不自动重试。
- run 级别有总预算与“无进展轮次”熔断。
- 预算检查在派发前（估算）与执行中（usage 流）双重生效。

### FR-10 并行隔离与合并队列

**需求**：可并行的任务在独立 git worktree / 分支执行；同一路径同一时间只允许一个写者；合并串行。

**验收**：
- 每个任务有 `workspace.branch` 与 `allowed_paths`。
- 路径锁有 owner、lease、TTL；冲突时任务进入 `blocked`，不强行覆盖。
- 合并前必须通过 verify；合并后跑一次集成 verify。

### FR-11 显式模型分层路由

**需求**：任务通过 `tier` 显式选择模型层级；网关按 alias 路由到具体 provider/model；禁止隐式升级。

**验收**：
- 层级至少 `frontier` / `worker` 两档；alias 在 LiteLLM 配置中定义。
- 未知 tier 拒绝派发；provider 失败只允许同层 fallback。
- `by_model` 能看到两档模型；`routing` 不再为空。

### FR-12 网关顺序与压缩归属唯一

**需求**：请求路径为 `agent → Headroom → LiteLLM → provider`；同一请求只允许一个压缩归属；压缩模式保持进程级 `cache`，不做 per-request 切换。

**验收**：
- Headroom 在下游 URL 指向 LiteLLM；agent 配置不需要知道 provider。
- pi 插件压缩与 LiteLLM guardrail 不叠加；Codex 路径不启用 pi 插件。
- 不启用以 `model` 字段切 `token/cache` 的设计；如未来需要两种模式，只按客户端/端口在进程边界分。

### FR-13 缓存友好调度

**需求**：主会话前缀稳定、append-only；不中途改 system prompt、不重排工具、不中途换模型；批量合并变更。

**验收**：
- orchestrator 的 system + tools + goal 位于前缀，且 run 内不变。
- 回执只追加；旧回执折叠为摘要，不修改原文。
- `cache_hit ≥ 75%`；下降超过 10pp 触发告警与回滚。

### FR-14 成本账本与归因

**需求**：每次请求记录 run / task / attempt / tier / model / input / cached / output / reasoning / cost；以 provider 账单或 LiteLLM 日志为准。

**验收**：
- 账本可按任意维度聚合；无 `task_id` 的请求进入 `unattributed` 并告警。
- 估算成本与 provider 账单误差 < 5%。
- Headroom stats 只作诊断，不作为账单依据。

### FR-15 指标、A/B 与看板

**需求**：提供 CPVT、resend ratio、cache hit、handoff overhead、context amplification、first-pass verify、escalation rate 等指标；支持同任务集 A/B。

**验收**：
- 每次 run 结束生成指标快照。
- A/B 使用同一任务集、同一基线、配对比较；不使用 lifetime 累计值直接对比。
- 质量 guardrail（defect escape / rework）与成本一起看。

### FR-16 可恢复、可审计、可回放

**需求**：run 的事件、任务状态、回执、verify 日志、账本可回放；崩溃后能从最后一个稳定点恢复。

**验收**：
- `events.jsonl` 追加写；每个状态变更都有事件。
- `loom resume` 不重复已通过任务；worktree 可重建。
- 任意历史任务可回答“谁在什么上下文、用什么模型、跑了什么命令、结果如何”。

### FR-17 权限、密钥与沙箱

**需求**：worker 只能改 `allowed_paths`；命令有 allowlist / 超时；密钥不进入状态文件；仓库内容视为不可信输入。

**验收**：
- 密钥只从环境变量/密钥管理器读取；日志脱敏。
- 默认禁止网络（除非 TaskSpec 显式允许）；危险命令拒绝执行。
- 每个任务有审计记录：命令、路径、退出码、耗时。

### FR-18 可扩展与版本兼容

**需求**：Runtime、模型、verify 类型、压缩器都可替换；schema 与适配器有版本号；升级有兼容窗口。

**验收**：
- Runtime Adapter 接口稳定；替换 pi/Codex 不改 orchestrator。
- `.agent/env.lock` 记录 pi / codex / headroom / litellm / 插件版本。
- schema 迁移脚本可用；至少兼容一个 minor 版本。

## 9. 约束与假设

### 9.1 环境约束

- 主力环境 Windows + PowerShell，路径可能含空格，所有脚本必须加引号并处理 UTF-8。
- Headroom 常驻进程已存在，pi 插件在 agent 端先压缩，再由 proxy 存储原文/转发；不要把“拉起 proxy”写进插件生命周期。
- 当前只有单 GPT 在用；多模型是后续阶段，不能阻塞首期止血。
- 网络可能经代理；provider 兼容性与流式/工具调用需要逐项验证。

### 9.2 技术假设（需本机核实）

| 编号 | 假设 | 核实方式 |
|---|---|---|
| A1 | pi subagent 支持按任务指定模型并回传 usage | 查文档/实测 |
| A2 | Codex 支持 subagent model override | 查 `--version` / 配置 |
| A3 | Headroom 的 `--openai-api-url` / `--anthropic-api-url` 可指向 LiteLLM | `headroom proxy --help` + 联调 |
| A4 | LiteLLM 同时支持 OpenAI Chat/Responses 与 Anthropic Messages | 兼容性矩阵 |
| A5 | LiteLLM 能透传 tool calls、流式、usage（含 cached tokens） | 兼容性矩阵 |
| A6 | git worktree 在 Windows 路径/长路径下可用 | 实测 |
| A7 | worker 模型在短切片 + verify 下通过率可接受 | 10–20 任务 A/B |
| A8 | Headroom stats 的 `by_model` 能看到 alias 或真实模型 | 采样 |

### 9.3 硬约束

- 不把 provider 密钥写入 `.agent/`、prompt、日志。
- 不让 worker 执行未经 allowlist 的任意命令。
- 不在同一个请求上叠加两个独立压缩器。
- 不以模型自评作为升级依据。
- 不把 worker transcript 读回 orchestrator。

## 10. 验收总则

1. **每个 FR 的验收必须可执行或可观测**，不能只写“支持”。
2. **成本主 KPI 是 CPVT，token 主 KPI 是 TPVT**：前者是 `总成本 / 通过 verify 的任务数`，后者是 `计费输入 / 通过 verify 的任务数`。token 单价、压缩率只是解释变量。
3. **A/B 必须同任务集、同基线、配对比较**；不能用 lifetime 累计值直接对比。
4. **质量 guardrail 优先**：如果 CPVT 下降但 defect escape / rework 上升，视为失败。
5. **成本口径优先级**：provider 账单 > LiteLLM 日志 > Runtime usage > Headroom stats。
6. **任何阶段都要能回滚**：保留上一版配置、prompt、schema 与可用的直接 provider 路径。

## 11. 术语表

| 术语 | 含义 |
|---|---|
| Orchestrator | 编排器；维护目标/任务图、派发、验收、升级，上下文恒定很小 |
| Worker | 执行单个切片的 agent；独立 worktree + 独立上下文 |
| Slice / Task | 可独立验证的最小工作单元 |
| TaskSpec | 结构化派发契约 |
| Receipt | 四行回执；跨边界唯一允许的“结果摘要” |
| Verify | 可执行的验收命令与证据 |
| Handoff | 跨 agent/跨上下文传递；只允许按引用 |
| Frontier | 前沿模型层级；设计、判断、关键 review |
| Worker tier | 低价/中价模型层级；短、可验证、可重跑的实施 |
| CPVT | Cost per Verified Task，每个已验证任务的成本 |
| Resend ratio | 计费输入中历史重发的比例 |
| Handoff overhead | 通信 token 占总 token 比例 |
| `.agent/` | 文件化状态目录；唯一事实源 |
