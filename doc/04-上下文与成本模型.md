# 04 上下文与成本模型

## 1. 为什么 token 会爆

### 1.1 基本公式

设：

- `P` = system prompt + 工具 schema（每轮都发）
- `U` = 用户任务/上下文（每轮都发）
- `A` = 每轮新增的 assistant/tool 内容
- `T` = 轮次

朴素长会话的计费输入近似：

```
BilledInput(T) = Σ_{t=1..T} [P + U + (t−1)·(U + A)]
              = T·(P + U) + (U + A)·T(T−1)/2
```

第一项是线性，第二项是**二次方**。T 越大，二次方项越主导。

### 1.2 量级示例

假设 `P+U = 20k`，`U+A = 5k`：

| 轮次 T | 线性项 | 二次方项 | 总输入 | 相对 T=10 |
|---:|---:|---:|---:|---:|
| 10 | 200k | 225k | 425k | 1× |
| 30 | 600k | 2.18M | 2.78M | 6.5× |
| 100 | 2.0M | 24.75M | 26.75M | 63× |

实测 154.0M / 5.94M ≈ **25.9×** 重发，量级一致。

### 1.3 切片为什么有效

把一个大任务拆成：

- 1 个 orchestrator 会话，`T_main` 小（只读回执/决策）；
- N 个 worker，每个 `T_worker` 小（3–8 轮），上下文独立。

总输入从：

```
T_total·(P+U) + (U+A)·T_total(T_total−1)/2
```

变成：

```
T_main·(P_main+U_main) + (U_main+A_main)·T_main(T_main−1)/2
+ Σ_i [T_i·(P_i+U_i) + (U_i+A_i)·T_i(T_i−1)/2]
```

关键在于：**worker 之间不共享历史**，所以没有跨 worker 的二次方项。每个 worker 的 `T_i` 很小，二次方项被压扁；orchestrator 的 `T_main` 也小，因为只追加四行回执。

> 这不是“把任务拆成多对话”那么简单。会话仍是一个长任务，但**上下文是短生命周期的**。

## 2. 浪费分类

| 类别 | 典型信号 | 实测/量级 | 机制 | 对策 | 归属 |
|---|---|---|---|---|---|
| 历史重发 | billed/unique 25.9× | 主账单 | 长会话每轮重发 | 短上下文 + 文件状态 | C1/C3 |
| 工具结果膨胀 | `json_bloat` 60.6M | 83% waste | 原始 JSON/日志进 toolResult | 引用 + 投影 + 截断 | C2/C12 |
| 重复读取 | `reread` 5.67M | 累计 | grep 后再整文件读 | 读缓存 + 批量 + range | C2 |
| 标记噪声 | `html_noise` 4.05M | 累计 | 网页/日志原样进上下文 | 清洗/摘要/引用 | C2 |
| base64 | `base64` 1.18M | 累计 | 图片/附件内联 | 存文件 + 引用 | C2 |
| 空白 | `whitespace` 1.50M | 累计 | 格式化文本 | 压缩/规范化 | C9 |
| Agent 通信 | 未单独计量 | 可能 5–20% | transcript 转述 | 四行回执 + 引用 | C5 |
| 过度压缩 | 压缩省 0.70% | $2.35 | 有损压缩破坏缓存 | 保持 cache | C9 |
| 错误分层 | 仅 sol | 单价浪费 | 所有任务走 frontier | 显式 tier | C8 |
| 返工 | 未计量 | 隐性 | verify 不足/规格漂移 | spec-tests + verify | C6 |
| 重复劳动 | 未计量 | 隐性 | 并行任务重叠 | 任务图去重 + 锁 | C4/C10 |
| 无效重试 | 未计量 | 隐性 | 无分类重试 | 错误分类 + 熔断 | C1/C7 |

### 2.1 优先级

按“可攻击性 × 影响面”排序：

1. **历史重发**（最大、最确定）→ 切片 + 状态外置。
2. **工具结果膨胀**（最大单项 waste signal）→ 按引用 + 投影。
3. **Agent 通信**（多 agent 场景新增）→ 四行回执 + 禁止 transcript。
4. **重复读取**（易治理）→ 读缓存 + 批量。
5. **错误分层**（二阶）→ 路由。
6. **压缩参数**（最低 ROI）→ 不动。

## 3. 上下文预算

### 3.1 预算表

| 区域 | 上限 | 内容 | 超限策略 |
|---|---:|---|---|
| Orchestrator system | 8k | 角色、规则、协议、工具 | 固定，不随任务改 |
| Orchestrator goal | 2k | GOAL 摘要 + 验收 | 固定 |
| Orchestrator task graph | 6k | 任务索引 + 状态 | 折叠已完成 |
| Orchestrator receipts | 4k | 最近 3–5 条四行回执 | 旧回执归档 |
| Orchestrator decisions | 6k | 决策索引 + 一句话 | 只保留 accepted |
| Orchestrator reserve | 4k | 当前决策/异常 | — |
| **合计** | **30k** | | |
| Worker spec | 2k | TaskSpec | 拆任务 |
| Worker refs | 40k | must_read + 按需读 | 减引用/拆任务 |
| Worker tool results | 50k | 投影/截断/引用 | 写文件 |
| Worker output | 10k | 代码/diff/命令 | 分批 |
| Worker reserve | 18k | 错误/重试 | — |
| **合计** | **120k** | | |
| Judgment evidence | 40k | 失败日志片段 + diff + 决策 | 截断 + 路径 |
| Report | 无上限 | 人读详情 | orchestrator 不加载 |

> 这些是**预算**，不是目标。能更小更好；超过 80% 就应停止并写状态，而不是静默压缩。

### 3.2 折叠策略

- orchestrator 只保留最近 3–5 条回执；更早的折叠成“任务 ID + 状态 + 证据路径”一行。
- 决策只保留 accepted + 被取代的索引；详情在 `DECISION.md`。
- 任务图只保留未完成 + 最近完成；归档任务进 `runs/`。
- worker 不折叠历史；上下文超限就停止，写 `needs_input` 或 `budget_exceeded`。
- 禁止“静默自动摘要”替换原始证据；摘要只能附加，不能覆盖。

### 3.3 读取策略

- 先 `grep` 定位，再按 `range` 读；不要先整文件读。
- 一次批量读多个相关文件；不要“读一个、想一下、再读一个”。
- 同一文件在任务内只读一次；需要再看用行号/符号。
- 大文件只读签名/类型/接口；实现细节按需。
- 禁止 `cat` 整个仓库/整个日志；用 `head/tail/grep` + 引用。
- 工具结果超过阈值（如 4k tokens）→ 写文件，返回路径 + 摘要 + 行号。

## 4. 缓存策略

### 4.1 前缀顺序

```
[system prompt] → [tool schemas] → [GOAL 摘要] → [任务图摘要] → [回执/决策追加]
```

- 越稳定越靠前；越易变越靠后。
- run 内不改 system / tools / goal；任务图只追加/折叠，不重排。
- 不在前缀里放时间戳、随机 ID、动态日期。
- 工具 schema 顺序固定；不要按请求重排。

### 4.2 缓存不变量

| 不变量 | 违反后果 |
|---|---|
| run 内 system prompt 不变 | 前缀缓存全失效 |
| 工具列表/顺序不变 | 缓存键变化 |
| 模型不变 | 缓存按模型隔离 |
| 消息只追加，不编辑早期消息 | 缓存前缀失效 |
| 温度/参数稳定 | 部分 provider 缓存键包含参数 |
| 不在开头注入动态上下文 | 每轮都 miss |

### 4.3 并行与缓存

- 主会话串行；worker 并行不影响主会话前缀。
- 每个 worker 有自己的前缀；不要把所有 worker 的 system 改成不同版本。
- 同一模型并发过高会限流；用 LiteLLM 队列/退避，不要让 worker 自己重试风暴。
- **并发上限先按 2 控制**；3 个以上必须同时满足“文件所有权完全不重叠 + A/B 证明 `WPT`/`CPVT` 不退化”。外部实测多 agent 约为单 agent 的 4–15× token，fan-out 常见 2.6–5.9×，且不一定更快；我们的实测也出现过并发下降、整体变慢。
- 并行 task 的写集必须不相交；`schema`、锁文件、迁移、依赖清单等共享文件串行或由 orchestrator 合并。
- 子代理完成时通知一次，不要轮询进度。

### 4.4 指标

- `cache_hit = cached_input_tokens / input_tokens`
- 目标 ≥ 75%；下降 > 10pp 告警。
- 不要把 cached token 当免费；按 cached 价格计。
- 缓存收益单独记，不与压缩节省相加。

## 5. 压缩策略

### 5.1 当前结论

保持 Headroom `mode=cache`，不动压缩参数。原因：

- 压缩只省 0.70%（$2.35），缓存折扣 $270.63；
- `token` 模式会重写历史、破坏前缀稳定；
- `size_floor` 跳过了约 71% 的小结果，调低阈值收益有限且会增加延迟/风险；
- 压缩只对“全价新增输入”有效；改写已缓存前缀会触发全量 prefill，可能越压越贵；
- 真正的浪费在工具层与历史重发，不在 live-zone 压缩率。

### 5.2 ROI 公式

压缩是否值得，不看压缩率，看：

```
CompressionSaving ≈ tokens_removed × p_in × (1 − cache_hit)
CacheLoss        ≈ prefix_tokens × p_in × Δcache_hit
Net              = CompressionSaving − CacheLoss − 额外延迟/失败成本
```

只有 `Net > 0` 且可持续时才调压缩。当前 `CacheLoss` 远大于 `CompressionSaving`。

### 5.3 压缩归属

| 路径 | 压缩器 | 规则 |
|---|---|---|
| pi + 插件 | pi-headroom 插件 + Headroom proxy | 视为一条受控链路；不再叠 LiteLLM guardrail |
| Codex | Headroom proxy | 不启用 pi 插件 |
| Aider | Headroom proxy（cache） | 不依赖 retrieve |
| Claude Code | Headroom proxy（cache） | 不再叠其他压缩器 |

**硬规则**：同一请求只能有一个“压缩决策者”。多个压缩器叠加会导致：

- 原文丢失、无法 retrieve；
- 前缀变化、缓存失效；
- 调试困难、责任不清。

### 5.4 什么时候可以动

满足全部条件才考虑：

1. 缓存命中稳定 ≥ 75%；
2. 工具层治理已完成（引用/投影/截断）；
3. 有 A/B 证明 CPVT 下降；
4. 有 retrieve/回滚方案；
5. 只在非关键路径 canary。

否则：**不动**。

## 6. 路由策略

### 6.1 两档模型

| tier | 任务 | 模型示例 | 上下文 | 调用频率 |
|---|---|---|---|---|
| frontier | 目标拆解、设计、judgment、关键 review | gpt-6.1-sol @ medium | 小（≤30k） | 低 |
| worker | survey、spec-tests、implement、机械重构、文档 | DeepSeek / Kimi / MiniMax / MiMo（先 1 主力 + 1 fallback） | 中（≤120k） | 高 |

> **前期约束**：API key 可覆盖 GPT 与多家国产模型。先用 GPT `frontier` + DeepSeek `worker` 验证 tier 路由；Kimi/MiniMax/MiMo 等按 A/B 逐步接入。订阅 lane 后置，不影响 M0–M3。

### 6.2 任务类别矩阵

| 任务 | tier | 理由 | 例外 |
|---|---|---|---|
| 目标/范围拆解 | frontier | 需要判断与取舍 | — |
| 架构/接口契约 | frontier | 错误代价高 | 可由 worker 起草，frontier 审 |
| 测试规格 | worker | 可验证、可重跑 | 安全/支付关键由 frontier 审 |
| 单模块实现 | worker | 短、可验证 | 跨模块/并发/安全关键 → frontier |
| 机械重构/格式化 | worker | 低判断 | — |
| 文档 | worker | 低风险 | 对外契约文档由 frontier 审 |
| verify 失败 judgment | frontier | 需要诊断 | — |
| 最终 review | frontier | 把关 | 低风险可抽样 |

**spec 是决策工作**：实现者从全新上下文启动，简报里没写的就要重新发现或靠猜；spec 错了，错误会乘以 task 数量。因此：

- spec / 接口契约 / 验收标准由 frontier 定稿；便宜模型只起草候选，必须过 deterministic verify 或人签核；
- 长上下文模型适合“全仓扫描 → 结构化候选”，不直接产出最终 spec；
- 扫描结果不进每轮上下文；只把编号化、短、稳定的 AC 放进 TaskSpec；
- AC 至少覆盖正常路径、失败路径、权限/空状态/重复请求、非目标保护；
- 验收证据必须能映射回 AC 编号。

### 6.3 路由护栏

- 没有 deterministic verify 的任务，不允许走 worker。
- 规格不清（`ambiguous_spec`）的任务，不允许走 worker。
- 跨模块/安全/并发/数据迁移，默认 frontier。
- worker 失败两次 → frontier judgment；不允许 worker 自行“升级”。
- 同层 fallback 可以；跨层升级必须经过 judgment。
- 每次路由变更记录到 `DECISION.md`。

### 6.4 收益与风险

| 收益 | 风险 | 验证 |
|---|---|---|
| 单价下降 | 便宜模型多轮/返工，CPVT 反而升 | 同任务集 A/B |
| 并行便宜 worker | 质量下降、review 成本上升 | first-pass verify + defect escape |
| 降低 frontier 上下文 | 拆解质量下降 | 任务图质量/返工率 |

> 结论：多模型不是“接上就省”。必须用 CPVT + 质量 guardrail 验证；如果 worker 需要 >2× 轮次或返工率明显上升，就不值得。

### 6.5 模型能力位（不写死模型名）

模型迭代快，强制 thinking、`reasoning_content` 回传、模型 ID 下线、缓存价时段变化都会让“写死模型名”的配置迅速腐烂。选型记录能力位：

| 能力位 | 取值 | 影响 |
|---|---|---|
| `tier` | `frontier` / `worker` | 任务类别 → 层级路由；先从两档开始 |
| `thinking_mode` | `off` / `optional` / `forced` | 强制 thinking 的模型不放进多轮工具链，除非有透传通道 |
| `reasoning_passthrough` | `required` / `optional` | 需要原样回传 `reasoning_content`，压缩器不能改写 |
| `wire` | `chat` / `responses` / `messages` | 决定网关、压缩器、计费是否覆盖 |
| `context_window` / `max_output` | 数值 | 切片与预算 |
| `input_usd_per_mtok` / `cached_input_usd_per_mtok` / `cache_write_usd_per_mtok` / `output_usd_per_mtok` | 数值 | 真实成本主项；缓存价与列表单价分开记 |
| `model_id` | 固定版本或日期 | 变更必须重跑验收基线 |
| `pricing_version` | 字符串 | 价格来源版本，对账时可追溯 |

规则：

- 执行层优先选**能关 thinking、协议干净、可无状态一次调用**的模型；
- 先 **1 主力 + 1 fallback**，按 task 类型 A/B 后再扩；不一次接四家；
- 别名必须映射到真实模型 + 能力位，账本同时记 alias 与真实模型；
- 配置落位与检查命令见 [06](06-技术选型.md) §5.6；价格未知时留空，不用猜测值填账本。

## 7. 记账与指标

### 7.1 定义

| 指标 | 公式 | 说明 |
|---|---|---|
| `billed_input` | Σ input_tokens | 计费输入 |
| `cached_input` | Σ cached_input_tokens | 缓存命中部分 |
| `unique_new` | 新内容 tokens（估算/账单差） | 真实新增 |
| `resend_ratio` | `(billed_input − unique_new) / billed_input` | 历史重发比例 |
| `context_amplification` | `billed_input / unique_new` | 放大倍数 |
| `cache_hit` | `cached_input / billed_input` | 缓存命中率 |
| `handoff_overhead` | `handoff_tokens / total_tokens` | 通信开销 |
| `CPVT` | `total_cost / verified_tasks` | **成本主 KPI** |
| `TPVT` | `billed_input / verified_tasks` | **token 主 KPI** |
| `first_pass_verify` | 首次 verify 通过任务 / 总任务 | 质量 |
| `escalation_rate` | 升级任务 / 总任务 | 升级滥用 |
| `budget_exceeded_rate` | 超预算任务 / 总任务 | 预算合理性 |
| `human_touch_rate` | 人工介入任务 / 总任务 | 自动化程度 |
| `rework_rate` | 返工任务 / 总任务 | 规格/验收质量 |

### 7.2 目标

| 指标 | 基线 | 首期目标 | 长期目标 |
|---|---:|---:|---:|
| CPVT | 待测 | −40% | −60% |
| TPVT | 待测 | −50% | −60% |
| resend_ratio | ~96% | −20pp | −40pp |
| cache_hit | ~75% | ≥75% | ≥80% |
| handoff_overhead | 待测 | ≤5% | ≤3% |
| first_pass_verify | 待测 | 不下降 | ≥70% |
| escalation_rate | 待测 | ≤20% | ≤10% |
| human_touch_rate | 待测 | ≤30% | ≤15% |

> 基线必须用同一任务集、同一口径重新采样；不要直接套用本文的历史快照。

### 7.3 成本口径

优先级：

```
provider 账单 > LiteLLM 日志 > Runtime usage > Headroom stats
```

- `with_headroom_usd` 只用于单次快照对比；不要与 lifetime 累计混用。
- `provider_cache_discount_usd` 单独记；不要与压缩节省相加。
- `WasteSignals` 是累计检测量，不是“已节省”；A/B 只看 `Δ值 / Δrequests` 的增速。
- `reread_compressed` 的归因未落地，不能作为压缩失效判据；`share_of_saved_percent` 可能因分母错误而失真，禁用。
- 客户端归属看 `agent_usage.agents[]` 的 `source`；`requests.by_client` 可能为空。
- 每次 run 生成 `cost_report.json`：按 tier/model/task 聚合。
- 每月与 provider 账单对账；误差 >5% 要查归因。

### 7.4 A/B 设计

1. 选 10–20 个同类型任务，固定 spec/verify。
2. 随机分两组：baseline / treatment；或同任务跑两遍（顺序随机）。
3. 记录 CPVT、first-pass verify、escalation、human touch、defect escape。
4. 用配对比较（同任务差值），不要比 lifetime 累计。
5. 至少 1 周或 20 个任务；结论写入 `DECISION.md`。
6. 如果 treatment 的 CPVT 下降但质量下降，视为失败。

### 7.5 成本模型示例

假设（仅示例）：

- frontier：输入 $10/M，输出 $30/M；
- worker：输入 $1/M，输出 $2/M；
- 一个任务：100k 输入、10k 输出。

| 方案 | 输入成本 | 输出成本 | 单次 | 若 1 次通过 | 若 3 次通过 |
|---|---:|---:|---:|---:|---:|
| frontier | $1.00 | $0.30 | $1.30 | $1.30 | $3.90 |
| worker | $0.10 | $0.02 | $0.12 | $0.12 | $0.36 |

但 worker 可能：

- 需要更多轮次（上下文更长）；
- 需要 frontier review（+$0.20–0.50）；
- 返工/人工介入（隐性成本）。

所以判断标准是 **CPVT**，不是单价。若 worker 3 次通过 + review 仍低于 frontier 1 次，才值得。

## 8. 结论

1. **先降面积，再降单价。** 历史重发是最大、最确定的目标。
2. **工具层治理比压缩层更值钱。** json_bloat 60.6M 是最大单项。
3. **多 agent 必须 hub-and-spoke。** 网状通信会把省下的 token 吃回去。
4. **verify 是成本与质量的共同锚点。** 没有 verify，便宜模型只会制造返工。
