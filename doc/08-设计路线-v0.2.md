# 08 设计路线 v0.2：自有编排内核 + 可替换执行器

> 本版不推翻 01–07 的协议，只更换**载体**。  
> 触发原因：2026-11 的 prompt 协议实测有效（单次通信 token 降低 40%–70%），但“手工放文件 + pi 插件”的方式不可持续；pi 的插件/概念变化太快，不能作为长期基座。  
> **阅读方式**：01–04 的协议内容仍然有效；目录从 `.agent/` 映射到 `.loom/`，见 §10。05/06 中“pi 为主路径”的部分由本文替代。

---

## 0. 一句话结论

**不要再把 pi 当基座，也不要把 agent 的聊天当状态。**

把 Loom 做成一个独立的本地 CLI/daemon：

- 它拥有状态、任务图、上下文编译、验收、账本；
- agent 只是可替换的“执行器进程”；
- 稳定契约是 **进程 + 文件 + JSON + exit code**，不是插件 API。

这样 pi 可以换、Codex 可以换、OpenCode 可以换，而 Loom 的状态协议、验收协议、成本账本不变。

---

## 1. 实测告诉了我们什么

| 观察 | 解释 | 决策 |
|---|---|---|
| 单次通信 token −40%~70% | 切片 + 短上下文 + 按引用交付确实有效 | **保留协议，产品化** |
| 并发下降、整体变慢 | 手工派发、串行等待、人工 review；不是协议本身的问题 | 调度与执行分离，队列化；同时看墙钟，不只看 token |
| 每个项目手工放文件 | 没有初始化/脚手架 | `loom init` 生成；模板内置在工具里 |
| LLM 会覆写状态文件 | 状态和工作区没有隔离，agent 有写权限 | **单写者 + 只读快照 + outbox** |
| 会话结束后不确定能否复用 | 状态依赖会话，且可能已被改写 | 事件日志 + 无会话状态 + `loom resume/doctor` |
| pi 插件一个月后可能不能用 | 依赖了别人的插件 API | 只做进程级 adapter；核心不 import pi |
| Aider 只能顶一阵 | 共享 transcript、无子 agent 隔离 | 借鉴理念，作为临时 adapter |

**最重要的结论**：你验证的是“协议有效”，不是“pi 插件方案有效”。下一步应该把协议变成**自己的工具**，而不是继续在 pi 上加插件。

## 2. 三条架构决策

### D1 控制面自研，执行面可替换

| 层 | 归属 | 内容 |
|---|---|---|
| 控制面 | **自研** | 状态存储、任务图、调度、上下文编译、验收、预算、账本、策略 |
| 执行面 | **可替换** | 原生最小执行器、Codex、OpenCode、Aider、pi、OpenHands、goose |
| 网关 | **可选复用** | LiteLLM（路由）+ Headroom（缓存/压缩） |

控制面是差异化，也是 token 收益的来源；执行面是商品，谁稳定就用谁。

### D2 稳定契约是进程级，不是插件级

一次任务派发的契约：

```text
Task Packet（目录，只读）
    ↓
执行器进程（独立 cwd / 独立上下文）
    ↓
代码变更 + outbox/receipt.json + usage.jsonl + exit code
```

不依赖：

- 插件的 hook 名称；
- agent 的内部 session 格式；
- 共享内存/共享 transcript；
- 父 agent 的上下文继承。

### D3 状态是数据库，不是提示词

- **唯一事实源**：append-only 事件日志 + 任务记录。
- **Markdown 视图**：由事件生成，不是手写、不是 LLM 写。
- **worker**：只读快照 + 只写 `outbox/`。
- **orchestrator**：唯一写状态的人。
- **状态目录不在 worker worktree 内**；worker 默认看不到 `.loom/`。

这直接解决“LLM 覆写状态”和“换个会话就接不上”的问题。

## 3. 目标架构

```text
┌──────────────────────────────────────────────────────────────┐
│ Human / CLI                                                  │
│  loom init | task | dispatch | verify | status | resume       │
└──────────────────────────┬───────────────────────────────────┘
                           │
┌──────────────────────────▼───────────────────────────────────┐
│ Loom Control Plane（自研，确定性优先）                        │
│  ├─ State Store：.loom/events.jsonl + tasks/                  │
│  ├─ Scheduler：ready queue / 并发 / 重试 / 升级               │
│  ├─ Context Compiler：每次调用重新编译有界上下文              │
│  ├─ Budget Governor：token / 成本 / 时间                      │
│  ├─ Verifier：独立重跑 acceptance                             │
│  └─ Ledger：请求 / 任务 / 成本 / CPVT                         │
└───────────────┬──────────────────────────────┬───────────────┘
                │ Task Packet（只读）           │ Receipt + patch + usage
                ▼                              │
┌──────────────────────────────────────────────┴───────────────┐
│ Executor Adapters（可替换）                                   │
│  ├─ native minimal loop（后期）                               │
│  ├─ codex exec --json                                        │
│  ├─ opencode run --format json / server SDK                  │
│  ├─ aider --message（临时/A-B）                              │
│  └─ pi（可选，不作为基座）                                    │
└───────────────┬──────────────────────────────────────────────┘
                │
                ▼
        git worktree（每任务一个）
                │
                ▼
        LiteLLM → provider
        （可选）Headroom 在 LiteLLM 之前
```

### 3.1 控制面不是“常驻聊天”

C1 从“frontier 常驻小上下文”改为：

- **确定性代码优先**：调度、状态迁移、verify、账本、预算都不调用 LLM；
- **LLM 只处理歧义**：规划、失败判断、需要解释的验收；
- 每次 LLM 调用都是**有界函数**：输入是编译后的上下文，输出是 JSON，不保留 transcript。

这比“把聊天历史压小”更彻底：**根本没有长历史可重发**。

### 3.2 决策阶梯

每个决策先走最便宜的层：

1. 规则/脚本能做的 → 不调用 LLM；
2. 模板/检索能做的 → 不调用 LLM；
3. 需要生成 → worker 档模型；
4. 需要判断/规划/冲突处理 → frontier 档模型。

多模型不是“给每个 agent 配一个模型”，而是“给每个决策配一个层级”。

## 4. 状态所有权：解决覆写与会话依赖

### 4.1 目录布局

```text
repo/
├── .loom/                         # 状态根；gitignore；worker 默认看不到
│   ├── project.json               # 项目 id、repo、verify 命令、配置版本
│   ├── goal.md                    # 人写；orchestrator 只读
│   ├── constraints.md             # 人写；orchestrator 只读
│   ├── tasks/
│   │   └── T-001.json             # TaskSpec；orchestrator 写
│   ├── events.jsonl               # append-only；唯一事实源
│   ├── runs/
│   │   └── R-20261104-001/
│   │       ├── task.json          # 派发时快照；只读
│   │       ├── context/           # 编译后的片段；只读
│   │       ├── outbox/
│   │       │   ├── receipt.json   # adapter 归一化生成（不信任 worker 自述）
│   │       │   ├── final.md       # worker 最终消息，仅作摘要
│   │       │   └── report.md      # 可选，详情
│   │       ├── logs/
│   │       │   ├── agent.jsonl
│   │       │   └── verify.log
│   │       └── patch.diff         # 可选
│   ├── ledger/
│   ├── snapshots/                 # 派发前快照，用于恢复
│   └── locks/
└── .worktrees/
    └── T-001/                     # worker cwd；只含代码
```

> `.loom/` 放在仓库根、加入 `.gitignore`，因此 `git worktree add` 出来的 worktree 不会包含它。worker 的 cwd 是 `.worktrees/T-001`，默认看不到状态。  
> 需要中心化存储时，可用 `LOOM_HOME=~/.local/share/loom/projects/<id>`，协议不变。

### 4.2 写权限表

| 路径 | 所有者 | worker 权限 | 用途 |
|---|---|---|---|
| `.loom/events.jsonl` | orchestrator | 无 | 唯一事实源 |
| `.loom/tasks/*.json` | orchestrator | 只读快照 | 任务图 |
| `.loom/goal.md` | 人 | 只读快照 | 目标 |
| `.loom/runs/*/context/` | orchestrator | 只读 | 编译上下文 |
| `.loom/runs/*/outbox/receipt.json` | adapter | 无 | 归一化回执 |
| `.loom/runs/*/outbox/final.md` | worker | 写 | 最终消息，仅摘要 |
| `.loom/runs/*/outbox/report.md` | worker | 写 | 详情 |
| `.worktrees/T-001/**` | worker | 写 | 代码 |
| `.loom/ledger/**` | orchestrator | 无 | 账本 |

### 4.3 防覆写规则

1. **worker 不获得 `.loom/` 写路径**；Task Packet 是拷贝/只读挂载。
2. **受保护路径**：`.loom/**`、`.git/**`、`goal.md`、`constraints.md`。派发前后比对哈希；发现变更 → 拒绝回执、恢复快照、记事件。
3. **单写者**：只有 orchestrator 能追加事件、改任务状态、生成 Markdown 视图。
4. **快照**：每次派发前对 `.loom/` 做快照；`loom restore <run>` 可回滚。
5. **校验**：`loom doctor` 检查 schema、哈希、孤儿 run、过期锁。
6. **强隔离（可选）**：容器内只挂载 worktree 为 RW、`.loom` 为 RO；或 worker 以独立用户运行。

### 4.4 会话无关

- 状态里不存 session id；run 只由 `task_id + run_id` 标识。
- 进程崩溃后，`loom resume` 从 `events.jsonl` 重放，继续 `pending/running` 任务。
- 新 shell、新机器、新会话，只要拿到仓库和 `.loom/`，就能 `loom status` / `loom resume`。
- **验收测试**：派发后 `kill -9`，重启，`loom resume` 必须能从最后一个事件继续；worker 改 `.loom` 必须被拒绝。

### 4.5 目标/约束怎么改

- 人用 `loom goal edit` / `loom constraint edit`，带 schema 校验和版本号。
- worker 的 prompt 明确：**不要写 progress/goal/decision**；进度由事件生成。
- 如果确实需要 worker 提议改目标，写 `outbox/proposal.md`，由人确认后 orchestrator 应用。

## 5. 无长会话：每次调用都是有界函数

### 5.1 旧模式 vs 新模式

| | 旧：聊天式 orchestrator | 新：状态机 orchestrator |
|---|---|---|
| 历史 | 对话历史不断增长 | 不保留对话历史 |
| 每轮输入 | 全量历史重发 | 只发编译后的当前上下文 |
| 恢复 | 依赖 session | 依赖事件日志 |
| 成本形状 | 随轮数二次增长 | 每次调用有界 |
| 人工介入 | 在聊天里插话 | `loom` 命令/审批 |

### 5.2 主循环

```text
while 有 ready 任务:
    packet = context.compile(task, state, budget)
    result = adapter.dispatch(packet)
    receipt = validate(result)
    evidence = verify(task, receipt)
    state.append(TaskVerified | TaskFailed | NeedsHuman)
```

- 每个步骤都可恢复；
- adapter 是子进程，超时可杀；
- orchestrator 不等待聊天，不阻塞在某个 UI；
- 任务可以后台跑，`loom status` 随时看。

### 5.3 事件日志不是 prompt

事件日志用于恢复和审计，**不直接塞给模型**。模型只看到：

- 目标/约束的短版本；
- 当前任务；
- 依赖任务的一行摘要；
- 相关代码片段；
- 上次失败包（仅重试时）；
- 输出 schema。

`StateSummary` 由确定性代码生成，目标 < 2k tokens。这样既保留事实源，又避免把历史当上下文。

## 6. Context Compiler：真正的护城河

### 6.1 输入

| 部分 | 来源 | 预算（示例） |
|---|---|---|
| 稳定前缀 | system + 工具说明 + goal + constraints | 2–4k |
| 任务 | TaskSpec + acceptance | 1–2k |
| 依赖摘要 | 每个依赖一行 | 0.5–1k |
| 代码片段 | 路径 + 符号 + 行号 + 内容 | 8–16k |
| 失败包 | 仅重试时：失败命令 + 关键日志 + 相关 diff | 2–4k |
| 输出 schema | JSON Schema / 回执格式 | 0.5–1k |

### 6.2 规则

1. **硬预算**：planner 8k、worker 24k、judge 8k（示例，按模型调）。
2. **稳定顺序**：system → tools → goal → constraints → task → snippets → failure → schema。不要把时间戳、随机 id 放进前缀。
3. **工具结果结构化**：`{summary, path, hash, range, truncated}`；全文写 artifact，模型按需 `read range`。
4. **按符号/路径/行号读**：禁止整仓 dump；同一文件同一任务只读一次，重复读要说明理由。
5. **diff-only**：默认输出 patch；只有新文件才允许全文。
6. **确定性摘要**：状态摘要、依赖摘要、失败摘要都由代码生成，不让 LLM 二次总结。
7. **缓存友好**：任务内不换 system/tools；批量变更；同一任务复用前缀。
8. **工具端先裁**：工具输出默认“摘要 + 地址 + artifact 引用”；单次调用与单 run 都有硬上限；不把原始 JSON/HTML/日志回贴。
9. **网关兜底**：Headroom 只处理模型层重复与缓存，不负责工具结果治理。

### 6.3 成本形状

单任务内：

```text
billed_input ≈ turns × bounded_prompt
```

任务之间：

```text
总输入 ≈ Σ 每个任务的 bounded_prompt
```

不再有“整个 run 的历史 × 每轮”的二次增长。任务越短，收益越大；这也是为什么切片比压缩更重要。

## 7. 执行器策略：Adapter first，Native later

### 7.1 Adapter 契约 v1

```bash
loom-adapter dispatch \
  --packet .loom/runs/R-001 \
  --worktree .worktrees/T-001 \
  --model worker \
  --output .loom/runs/R-001/outbox
```

约定：

| 项 | 约定 |
|---|---|
| 输入 | Task Packet 目录；不通过 stdout 传大段内容 |
| 输出 | adapter 归一化写 `outbox/receipt.json`；worker 只写代码 + `final.md`/`report.md` |
| 回执 | 从 exit code、git diff、最终消息、verify 结果归一化生成；**不信任 worker 自述** |
| usage | `outbox/usage.jsonl` 或 adapter 日志；字段缺失标 `unknown` |
| exit code | `0` 成功；`2` 需人工；`3` 预算/超时；`4` adapter 故障 |
| 超时 | orchestrator 杀进程组，记 `adapter_timeout` |
| 环境 | `LOOM_TASK_ID`、`LOOM_RUN_ID`、`LOOM_MODEL`、`LOOM_MAX_TOKENS` |
| 能力 | `streaming`、`tool_calls`、`usage`、`patch`、`resume`、`sandbox` 由 adapter 声明 |

**关键**：不要让 orchestrator 解析 agent 的自然语言 stdout 来决定状态；状态只来自 receipt + verify。

### 7.2 首批 adapter

| Adapter | 调用方式 | 适合 | 风险 |
|---|---|---|---|
| **goose** | `goose run --no-session -i task.md --output-format json` | **首选**：多 provider、headless、无会话 | JSON/usage 字段随版本变；需 pin + canary |
| **OpenCode** | `opencode run --format json` 或 headless server SDK | 备选：多 provider、结构化事件 | v2 迭代快；必须 pin 版本 |
| **Codex** | `codex exec --json` | 可选 frontier worker / 回退 | OpenAI 中心；工具较重；多 provider 不便 |
| **Aider** | `aider --message` | diff 生成、A-B、临时顶替 | 共享 transcript；无子 agent 隔离 |
| **pi** | 现有 CLI | 可选，不作为基座 | 插件/概念漂移 |
| **native** | `loom-exec` | 完全掌控上下文/工具结果 | 质量与工具生态要自己补 |

建议至少保留 **两个可用 adapter**（goose + OpenCode，或 goose + native）。`loom doctor --adapters` 每周跑一次 canary；一个坏了不影响主路径。

### 7.3 原生最小执行器

**什么时候做**：外部 adapter 无法控制工具结果投影/上下文，或者你需要完全掌控 token 结构时。

**范围**：

- 工具：`bash`、`read`（range）、`edit`（diff）、`search`；
- provider：LiteLLM / OpenAI-compatible；
- 观测：每次工具结果写 artifact，返回摘要 + 路径 + 行号；
- 循环：max steps、no-progress 检测、预算硬停；
- 不做：LSP、MCP 市场、TUI、多租户、完整沙箱。

**参考**：`mini-swe-agent`（MIT，agent 类约 190 行，bash-only，LiteLLM）。它证明了“极简循环 + 强模型”可以工作；我们只需要在它上面补：

- 结构化 observation；
- 工具结果投影；
- 任务/验收协议；
- 预算与恢复。

这不是“自研完整 runtime”，而是“自研一个可替换的最小执行器”。它和外部 adapter 走同一个契约，随时可以关掉。

## 8. 工具选型：二次开发友好度

> 许可与能力以仓库 `LICENSE` 和本机版本为准；下表是 2026-11 的判断。

| 工具 | 许可 | 可二次开发的稳定面 | 值得借鉴 | 在 Loom 中的角色 | 风险 |
|---|---|---|---|---|---|
| **OpenCode** | MIT | headless server + SDK + `run --format json` | server/event/SDK 分层、provider 无关 | 备选外部 adapter | v2 迭代快，API 会变 |
| **OpenHands SDK** | MIT | Python/TS SDK + Agent Server + sandbox | 事件溯源状态、workspace 抽象、沙箱 | 执行面候选/参考 | 较重，自带 conversation 模型 |
| **goose** | Apache-2.0 | GDK、recipes、MCP、CLI/API、headless JSON | recipes、MCP、provider 抽象、`--no-session` | **首选外部 adapter** | 自有概念多；需 pin 版本 |
| **Codex CLI** | Apache-2.0 | `codex exec`、JSONL、MCP | 强 frontier 执行 | 可选 frontier adapter | OpenAI 中心，工具较重 |
| **mini-swe-agent** | MIT | 约 190 行 agent + LiteLLM | 极简循环、bash-only、线性历史 | **原生执行器参考/起点** | 太简单，需要补投影/预算 |
| **Aider** | Apache-2.0 | Python、LiteLLM、repo map、architect/editor | repo map、diff 格式、双模型 | diff 引擎/A-B/临时 adapter | 共享 transcript，无隔离 |
| **Crush** | FSL | Go、MCP、LSP | TUI/LSP 体验 | 外部工具 | FSL，不适合作为分发基座 |
| **pi** | 以仓库为准 | 插件 | 现有工作流 | 可选 adapter | 插件 API 漂移 |
| **Claude Agent SDK** | 以官方条款为准 | TS/Python SDK | 工具/权限模型 | 仅 Claude 场景 | 模型锁定 |

### 8.1 结论

- **内核**：自己写，保持小；用端口-适配器（hexagonal）结构。
- **执行器**：首个接 **goose**；OpenCode/Codex 作为备选；native 后补。不要把任何 agent 的插件 API 作为核心依赖。
- **Aider**：只借鉴 repo map / diff / architect-editor，必要时做临时 adapter。
- **OpenHands SDK**：如果想要“沙箱 + 事件溯源 + 多语言 SDK”的完整执行面，它是最接近的 MIT 选项；但它有自己的 conversation/state 模型，适合放在执行面，不适合当 Loom 内核。
- **pi**：可以继续用，但只通过进程调用；不再为它写核心插件。

### 8.2 为什么不是“直接基于 OpenCode 开发”

OpenCode 的 headless server + SDK 很适合做执行器，但：

- 它是完整产品，不是薄框架；核心概念（session、message、agent）会与 Loom 的状态模型重叠；
- v2 迭代很快，插件/协议会变；
- 你要的是“控制面”，不是“另一个 agent 产品”。

所以：**用它的进程/HTTP 契约，不用它的内部模型。**

### 8.3 为什么 goose 适合做首个 adapter

goose 现在由 Linux Foundation 的 Agentic AI Foundation 治理，Apache-2.0；它不是“Block 内部工具”，而是中立基金会项目。对本项目更重要的是，它的 CLI 已经具备 adapter 需要的能力：

| 能力 | goose 对应 | 对 Loom 的价值 |
|---|---|---|
| 无头执行 | `goose run -i task.md` / `-t` | 一次任务一个进程 |
| 不落会话 | `--no-session` | 符合“无长会话” |
| 结构化输出 | `--output-format json` / `stream-json` | adapter 可解析，不靠自然语言 |
| 多 provider | `--provider` / `--model`，内置 LiteLLM provider | 可把 LiteLLM 当唯一上游 |
| 工具控制 | `--with-builtin developer` / `--with-extension` | 只给必要工具 |
| 轮次/重复限制 | `--max-turns` / `--max-tool-repetitions` | 预算/no-progress 的第一道闸 |
| 配方 | `--recipe` + `--params` | 可把 TaskSpec/系统提示模板化 |
| 服务化 | `goose serve`（ACP over HTTP/WS）、`goose acp` | 未来可换常驻模式，不必改核心 |
| 可嵌入 | GDK | 需要时再评估，不首期依赖 |

建议的 adapter 调用（示例，参数以本机 `goose --help` 为准）：

```bash
export GOOSE_PROVIDER=litellm
export GOOSE_MODEL=worker
export LITELLM_HOST=http://127.0.0.1:4000
export LITELLM_API_KEY=dummy

goose run --no-session \
  -i .loom/runs/R-001/task.md \
  --output-format json \
  --with-builtin developer \
  --max-turns 30 \
  --max-tool-repetitions 3 \
  --quiet
```

**关键设计**：goose 自带 **LiteLLM provider**，配置 `LITELLM_HOST` / `LITELLM_BASE_PATH` / `LITELLM_API_KEY` 即可，不需要分别配置 GPT/DeepSeek。这样：

```text
Loom → goose（provider=litellm, model=worker）→ LiteLLM → provider
```

goose 只看到“一个 LiteLLM endpoint + 一个 model alias”；GPT/DeepSeek 的差异由 LiteLLM 吸收。这正是“执行器可替换、路由集中”的形态。如果不用 LiteLLM，也可以用 goose 的 OpenAI-compatible custom provider；但优先用内置 LiteLLM provider，少一层配置。

> **前期约束**：API key 可覆盖 GPT、DeepSeek、Kimi、MiniMax、MiMo 等。LiteLLM 先做 GPT `frontier` + DeepSeek `worker` 两档；其他国产模型按 A/B 逐步接，订阅 lane 不参与。

风险与对策：

- **JSON/usage 字段要核实**：不同版本可能变；adapter 只依赖稳定字段，缺失就标 `unknown`，成本以 LiteLLM 日志为准。
- **工具输出可能很大**：goose 的 JSON 会带工具结果；Loom 不回贴给下一个模型，只落 artifact + 摘要。
- **developer 扩展也不轻**：M0 只开必要工具；如果工具面仍太重，再评估 native executor。
- **版本漂移**：pin 版本 + `loom doctor --adapters` canary；保留 OpenCode/Codex 作为第二 adapter。

### 8.4 Rust 做控制面：可以，而且适合这个架构

先说结论：**Rust 的二进制分发很好；对这个“进程编排 + 文件状态 + SQLite + JSON”的控制面，Rust 是合适的。** 真正的代价不是分发，而是开发速度和 native executor 的生态。

| 维度 | Rust | Python | TypeScript |
|---|---|---|---|
| 分发 | **最好**：单静态二进制 | 需要 Python/uv | 需要 Node/Bun |
| 开发速度 | 慢一些 | **最快** | 快 |
| 进程/信号/超时 | **最好** | 好 | 好 |
| JSON Schema | serde + schemars | pydantic | zod |
| SQLite | rusqlite/sqlx | 内置 sqlite3 | better-sqlite3 |
| LLM/agent 生态 | 少 | **最多**（LiteLLM/mini-swe-agent/OpenHands） | 多（OpenCode/pi） |
| native executor | 工作量较大 | **最容易**（mini-swe-agent） | 中等 |
| 长期维护 | **强**（无运行时依赖） | 中 | 中（依赖漂移） |

建议：

- **控制面用 Rust**：`clap` + `serde` + `rusqlite` + `tokio::process` + `tracing`；git 先 shell out，不急着上 `git2`。
- **M0/M1 不写 native executor**：先用 goose adapter。native executor 到 M2 才做；实现上选择独立进程 `loom-native`，控制面不 import 执行器代码。
- **如果 Rust 熟练度一般**：Python 会更稳，因为你要频繁改 prompt/context 逻辑；但 Python 的“单二进制分发”要接受 uv/pyinstaller 的折中。
- **不建议 Go**：你已经排除；而且这个项目真正需要的是“状态机 + 进程管理”，Rust 和 Python 都能做，Go 没有额外优势。

一句话：**Rust 适合做“不会天天改”的控制面；Python 适合做“天天改”的 agent 逻辑。** 你可以用 Rust 写核心，把 native executor 留成可替换的独立进程，避免把两件事绑死。

## 9. 路线图 v0.2

> 原来的 S 阶段是“手工放文件 + 手动派发”。现在你已经验证了协议，S 阶段的目标变成“把手工流程产品化”。  
> 不再先做 pi 插件；先做独立 CLI。

| 里程碑 | 时间 | 交付 | 退出标准 |
|---|---|---|---|
| **M0 协议产品化** | 2–3 天 | `loom init/task/dispatch/verify/status/resume/doctor`；状态所有权；1 个 adapter | 1 个真实任务端到端；重启可恢复；worker 改 `.loom` 被拒 |
| **M1 上下文与账本** | 1 周 | Context Compiler、事件日志、usage、CPVT、第二个 adapter | 主上下文 ≤30k；0 未归因；adapter canary 通过 |
| **M2 原生执行器** | 1–2 周 | 最小循环、工具结果投影、预算、prompt 库 | worker 任务通过；单任务 token 下降；可回退 adapter |
| **M3 路由** | 1 周 | LiteLLM、role→tier、升级、成本护栏；GPT + DeepSeek 起步 | worker ≥50%；CPVT −20%；质量不退化 |
| **M4 并行** | 1–2 周 | worktree、合并队列、锁、看板 | **2 并行起步**；无丢更新；合并 <5min；3 并行需 A/B 证明 `WPT`/`CPVT` 不退化 |
| **M5 多仓库工作区**（待排期） | 1 周 | manifest 成员仓库、`loom workspace *`、跨成员同名分支 worktree | 见 [13](13-多仓库工作区与多端协同.md) §11 P0–P3；单成员任务零迁移 |

### 9.1 M0 具体做什么

1. `loom init`：识别 repo、创建 `.loom/`、写 `project.json`、检测 verify 命令、记录工具版本。
2. `loom task add`：从 JSON/交互创建 TaskSpec；校验 schema。
3. `loom dispatch T-001 --adapter goose`：创建 worktree、快照状态、编译 packet、启动 goose。
4. `loom verify T-001`：在干净 worktree 重跑 acceptance；写证据。
5. `loom status`：任务图、预算、异常、待人工。
6. `loom resume`：从事件日志恢复。
7. `loom doctor`：schema、哈希、孤儿 run、过期锁、adapter canary。
8. 写 3 个测试：worker 改 `.loom` 被拒；`kill -9` 后恢复；新 shell 能读状态。

**M0 不调用 LLM 做规划**。任务由人写，先验证状态/派发/验收闭环。规划是 M1/M2 的放大器，不是第一步。

### 9.2 M1 具体做什么

- Context Compiler：稳定前缀、片段选择、失败包、预算。
- 事件日志：JSONL 为事实源，SQLite 为索引（可选）。
- Ledger：解析 adapter usage + LiteLLM 日志；CPVT/TPVT；对账。
- Prompt 库：版本化，派发时渲染；不往项目里拷贝静态 prompt。
- Adapter 契约测试：schema、exit code、超时、usage、空输出。
- 第二个 adapter（OpenCode 或 native）作为回退。

> **实现状态（2026-11-06）**：以上均已落地为 `loom-context` / `loom-adapter` 两个 crate 与 `loom context/prompt/adapter/dispatch/verify/resume` 命令；mock adapter 端到端（dispatch → verify → 事件重放 → canary）已通过。剩余：真实 goose/OpenCode canary（需二进制）、LiteLLM 日志的现场对账。

### 9.3 M2 具体做什么

- native executor：bash/read/edit/search；
- observation：大结果写 artifact，返回摘要 + 路径 + 行号；
- 预算：预估 + 实时 usage + 硬停；
- no-progress：连续 N 轮无 diff/无 verify 进展就停；
- A/B：同一任务集，native vs adapter，按 CPVT/TPVT/墙钟比较。

> **实现状态（2026-11-06）**：`loom-native` 已作为独立进程落地，`loom dispatch --adapter native` 可直接调用。当前实现 OpenAI-compatible `/chat/completions` 工具循环，工具为 `read/search/edit/write/bash/finish`；长输出写 `.loom/runs/<run>/outbox/artifacts` 并只回投影摘要；已实现 token/墙钟/步数/成本预算、no-progress、acceptance 预跑、`final.md`/`report.md`/`usage.jsonl`。
>
> acceptance 失败会在同一次 native run 内回灌：失败命令、退出码和截断输出（单命令 3KB、总包 8KB）作为 `finish` 的 tool result 或 user message 回给模型，默认最多 2 轮（`LOOM_NATIVE_MAX_VERIFY_ROUNDS`，最小 1），重试会重置 no-progress；轮次耗尽标记 `failed`。`loom dispatch` 还会读取上一 run 的失败回执与 `verify.log` 生成 `FailurePack` 注入 Context Compiler。
>
> 成本：provider 成本优先（`cost_source=provider`）；否则用派发模型的 `ModelCapability` 价格表估算（`pricing_table`）；价格未知则省略 `cost_usd` 并标 `unknown`。估算成本计入运行中预算与 `TaskBudget.max_cost_usd`，超限以 `budget_exceeded`/exit 3 停止。离线测试用 `LOOM_NATIVE_SCRIPT` 脚本化 provider，`scripts/smoke-native.sh` 端到端通过。剩余：真实模型 A/B、成本预算与真实账单校准、真实 goose/OpenCode canary。

### 9.4 M3 具体做什么

- 确定性路由：`role → tier`、显式 `--model` 覆盖、任务自带 tier 兜底；
- 升级：只在 verify 失败后升级，worker 默认失败 2 次转 frontier，每任务最多 1 次；
- 成本护栏：tier 级每任务成本上限 + 派发前最坏情况估算，超限拒绝派发；
- 可解释：`loom route TASK` 输出选中模型、tier、原因、fallback、预算与估算；
- LiteLLM 作为可选网关：模型 alias 由控制面固定，LiteLLM 吸收 provider 差异。

> **实现状态（2026-11-06）**：控制面路由已落地。`.loom/config.toml` 新增 `[routing]`：`roles`（role→tier）、`escalate_after_failures`、`max_escalations_per_task`、`fallbacks`、`cost_limits`。`loom route TASK` 与 `loom dispatch` 共用同一个 `RoutingConfig::plan`；显式 `--model` 优先，未配置 role 时使用任务 tier。升级只读取 `task.failed` 事件次数，并在派发前写 `task.escalated`；`TaskDispatched` 记录 route 原因、tier、fallback。成本护栏会在 `budget.max_cost_usd` 超过 tier 上限，或按价格表估算的最坏成本超过上限时拒绝派发。`loom route stats` 从事件日志统计每个任务最后一次派发的 tier、worker 占比、升级次数与路由原因，用于核对 M3 退出标准。
>
> **同层 fallback 已接线（2026-11-06）**：`[routing.fallbacks]` 按 tier 配置；配置加载时校验 alias 存在、alias 的 tier 必须等于键（跨层直接报错，跨层只能走升级）、tool-loop-safe、不重复。派发时只有**可用性失败**（adapter 退出码 4，或超时）才切换；`budget_exceeded` / `needs_input` / `blocked` 不切换——换模型撤销不了已经烧掉的预算，切了只会双倍花钱。每次切换写 `task.fallback`（`run_id` = 新 attempt 的 run、`parent_run_id` = 失败的 run、`attempt` 不变），并给新 attempt 开**独立 run**，receipt、usage、失败包互不覆盖，上一 attempt 的失败还会作为 FailurePack 注入下一 attempt 的 packet。显式 `--model` 会钉住 alias：`RouteDecision.fallback_enabled = false`，不切换。`scripts/smoke.sh` 用 `LOOM_MOCK_FAIL_ALIAS` 覆盖“主模型 exit 4 → fallback 成功 → verify 通过”的全链路。
>
> 未完成：worker 占比 ≥50%、CPVT −20%、质量不退化仍需要真实模型与账单 A/B。LiteLLM 只保留接入设计，容器内没有 LiteLLM 服务，未做现场 canary。

### 9.5 M4 并行：实现状态（2026-11-08，完成）

- **路径锁**：`.loom/locks/<sha256(path)[..12]>.lock`，字段与规则见 [03](03-核心协议.md) §13。`loom dispatch` / `loom verify` 在执行前按 `workspace.allowed_paths` 加锁；guard 是 RAII 且只释放自己写过的路径（嵌套 guard 不互相误释放）；owner 进程消失立即回收，lease 过期但 owner 存活由 `loom doctor` 报告为 stuck。
- **并行上限与预算**：`[parallel] max_running`（默认 2）按“持有存活锁的任务数”计数；`[parallel] max_inflight_cost_usd`（默认 0 = 不限）限制并发任务 `budget.max_cost_usd` 之和。超限分别写 `task.blocked(code=parallel_cap / inflight_budget)`，任务可重试。
- **合并队列**：`loom merge <task>` 只接受 `passed` 任务（或上次 `merge_conflict`/`integration_verify` 阻塞后的重试）。流程 = 全局 `**` 锁（合并期间暂停一切写任务派发）→ 合并前重新 verify → 干净树检查 → `git rebase`（冲突则 abort 并 `task.blocked(code=merge_conflict)`）→ `git merge` → 集成 verify（在 base checkout 重跑 acceptance，失败则 `reset --hard` 回滚并 `task.blocked(code=integration_verify)`）→ `task.merged(merge_sha, base_before, integration_verify)` → 清理 worktree 与分支（失败仅告警）。in-place 任务被拒绝（改动已在 base 分支上）。
- **看板**：`loom board`（`--format json|pretty`）按状态列出全部任务，并显示 running/max、锁持有者。
- **并发正确性（无丢更新）**：`events.jsonl` / `requests.jsonl` / `seen.jsonl` / `tools.jsonl` 改为单次 `write_all`（两个进程交错写半行会毁掉 JSONL）；`tasks.json` 临时文件带 pid 后缀；`new_run_id` 用原子 `mkdir` 预留目录，同一秒并发派发不再共享 run id。
- **实测**：`scripts/smoke-parallel.sh` 在一次性 git 仓库里用 native 脚本跑 **10 任务、2 并发派发**（采样 `loom board` 确认同时在跑 = 2），全部 verify 通过后串行合并：**10 个 `task.merged`、0 `task.failed`、0 `task.blocked`、10 个文件无丢失、锁全部释放、worktree 与分支全部清理、10 次合并 <5 分钟**；期间用外部 `**` 锁验证了合并队列的全局闸门。`scripts/smoke.sh` 覆盖锁冲突、并行上限、inflight 预算与 in-place/未验收合并拒绝。
- **任务图去重**：`doc/05` §6 的“相同输入哈希 + 相同输出路径不并行”被路径锁覆盖——输出路径相交本身就会被阻塞；相同输入但输出不相交的任务属于重复劳动，留到有真实任务集后再做输入哈希去重。
- **仍未做**：3 并行（需 A/B 证明 `WPT`/`CPVT` 不退化）、并行对 cache hit 的影响（需真实 provider）、真实仓库的合并冲突率统计。

### 9.6 暂不做

- 完整 Agent Runtime、IDE、TUI、云平台；
- 插件市场；
- LLM 自评复杂度路由；
- 自动压缩/自动摘要（状态摘要必须确定性）；
- 多 agent 互相聊天；
- 无人值守的大任务。

## 11. 指标：不要只看 token

| 指标 | 定义 | 用途 |
|---|---|---|
| **CPVT** | 总成本 / 通过验收的任务数 | 核心成本指标 |
| **TPVT** | 计费 token / 通过验收的任务数 | 核心 token 指标 |
| **WPT** | 墙钟 / 通过验收的任务数 | 解释“token 降了但更慢” |
| **first-pass verify** | 首次 verify 通过率 | 质量 |
| **human intervention** | 人工介入次数/任务 | 自动化程度 |
| **cache hit** | 缓存命中 token / 输入 token | 网关健康 |
| **handoff ratio** | 跨 agent 传递 token / 总 token | 通信浪费 |

你观察到的“单次通信 −40%~70%，但整体变慢”，很可能是因为：

- 任务切片后调用次数变多；
- 手工派发/等待/复制文件的时间没有算进去；
- 并发下降，墙钟变长。

所以 M0/M1 必须同时记录 **CPVT、TPVT、WPT**；否则会误判“省了 token 但没省时间/钱”。

## 12. 风险与缓解

| 风险 | 缓解 |
|---|---|
| adapter 输出/schema 变化 | 契约测试 + canary + 两个 adapter + pin 版本 |
| native executor 质量不够 | 只接 worker 任务；frontier 回退；A/B |
| 状态损坏 | 事件日志 + 快照 + `doctor` + `restore` |
| 成本归因缺失 | adapter usage + LiteLLM 日志 + 对账；缺失标 `unknown` |
| 并发导致更慢 | 派发异步化；队列；测 WPT；先串行跑通再并行 |
| 工具本身变重 | 核心保持小；UI 推迟到 M4；不自研 runtime |
| 范围蔓延 | 每个里程碑有退出标准；不达标不进下一阶段 |

## 13. 已定与待定

### 13.1 已定

| 项 | 决定 | 备注 |
|---|---|---|
| 状态目录 | `.loom/` | 提供 `loom import .agent` 迁移；旧目录只读保留 |
| 首个 adapter | **goose** | Apache-2.0、Linux Foundation、headless JSON、多 provider |
| 控制面语言 | **Rust** | 单二进制分发；核心保持薄；native executor 不绑死在 M0 |
| 执行器边界 | 进程 + 文件 + JSON + exit code | 不用任何 agent 的插件 API 做核心 |
| 路由 | 先直连，M3 上 LiteLLM | goose 指向 LiteLLM 的 OpenAI-compatible endpoint |
| UI | CLI only 到 M3 | TUI/Web 是 M4 之后的可选层 |
| 代码检索 | v1 不引入 embedding / 向量库；R2 用 BM25/FTS5 | 客户机性能与分发体积优先；见 09 |
| 工具 I/O | wrapper 强制预算 + 落盘 + 去重 | 优先于网关压缩；见 09 §8 |
| 知识库共享 | 默认仅本项目；用户可显式开启跨项目 | 避免默认泄露与索引膨胀；见 09 |
| 工具输出协议 | `items` 短键 + 8/24/128KB 三级预算 + telemetry | 人类视图由工具层转换，不占 token；见 10 |
| MCP | M0 不做 | 先 CLI + 内部 API；Headroom 用 proxy |
| 输出本地化 | 默认中文，可切英文/日文 | 路径/符号/枚举不翻译；见 10 §6 |

### 13.2 待定/需 spike

1. **Rust 熟练度与维护成本**：如果实际迭代明显拖慢，回退 Python；不建议 Go。
2. **goose JSON 的 usage 字段**：M0 先做 1 个 spike，确认 token/成本字段；缺失就以 LiteLLM 日志为准。
3. **goose 的 developer 扩展是否太重**：用 `--with-builtin` 最小集合试；如果工具面仍过大，M2 上 native executor。
4. **目标平台**：Linux only，还是 Windows 也要支持。
   - Windows 会影响 worktree 长路径、进程组、文件锁、shell。
5. **native executor 的实现位置**：Rust 主二进制内，还是独立进程（Python/Go/Rust）。
   - 建议先独立进程，避免和 M0 控制面绑死。
6. **代码索引的规模与语言覆盖**：R1 是否值得做、是否引入 zoekt；见 [09-代码检索与知识库.md](09-代码检索与知识库.md) §14.2。
   - 已定：v1 不引入 embedding；M0 只做 R0 + 工具预算 + 检索轨迹。

## 14. 一句话总结

**把“agent 怎么聊”降级为执行细节，把“任务怎么被定义、编译、验收、记账”升级为产品。**

这样你既不会被 pi 的插件 API 绑架，也能持续吸收主流 agent/harness 的新玩法：新玩法先作为 adapter 或内部模块接进来，验证有效再进核心。
