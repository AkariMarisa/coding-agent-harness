# 02 总体架构与技术方案

> **v0.2 修订（2026-11-04）**：本文的“pi 主路径 / 常驻小上下文”已由 [08-设计路线-v0.2.md](08-设计路线-v0.2.md) 修订。  
> 控制面改为确定性状态机，执行器改为进程级可替换 adapter；本文的分层、组件、网关与安全部分仍然有效。

## 1. 设计原则

| 编号 | 原则 | 含义 | 反例 |
|---|---|---|---|
| P1 | 状态与对话分离 | 状态在 `.agent/`，聊天只做控制 | 把需求、决策、进度都留在 transcript |
| P2 | 上下文预算化 | 每类上下文有硬上限，超限就停/折叠 | 让上下文自然增长到 200k |
| P3 | 按引用不按值 | 传路径、哈希、行号、diff、日志路径 | 把文件全文/JSON/HTML 贴进消息 |
| P4 | 验证驱动 | verify 是唯一验收与升级信号 | 模型说“我完成了”就合并 |
| P5 | 确定性优先 | 能用脚本做的，不交给 LLM | 用 LLM 解析测试结果、算成本 |
| P6 | 单写者 + append-only | 每个状态文件一个写者；日志只追加 | 多个 agent 同时改 `PROGRESS.md` |
| P7 | 缓存友好 | 稳定前缀、批量变更、run 内不换模型 | 中途改 system prompt、重排工具 |
| P8 | 透明网关 | 压缩/路由对 agent 透明，可替换 | 把 provider 地址写死在 prompt 里 |
| P9 | 先测量后优化 | 没有账本就不改参数 | 凭感觉调压缩阈值 |
| P10 | 最小自研 | 只写编排、协议、账本；其余复用 | 自研 runtime/沙箱/压缩器 |

## 2. 系统边界

**Loom 是**：

- 一个运行在现有 agent runtime 之上的**编排层**；
- 一套**文件化状态协议**；
- 一个**薄 runner**（任务图、派发、verify、预算、升级、恢复）；
- 一个**成本/质量账本**；
- 一份**网关配置约定**（Headroom + LiteLLM）。

**Loom 不是**：

- 不是新的 Agent Runtime；
- 不是新的压缩器或路由器；
- 不是 IDE / TUI / 云平台；
- 不是“让 LLM 自己管理自己”的自治系统。

## 3. 逻辑架构

```
┌──────────────────────────────────────────────────────────────┐
│ Human / CLI                                                  │
│  loom run | status | approve | abort | resume | report       │
└──────────────────────────┬───────────────────────────────────┘
                           │
┌──────────────────────────▼───────────────────────────────────┐
│ C1 Orchestrator（frontier，常驻小上下文）                     │
│  · Goal / Task graph   · Scheduler   · Budget   · Escalation │
│  · 只读状态文件 + Receipt；不读 worker transcript             │
└───────┬──────────────────────────────┬───────────────────────┘
        │ TaskSpec（引用）              │ Receipt（4 行）
┌───────▼──────────────────┐   ┌───────▼───────────────────────┐
│ C2 Worker Runtime        │   │ C3 State Store（.agent/）      │
│  pi / Codex / SDK        │◀─▶│ GOAL/spec/design/tasks/       │
│  独立 context + worktree │   │ PROGRESS/DECISION/reports     │
└───────┬──────────────────┘   └───────────────────────────────┘
        │ LLM requests（原生 OpenAI / Anthropic 格式）
┌───────▼──────────────────────────────────────────────────────┐
│ C9 Context Gateway：Headroom :8787（mode=cache）              │
│  · live-zone 压缩 · 前缀缓存 · retrieve · 诊断 stats          │
└───────┬──────────────────────────────────────────────────────┘
        │ OpenAI-compatible / Anthropic-compatible
┌───────▼──────────────────────────────────────────────────────┐
│ C8 Model Router：LiteLLM :4000（P2 起）                       │
│  · alias → provider/model · fallback · 预算 · 权威日志        │
└───────┬───────────────────────────┬──────────────────────────┘
        │                           │
   frontier tier                worker tier
   gpt-6.1-sol medium           GPT 低档（DeepSeek 等后接）
```

### 3.1 分层职责

| 层 | 组件 | 职责 | 不负责 |
|---|---|---|---|
| 控制层 | C1 Orchestrator | 目标、任务图、调度、预算、升级 | 写代码、读 transcript |
| 协议层 | C5 Handoff | TaskSpec/Receipt/Decision schema | 业务逻辑 |
| 执行层 | C2 Runtime Adapter | 调 pi/Codex，收集 usage | 任务拆解 |
| 状态层 | C3 State Store | 文件读写、schema、锁 | 推理 |
| 验收层 | C6 Verify Runner | 执行 acceptance，收集证据 | 判断“应该做什么” |
| 网关层 | C9 Headroom | 压缩、缓存、retrieve | 模型路由、任务语义 |
| 路由层 | C8 LiteLLM | alias、fallback、日志、预算 | 上下文隔离 |
| 隔离层 | C10 Worktree | 分支/worktree/合并 | 任务编排 |
| 观测层 | C11 Ledger | 请求/任务/成本账本 | 压缩/路由 |

## 4. 部署拓扑

### 4.1 当前（As-Is）

```
pi / Codex ──▶ Headroom :8787 (cache) ──▶ provider (gpt-6.1-sol)
```

- pi 插件在 agent 端压缩 toolResult，再由 Headroom 存原文/转发；
- 只有单模型；
- `by_model` 只有 `gpt-6.1-sol`，`routing=null`。

### 4.2 目标（To-Be）

```
pi / Codex / Aider
        │ 原生协议
        ▼
Headroom :8787  (mode=cache)
        │ OpenAI /v1 或 Anthropic /v1/messages
        ▼
LiteLLM :4000
        ├── frontier  → gpt-6.1-sol (medium)
        └── worker    → GPT 低档（DeepSeek 等后接）
```

**关键点**：

1. **LiteLLM 在 Headroom 之后**，不是之前。Headroom 是透明转发代理，拿到请求时不需要知道最终 provider；LiteLLM 负责 alias 解析。
2. **压缩与路由解耦**。Headroom 保持进程级 `cache`；不要试图按请求里的 `model` 字段切 `token/cache`。
3. **成本以 LiteLLM 日志 / provider 账单为准**。Headroom 的 `by_model` 只作诊断；alias 可能让它看不清真实模型。
4. **协议格式由客户端决定**。pi 用 OpenAI 格式、Claude Code 用 Anthropic 格式、Codex 可能用 Responses；每一类都要单独验证。

> **首期 provider 约束**：当前只有 GPT API token，`frontier` / `worker` 都先映射到 GPT 的不同档位；DeepSeek/GLM/Kimi 只是目标示例，key 到位后再接。

### 4.3 为什么不是“LiteLLM 在前、Headroom 在后”

| 方案 | 问题 |
|---|---|
| `agent → LiteLLM → Headroom → provider` | Headroom 的压缩/缓存只服务单一上游；多 provider 时要为每个 provider 配一套 Headroom，且 LiteLLM 的重试/fallback 会绕过压缩层 |
| `agent → Headroom → LiteLLM → provider` | 所有客户端共享同一压缩/缓存层；路由对 Headroom 透明；新增 provider 只改 LiteLLM 配置 |

### 4.4 分阶段拓扑

| 阶段 | 拓扑 | 目的 |
|---|---|---|
| S | `agent → Headroom → provider` | 单 GPT 止血，零架构改动 |
| P0 | 同上 + `.agent/` 账本 | 建立基线 |
| P1 | 同上 + Loom runner | 自动化调度/verify/预算 |
| P2 | `agent → Headroom → LiteLLM → provider` | 多模型路由 |
| P3 | P2 + 多 worktree / 合并队列 | 并行 |
| P4 | P3 + 看板/A-B | 持续优化 |

> P2 之前不要引入 LiteLLM。单 GPT 阶段先把上下文生命周期改对；否则只是把一个模型的浪费复制到两个模型。

### 4.5 兼容性变体

如果 Codex 的 Responses API 无法经 LiteLLM/Headroom 透传，采用降级变体：

- **pi / Claude Code**：走 `Headroom → LiteLLM`；
- **Codex**：走 `Headroom → provider` 直连，仅用 Headroom 压缩/缓存；
- 多模型只对 pi worker 生效，Codex 继续 frontier。

这不是失败，而是**按客户端能力选择路径**；兼容性矩阵见 07。

## 5. 组件清单

| 编号 | 组件 | 职责 | 自研/复用 | 技术建议 | 关键接口 |
|---|---|---|---|---|---|
| C1 | Orchestrator | 目标/任务图/调度/预算/升级 | 自研 | TypeScript + zod | `plan() / next() / decide()` |
| C2 | Runtime Adapter | 把 TaskSpec 变成 pi/Codex 调用，收集 usage | 自研薄层 | CLI 子进程 / RPC | `dispatch(spec) → receipt` |
| C3 | State Store | `.agent/` 读写、schema、锁 | 自研 | FS + JSON/JSONL + git | `read/write/append/lock` |
| C4 | Scheduler | DAG、ready queue、并发、重试 | 自研 | 内存 + 持久化 | `next() / complete()` |
| C5 | Handoff Protocol | TaskSpec/Receipt/Decision schema | 自研 | JSON Schema | `validate()` |
| C6 | Verify Runner | 执行 acceptance、收集证据 | 自研 | subprocess + timeout | `run(spec) → evidence` |
| C7 | Budget Governor | token/成本/时间上限、熔断 | 自研 | usage 流 + 估算 | `check() / stop()` |
| C8 | Model Router | alias → provider、fallback、日志 | 复用 LiteLLM | YAML | OpenAI/Anthropic API |
| C9 | Context Gateway | 压缩/缓存/retrieve | 复用 Headroom | proxy | HTTP |
| C10 | Workspace Isolation | worktree/branch/合并 | 复用 git | `git worktree` | `create/merge/remove` |
| C11 | Ledger | 请求/任务/成本账本 | 自研 | JSONL → SQLite/DuckDB | `record/query` |
| C12 | Prompt Library | orchestrator/worker/judgment prompts | 自研 | Markdown + 版本号 | `load(role)` |
| C13 | Human CLI | run/status/approve/abort/resume | 自研 | commander | CLI |
| C14 | Aider Adapter | 旁路 A/B / diff 生成 | 复用 + 薄封装 | aider CLI | `dispatch(spec)` |

### 5.1 自研边界

**必须自研**（约 1–2k 行，首期可更少）：

- 状态协议与校验；
- 调度状态机；
- verify runner；
- 预算/熔断；
- 账本与指标；
- prompt 模板。

**绝对不自研**：

- Agent Runtime、工具执行、沙箱；
- 压缩器、缓存层；
- provider 路由/重试；
- IDE/TUI。

## 6. 核心流程

### 6.1 初始化

1. 人写 `GOAL.md` / `spec.md` / `design.md`。
2. `loom init` 校验文件、生成 `tasks.json` 骨架、记录 `env.lock`。
3. orchestrator 读目标，产出初始任务图（仅 frontier）。

### 6.2 规划

1. orchestrator 把目标拆成 3–10 个切片。
2. 每个切片写清：输入引用、允许路径、验收命令、预算、依赖。
3. 人只 review 任务图与验收，不 review 每个实现细节。

### 6.3 派发

1. Scheduler 选 ready 任务。
2. State Store 创建 worktree + branch + 任务目录。
3. Runtime Adapter 用 worker prompt + TaskSpec 启动独立上下文。
4. 记录 `task.dispatched` 事件与预算。

### 6.4 执行

1. worker 读 `must_read` 引用；需要更多文件时按路径自读。
2. worker 在 `allowed_paths` 内修改；不碰 forbidden。
3. worker 运行 acceptance；失败先自修，超预算即停。
4. 结束时写 report，输出四行回执。

### 6.5 验收

1. Verify Runner 在干净环境重跑 acceptance（不信任 worker 自述）。
2. 比对 exit code、日志、产物哈希。
3. 通过 → `passed`；失败 → `failed`，进入重试/升级。

### 6.6 合并

1. 合并队列串行处理 `passed` 任务。
2. 合并前检查 base 是否漂移；漂移则 rebase + 重跑 verify。
3. 合并后跑集成 verify；失败则回滚 merge commit 并标记。
4. 更新 `PROGRESS.md`、`DECISION.md`（如有决策）。

### 6.7 升级

1. 同层重试一次；仍失败 → 生成证据包。
2. frontier `judgment` 读证据包，输出 `fix_plan / split / reject / human`。
3. `fix_plan` → 新 worker 任务（带计划与证据引用）；`split` → 拆任务；`human` → 停。
4. 每个任务最多升级一次；每个 goal 有升级总次数上限。

### 6.8 恢复

1. `loom resume` 读事件与任务状态。
2. 重建未完成任务的 worktree；已通过任务不重跑。
3. 未完成回执的任务标记 `unknown`，保留现场，等待人工或重派。

## 7. 任务状态机

```
pending ──▶ ready ──▶ running ──▶ verifying ──▶ passed ──▶ merged
              │          │            │
              │          │            ├──▶ failed ──▶ retrying ──▶ running
              │          │            │                 └──▶ escalated ──▶ passed/failed/human
              │          └──▶ blocked / needs_input / budget_exceeded / timeout
              └──▶ cancelled
```

| 状态 | 含义 | 允许的下一状态 | 触发 |
|---|---|---|---|
| `pending` | 已创建，依赖未满足 | `ready` / `cancelled` | 依赖完成 |
| `ready` | 可派发 | `running` / `cancelled` | Scheduler |
| `running` | worker 执行中 | `verifying` / `blocked` / `needs_input` / `timeout` / `budget_exceeded` | worker 回执/超时 |
| `verifying` | 独立重跑验收 | `passed` / `failed` | Verify Runner |
| `failed` | 验收失败 | `retrying` / `escalated` / `human` | 重试策略 |
| `retrying` | 同层重试 | `running` | 预算允许 |
| `escalated` | 已升级 judgment | `running` / `passed` / `human` | judgment 输出 |
| `passed` | 验收通过 | `merged` | 合并队列 |
| `merged` | 已合并 | — | 集成 verify 通过 |
| `blocked` | 路径冲突/环境问题 | `ready` / `human` | 锁/环境恢复 |
| `needs_input` | 规格不清 | `ready` / `human` | 补充 spec |
| `budget_exceeded` | 超预算 | `human` / `cancelled` | 预算 governor |
| `timeout` | 超时 | `retrying` / `human` | 墙钟 |
| `cancelled` | 人工/目标取消 | — | CLI/目标变更 |

**硬规则**：

- `passed` 必须来自 Verify Runner，不能来自 worker 自述。
- `merged` 必须经过合并队列 + 集成 verify。
- `budget_exceeded` / `timeout` 不自动重试，除非人批准。
- `escalated` 每个任务最多一次。

## 8. 并发模型

### 8.1 基本模型

- Orchestrator 单线程事件循环；所有状态变更串行。
- Worker 并行度默认 **2**，上限 **3**（首期）。
- 同一路径同一时间只允许一个写者；读可以共享。
- 合并队列串行；合并期间暂停新的写任务派发（或只派发只读任务）。

### 8.2 并行收益与风险

| 收益 | 风险 | 对策 |
|---|---|---|
| 缩短墙钟时间 | 路径冲突 | `allowed_paths` + 路径锁 |
| 独立上下文 | 重复劳动 | 任务图去重 + 输入哈希 |
| 独立缓存前缀 | 缓存命中下降 | 主会话串行；worker 各自前缀 |
| 失败隔离 | 合并冲突 | 合并队列 + rebase + 集成 verify |

### 8.3 缓存与并行的关系

- 前缀缓存按“前缀”命中；不同 worker 有不同 system/task 前缀，彼此不影响。
- 主会话的调用必须串行，且前缀稳定；不要在并行任务中让主会话频繁改 prompt。
- 同一模型的并发请求可能触发限流；LiteLLM 负责重试/排队，worker 只感知最终结果。

## 9. 数据持久化

### 9.1 存储选型

| 数据 | 格式 | 是否入库 | 原因 |
|---|---|---|---|
| 目标/规格/设计 | Markdown | 是 | 人可读、可 review、可 diff |
| 任务图 | JSON | 是 | 机器可读、可校验 |
| TaskSpec | JSON（每任务一个文件） | 是 | 可审计、可重放 |
| Receipt | JSON + 四行文本 | 是 | 机器解析 + 人可读 |
| 事件 | JSONL | 否（ignored） | 追加写、可回放 |
| 账本 | JSONL → SQLite/DuckDB | 否（ignored） | 高频写、可查询 |
| 报告 | Markdown | 是 | 人可读、按需加载 |
| verify 日志 | 文本 | 否（ignored） | 体积大、按路径引用 |
| 锁 | JSON | 否（ignored） | 临时状态 |
| 密钥 | 环境/密钥管理器 | 否 | 安全 |

### 9.2 为什么 v1 不上数据库

- 状态文件需要人可读、可 review、可 git diff；
- 任务量首期是每天几十个，不是百万级；
- JSONL 足够做事件与账本；
- 等查询复杂到 JSONL 不够，再引入 SQLite/DuckDB，保持同一 schema。

### 9.3 一致性与锁

- 每个文件一个写者；写者通过 `.agent/locks/<path>.lock` 声明。
- 锁有 `owner / lease_until / mode`；过期可回收。
- 写文件用“临时文件 + rename”原子替换。
- 事件与账本只追加，不修改历史。
- 所有写操作记录 `event`，便于回放。

### 9.4 schema 版本

- 所有 JSON 有 `schema_version`（semver）。
- 迁移脚本放在 `tools/migrate/`；至少兼容一个 minor。
- 读取时先校验版本，再校验 schema；不合法直接拒绝，不“猜”。

## 10. 模型路由设计

### 10.1 层级

首期只保留两档，避免过度设计：

| tier | 用途 | 示例模型 | 约束 |
|---|---|---|---|
| `frontier` | 目标拆解、架构/设计、judgment、关键 review | gpt-6.1-sol @ medium | 上下文小、调用少、只做决策 |
| `worker` | survey、spec-tests、implement、机械重构、文档 | GPT 低档；DeepSeek/GLM/Kimi 后接 | 必须短切片、有 verify、可重跑 |

> 模型名是占位；通过 LiteLLM alias 映射。新增第三档必须先用 CPVT 证明收益。
> **当前只有 GPT API token**：首期 `worker` 也用 GPT 低档模型，跨 provider 路由等 key 到位后再做。

### 10.2 任务类别 → 层级

| 任务类别 | 默认 tier | 例外 |
|---|---|---|
| goal / spec 拆解 | frontier | — |
| 架构、接口契约、数据模型 | frontier | — |
| 测试规格（spec-tests） | worker | 关键安全/支付逻辑由 frontier review |
| 实现（单模块、单接口） | worker | 跨模块重构、并发/安全关键 → frontier |
| 机械重构、格式化、文档 | worker | — |
| verify 失败 judgment | frontier | — |
| 最终合并前 review | frontier | 低风险可抽样 |

### 10.3 路由规则

1. `TaskSpec.tier` **必填**；缺省不推断，直接拒绝。
2. 未知 tier 拒绝；不允许“默认 frontier”。
3. provider 失败只允许**同层 fallback**；不允许静默升级到 frontier。
4. worker 任务必须有 deterministic verify；否则不允许走 worker。
5. 一个任务最多升级一次；升级由 verify 触发，不由模型自评触发。
6. 路由变更（alias、fallback、价格）必须走配置 review，并记录到 `DECISION.md`。

### 10.4 alias 设计

```yaml
# 示意，落地以 LiteLLM 版本为准
model_list:
  - model_name: frontier
    litellm_params:
      model: openai/gpt-6.1-sol
  - model_name: worker
    litellm_params:
      model: openai/deepseek-v4-flash
  - model_name: worker-backup
    litellm_params:
      model: openai/glm-5.3-flash
```

- agent 只认 `frontier` / `worker`，不认 provider。
- alias 变更不影响 TaskSpec。
- 成本账本记录 alias + 真实模型（LiteLLM 日志）。

### 10.5 多 Anthropic 格式模型

- 客户端保持原生 Anthropic Messages 格式；LiteLLM 负责转换。
- 槽位名（如 `default / think / background / longContext`）映射到 alias，不由 Headroom 解析。
- 不要试图用 `model` 字段在 Headroom 里切压缩模式；mode 是进程级。
- 如果某 provider 不支持 Anthropic 格式，走 LiteLLM 的 OpenAI 兼容端点，客户端改 `ANTHROPIC_BASE_URL` 指向网关的兼容入口；需逐项验证 tool calls / streaming / usage。

## 11. 上下文网关设计（Headroom）

### 11.1 定位

Headroom 是**透明压缩/缓存网关**，不是路由器，也不是任务编排器。它解决“单请求内 live-zone 太大”，不解决“历史重发”和“工具结果按值传递”。

### 11.2 当前配置原则

- 保持 `mode=cache`；不要切 `token`。
- 不调低 `HEADROOM_MIN_TOKENS` / `SHELL_RESULT_MIN_CHARS` 去追求压缩率。
- 不启用有损压缩去换缓存稳定性。
- 不叠加 LiteLLM 的 Headroom guardrail；一条请求只有一个压缩归属。
- 不按 `model` 字段切模式；如未来要两种模式，按客户端/端口在进程边界分。

### 11.3 压缩归属

| 客户端路径 | 压缩归属 | 禁止 |
|---|---|---|
| pi + pi-headroom 插件 | 插件压缩 + Headroom proxy 存原文/转发 | 再叠 LiteLLM guardrail |
| Codex | Headroom proxy | 启用 pi 插件 |
| Aider 旁路 | Headroom proxy（cache） | 依赖 `headroom_retrieve` |
| Claude Code | Headroom proxy（cache） | 再叠另一个压缩器 |

### 11.4 能力边界

- `mode` 是进程启动配置，不能 per-request 切。
- 客户端分类看 `User-Agent` / `X-Client`，不看 `model`。
- 订阅态可能触发 `lossless-only` / `live_zone_only`，压缩更保守。
- `size_floor` 会跳过大量小结果（实测约 71% units）。
- `WasteSignals` 是累计检测量，不是节省量。
- `retrieve` 有 TTL；只有注册了工具的客户端（pi）能用；Aider/Codex 不注册则取不回原文。
- 压缩收益远小于缓存收益；不要把优化重点放在这里。

### 11.5 观测口径

- Headroom stats：诊断用（请求数、压缩率、waste signals、延迟）。
- LiteLLM logs / provider 账单：成本权威。
- Runtime usage：任务级估算，用于预算熔断。
- 三者对账，差异 > 5% 要查。

## 12. 安全与隔离

### 12.1 工作区隔离

- 每个写任务一个 git worktree + 分支；不在主工作区直接改。
- worktree 路径放短目录（Windows 长路径）；任务结束保留到合并/归档。
- 合并串行；合并前检查 base 漂移。

### 12.2 路径与命令

- `allowed_paths` / `forbidden_paths` 由 runner 强制，不靠 prompt 自觉。
- 命令 allowlist：测试、lint、typecheck、build、git 只读；危险命令拒绝。
- 默认禁网；需要网络的 verify 显式声明并记录。
- 所有命令有超时；输出截断后写日志文件。

### 12.3 密钥与隐私

- 密钥只从环境变量/密钥管理器读取；不写入 `.agent/`、prompt、日志。
- 日志脱敏：API key、token、cookie、连接串。
- 本地优先；默认不上传代码/日志到第三方（除模型 provider 本身）。

### 12.4 提示注入

- 仓库内容、issue、网页、工具输出都视为**不可信输入**。
- verify 命令只能来自 TaskSpec，不能由 worker 临时发明。
- worker 不得根据仓库内文本改变 `allowed_paths` 或验收标准。
- 关键任务由 frontier review diff，不只看回执。

## 13. 可观测性

### 13.1 事件

所有状态变更写 `events.jsonl`：

```json
{"ts":"2026-11-04T12:00:00Z","run_id":"R-001","task_id":"T-001","type":"task.dispatched","data":{"tier":"worker","model":"worker","attempt":1}}
```

事件类型：`run.started / goal.loaded / task.created / task.ready / task.dispatched / task.started / task.receipt / task.verify / task.passed / task.failed / task.escalated / task.merged / task.blocked / budget.warning / budget.exceeded / run.finished / human.approved / human.aborted`。

### 13.2 账本

每次 LLM 请求一行，字段见 03。聚合维度：`run / task / attempt / tier / model / provider / day`。

### 13.3 看板（首期可用 CLI/CSV）

- 今日/本周 CPVT；
- cache hit；
- resend ratio；
- handoff overhead；
- first-pass verify；
- escalation rate；
- budget exceeded 次数；
- waste signals 增速（Δ/Δrequests）。

### 13.4 告警

- cache hit 下降 > 10pp；
- 单任务成本 > 预算 80%；
- 同一错误连续 3 次；
- provider 5xx/429 激增；
- 账本出现 `unattributed`；
- 合并后集成 verify 失败。

## 14. 失败模式与降级

| 失败 | 表现 | 降级策略 | 恢复 |
|---|---|---|---|
| Headroom 挂 | 所有请求失败/超时 | 客户端临时直连 provider（保留缓存失效告警） | 重启 proxy，检查 mode |
| LiteLLM 挂 | 路由失败 | 同层直连 provider（如果配置了 backup） | 重启，检查 alias/密钥 |
| provider 429 | 限流 | 指数退避 + 同层 fallback | 降低并发/换 provider |
| provider 5xx | 上游错误 | 重试 2 次 → 同层 fallback → 停 | 查状态页 |
| verify flaky | 同任务时好时坏 | 标记 `flaky`，最多重跑 2 次；仍不稳定转人工 | 修测试或隔离 |
| 状态文件损坏 | 解析失败 | 从事件回放重建；保留损坏文件 | 修复/迁移 |
| worktree 冲突 | 合并失败 | rebase + 重跑 verify；冲突大则拆任务 | 人工合并 |
| 预算超限 | 任务中止 | 保留现场，转人工/拆小 | 调预算/拆任务 |
| 缓存命中骤降 | 成本上升 | 回滚 prompt/工具变更；检查前缀 | 恢复稳定前缀 |
| 账本不一致 | 成本对不上 | 以 provider 账单为准；修正归因 | 对账脚本 |

**总原则**：宁可降级到“慢但正确”，不要降级到“静默错误”。

## 15. 技术栈建议

### 15.1 推荐

| 层 | 选择 | 理由 |
|---|---|---|
| 编排器 | TypeScript / Node 20+ | 与 pi/MCP 生态一致；JSON Schema、子进程、CLI 成熟 |
| Schema | zod / JSON Schema | 运行时校验 + 文档生成 |
| CLI | commander / clipanion | 简单、跨平台 |
| 子进程 | execa | 超时、信号、输出流处理 |
| Git | simple-git / `git` CLI | worktree、diff、merge |
| 账本 | JSONL → SQLite/DuckDB | 先简单，后可查询 |
| 测试 | vitest | 与 TS 生态一致 |
| 网关 | Headroom + LiteLLM | 复用，不自研 |
| 隔离 | git worktree + 可选容器 | 够用、低成本 |

### 15.2 备选

- Python：如果团队更熟 Python，用 `pydantic` + `typer` + `subprocess`；协议不变。
- Go：单二进制、部署简单；但 JSON Schema/生态不如 TS 顺手。
- Claude Agent SDK：如果不想用 pi/Codex 的 subagent，可用它做 worker runtime；不要用它重写全部编排。

### 15.3 不建议

- 自研 TUI/IDE 插件：先把协议跑通。
- 自研压缩器：Headroom 已够用，且收益低。
- 自研 provider 路由：LiteLLM 已够用。
- 一开始上 Kubernetes/云：单机 CLI 足够。

## 16. 关键设计决策（ADR）

### ADR-001 不自研 Agent Runtime

- **决策**：复用 pi / Codex / Claude Agent SDK 作为执行端。
- **理由**：runtime、工具执行、沙箱、流式、重试都是重活；自研 API 会漂移。
- **代价**：受 runtime 版本/能力约束；用 Adapter 隔离。
- **替代**：自研 runtime（否决：成本高、无差异化）。

### ADR-002 状态用文件 + JSONL，v1 不上数据库

- **决策**：Markdown/JSON 状态文件 + JSONL 事件/账本；查询复杂后再上 SQLite。
- **理由**：人可读、可 diff、可 review；首期数据量小。
- **代价**：复杂查询弱；用脚本补。
- **替代**：一开始 SQLite（否决：状态不可读、review 成本高）。

### ADR-003 Hub-and-spoke，worker 不互聊

- **决策**：所有协调经 orchestrator 与共享状态文件；worker 之间无直接通道。
- **理由**：避免网状通信的重复计费与目标漂移；单点对齐。
- **代价**：orchestrator 是瓶颈；用任务图与异步缓解。
- **替代**：worker 网状协作（否决：不可审计、token 爆炸）。

### ADR-004 路由按显式 tier，不做 LLM 自评

- **决策**：TaskSpec.tier 必填；任务类别 → tier 映射。
- **理由**：可解释、可审计、可回滚；避免“模型觉得自己不行就升级”。
- **代价**：人/编排器要维护映射；用数据迭代。
- **替代**：LLM 复杂度分类（否决：v1 不稳定）。

### ADR-005 升级只由 verify 触发，最多一次

- **决策**：verify 失败两次 → frontier judgment → 最多一次升级。
- **理由**：验收可执行；防止无限循环和自评漂移。
- **代价**：verify 覆盖不足时会误判；用 spec-tests 补。
- **替代**：模型自评升级（否决）。

### ADR-006 Headroom 保持 cache，压缩归属唯一

- **决策**：`mode=cache`；一条请求只允许一个压缩器；不按 model 切模式。
- **理由**：缓存收益 $270 vs 压缩 $2.35；模式是进程级。
- **代价**：压缩率不最大化；接受。
- **替代**：双实例 token/cache（否决：收益小、复杂度高；未来可按客户端/端口分）。

### ADR-007 LiteLLM 在 Headroom 之后

- **决策**：`agent → Headroom → LiteLLM → provider`。
- **理由**：所有客户端共享压缩/缓存；路由对 Headroom 透明。
- **代价**：Headroom 看不到真实模型；成本以 LiteLLM 为准。
- **替代**：LiteLLM 在前（否决：多 provider 要多个 Headroom）。

### ADR-008 主会话不读 worker transcript

- **决策**：orchestrator 只读四行回执 + report 路径 + verify 证据。
- **理由**：避免 transcript 注入导致上下文爆炸；强制结构化。
- **代价**：回执信息量有限；需要好的 report 与证据包。
- **替代**：主会话读摘要（否决：摘要也会膨胀、会漂移）。

### ADR-009 单写者 + append-only

- **决策**：每个状态文件一个写者；事件/账本只追加；写文件原子替换。
- **理由**：并发安全、可回放、易审计。
- **代价**：并行写要排队；用锁与合并队列。
- **替代**：多写者 + 锁（否决：复杂、易冲突）。

### ADR-010 成本以 provider/LiteLLM 为准

- **决策**：provider 账单 > LiteLLM 日志 > runtime usage > Headroom stats。
- **理由**：Headroom 只看请求，不知道 alias/真实价格；stats 有累计口径陷阱。
- **代价**：需要对账；用脚本。
- **替代**：用 Headroom stats 当账单（否决：会误导）。

## 17. 一页纸总结

- **不改 runtime，不改 headroom 模式，不先接多模型。**
- **先做三件事**：状态外置、切片派发、四行回执 + verify。
- **再做一个薄 runner**：任务图、预算、升级、恢复、账本。
- **最后才做路由**：LiteLLM 放在 Headroom 之后，两档模型，显式 tier。
- **主 KPI**：`CPVT`（成本）+ `TPVT`（token）。
