# 18 Agent 协作工作法提案

> 语言：[English](18-agent-collaboration-workflow-proposal.md) | **简体中文**

> **状态：方法提案，未实施（2026-11-12）。** 工作名暂用《Loom 工作法》，占位，随时可改。
> 读者：打算用 agent 开发产品、但不熟悉项目管理的人。
> 结论先行：几十年流程史沉淀下来的存活原则只有几条（小步、短反馈、验收前置于合并、限制在制品、状态外置、预算不估点），失效的是仪式与角色；本提案按存活原则重排节奏，把人的参与收窄到四个介入点，六条命令即可上手。

## 1. 问题

两个症状同时出现：

- **设计完整、实施漂移**：大 spec 写完，agent 按惯性自动实施，记忆偏移，方向越走越偏；
- **烧 token 不出活**：agent 花在“重新理解设计”上的开销，远大于落在 diff 上的开销。

根因是同一件事：把“执行者能随时回翻、长期 hold 住大设计”当成前提，而 agent 没有这个能力。人需要的不是更大的 prompt，而是另一套把“决定什么、验收什么、卡住找谁”说清楚的节奏。

## 2. 六十年流程史：什么失效了，什么还成立

| 流程 | 年代 | 当年解决什么 | 对 agent 开发的现状 |
|---|---|---|---|
| Waterfall | 1970s | 大型合同、可预测性 | 失效。正是“大 spec 实施漂移”的源头 |
| RUP | 1990s | 迭代、风险前置 | 迭代思想存活，文档体量失效 |
| **XP** | 1990s | 短反馈、TDD、持续集成、小发布 | **存活度最高**：核心实践全部可机器执行 |
| Scrum | 1990s–2000s | 优先级对齐、节奏、可见性 | 节奏与角色部分失效，见 §3 |
| Kanban / Lean | 2000s | 限制在制品、可视化流动 | 存活。WIP 上限即并发上限 |
| DevOps / 持续交付 | 2010s | 主干开发、自动验证 | 存活，已实现为合并队列与集成验收 |
| Stage-gate | 产品开发 | 阶段末设人决策门 | 存活，对应“四个介入点” |
| V 模型 | 软硬件/安全关键 | 每条需求配对一条验证 | 存活，即验收与 spec 一一对应 |
| Shape Up | 2019 | 固定预算、范围可变、不估点 | 存活，即任务预算取代工时估算 |
| 设计文档 / ADR 文化 | 2010s | 决策书面化、可追责 | 存活，对应契约层与方向记录 |
| Spec-driven AI | 2023– | 用大文档驱动 agent | 失效，即本文要解决的症状 |

流程史里被反复发明、又反复失效的东西是仪式（每日站会、故事点、迭代计划会）；被验证有效的原则只有几条，见 §3。

## 3. 存活的六条原则

1. **小步**：变更小到可评审、可回滚。对应工作项切片与 `max_files_touched`。
2. **短反馈**：变更与验证之间的延迟最短。对应 acceptance 命令与逐片 verify。
3. **验证前置于合并**：不通过验证的变更不进主干。对应合并队列的 pre-merge verify。
4. **限制在制品**：同时进行的事不超过可评审能力。对应 `parallel.max_running`。
5. **状态外置**：进度与决策写在盘上，不依赖任何参与者的记忆。对应契约层与事件日志，也是 agent 记忆偏移的正解。
6. **预算取代估点**：不做工时估算，直接给出上限，超了就停或拆。对应 TaskBudget 的 token/成本/墙钟。

## 4. 已经失效、不再照搬的部分

- **固定时间盒**（两周 Sprint）：agent 按验收推进，不按日历推进；
- **故事点与速度**：真实货币是 token、成本与落地 diff 数，`route stats`/`churn stats` 就是仪表盘；
- **每日站会**：进度由事件日志重放，`loom board` 即站会；
- **角色头衔**（PO/SM/开发）：收敛为 §5 的四个介入点与三个执行者；
- **前期大 spec**：契约层只放方向、不变量与模块契约，设计全文是按需读取的输入，不是执行指令；
- **会议驱动的协调**：协调走协议，升级走结构化报告与收件箱。

## 5. 工作法本体

### 5.1 词汇

| 概念 | 落点 | 生命周期 |
|---|---|---|
| 方向 | `goal.md` 主路线 + 非目标 | 方向变更才改 |
| 契约 | `constraints.md` + `.loom/specs/` | 缓慢演化，每步注入 |
| 批次 | `loom plan` 一次切出的一组工作项（`depends_on` 串接） | 每次开一批 |
| 工作项 | TaskSpec + acceptance | 一片一验收一合并 |
| 门 | 机器门（exit code）与人门（证据审阅）两级 | 合并前 |
| 升级 | `needs_input`（已实现）+ 收件箱 + 结构化报告（见 `doc/15`，待实现） | 随时 |
| 账 | usage / churn / route stats | 每批复盘 |
| ADR | `doc/adr/` 决策记录（含模型能力假设字段） | 写一次，被推翻只 Supersede、不改原文 |

硬件与软硬结合的产品，其物理验收走人门：工作项产出测量、照片或实测记录作为 artifact，批次关闭时由人按证据放行。风险未知的部分按 spike 切片，先验证再进主路线。

### 5.2 节奏

```
定向（方向变更时）   人提问 → loom goal 起草 → 人审 diff
开批（每批次一次）   人选当前方向与紧急度 → 模型切片 → 人审 TaskSpec
跑片（每工作项）     dispatch → verify → merge，agent 循环，卡住即升级
关批（批次结束）     board + stats 复盘 → 确认过的失败转回归用例/验收（无用例不关批）→ 记方向记录 → 回到开批
```

节奏由验收与预算驱动，不由日历驱动。

### 5.3 人的四个介入点

1. **定向**：改不改方向；
2. **开批**：现在做哪批、为什么急；
3. **审片**：合并前看 diff（即 `loom merge` 这个动作本身）。工程变大后人审会退化为橡皮图章，这一项的演进路线见 §8；
4. **接升级**：回答收件箱里的结构化问题。

除此之外人不参与。四个点全是判断类工作，不可自动化；其余全部交给控制面。

### 5.4 三个执行者

| 执行者 | 职责 | 边界 |
|---|---|---|
| 人 | 定方向、开批次、审落地、答升级 | 不做拆分，不做进度复述 |
| agent | 只做被切好的工作项，交付验收证据 | 不选题、不改验收、不碰禁区；卡住交报告而不是硬试 |
| 控制面（Loom） | 编排、验收、记账、报警、重放进度 | 不做业务判断，不替人决定优先级 |

## 6. 新人上手路径

全部技能是两个决策加六条命令：

```text
loom init → loom goal -i → loom constraints   # 定向
loom plan                                      # 开批（选组、切片）
loom dispatch → loom verify → loom merge       # 跑片循环
loom board / loom route stats                  # 看进度与复盘
```

从零到平台的路径：

- **第一天**：init、定向、第一批落地两三片，见到第一个可合并 diff；
- **第一周**：多批循环，`specs/` 随模块落地生长，方向记录积累；
- **之后**：平台按批长大，磁盘上的契约层就是平台的记忆，新 agent 与新人走同一条上手路径。

不依赖理解 agent 的记忆机制与 token 经济，那是控制面的事。

## 7. 非目标

- **不做自动规划**：批次、优先级、方向永远由人决定，`AGENTS.md` 列其为不要提前做的事项；模型只切片，不选题；
- 不做仪式本身：不为“像敏捷”增加任何会议或角色头衔；
- 不做估点与速度度量；
- 不做通用项目管理 SaaS；本工作法是 Loom 上的方法层，不是新产品线。

## 8. 落地

1. 建 `loom plan`（开批仪式的核心命令，含非交互预览与人审 diff）；
2. 方法文档与 README 快速上手段随 `loom plan` 一起落地，命令与仪式互相验证；
3. 四步计划剩余的 judgment gate 先收尾，它对应机器门的最后一环，也是审片演进的前提。

### 8.1 审片的演进

前提是人会随工程变大而偷懒：改动量超过某个规模，人审必然退化为橡皮图章。所以 agent 辅助审不是可选项，是这条介入点能否长期存活的条件。按信任积累分三级：

| 级别 | 谁看什么 | 人的工作量 |
|---|---|---|
| **v1（现状，已确认）** | 人读全部 diff 后手动 merge，与当前做软件的步骤一致 | 全量 |
| **v2** | review 任务（review 角色、frontier 模型）产出带文件/行号引用的 verdict 报告；人读结论 + 抽查关键 diff | 降为读报告 |
| **v3** | 审查强度可配置：严格模式要求 `verdict: pass` 才允许合并且人终审；信任积累后放松为按比例抽查 | 只剩抽查 |

边界：agent 在三级里都只产出建议与证据，**合并决策始终在门禁策略里，人保留终审与否决权；取消人审不在提案范围内**。v2 的前提是 judgment gate 落地，让 verdict 被门消费（目前 verify 只检查 verdict 字样存在，见四步计划）。

在 `loom plan` 落地前，本文只是提案。
